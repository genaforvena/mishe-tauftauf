# Freshness: a coarse-grained lease used as a fine-grained verdict, and polling where Chubby chose invalidations

## What we read

**The Chubby lock service for loosely-coupled distributed systems** — Mike Burrows, Google Inc. *OSDI '06*, pp. 1–16. <https://static.googleusercontent.com/media/research.google.com/en//archive/chubby-osdi06.pdf> — full text read (16 pages; local copy /tmp/chubby-osdi06.pdf 115 KiB, 1546 lines via `pdftotext`; citations by PDF page and by extracted line).

This is the paper that names the failure mode of treating a session/presence lease as a fine-grained correctness signal, and — for a critique — it also names what the designers got wrong and had to repair.

1. **Coarse-grained only (§1–2, p. 1–2; l. 5, 164, 188).** "intended to provide coarse-grained locking" (abstract); "We do not expect lock use to be fine-grained, in which they instead, we expect coarse-grained use" (§2.1, l. 164); "Chubby is intended to provide only coarse-grained locking ... implement their own fine-grained locks" (§2.1, l. 188). A lease that is safe at coarse grain becomes a load amplifier when polled at fine grain.

2. **Session, lease, and KeepAlive (§2.7–2.8, pp. 6–8; l. 595–682).** Each session has a lease — "an interval of [time] guarantees not to terminate the session unilaterally" — end called "session lease timeout" (l. 611). Master advances timeout on creation, fail-over, or KeepAlive reply (l. 616). Default extension 12 s (l. 621). KeepAlive reply piggybacks events and cache invalidations (l. 627). "The client maintains a local lease timeout that is a conservative approximation of the master's lease timeout ... the server's clock advance no faster than" (l. 635–640). If the client's local timeout expires, "its session is in jeopardy. The client empties and disables its cache" and waits a further grace period (l. 642–651). Only if that too expires is the session expired; "jeopardy" vs "expired" are distinct verdicts with different actions (cache flush + block API vs tear down, l. 719–782).

3. **Sequencers as fencing (§2.4, p. 4; l. 369–424).** "At any time, a lock holder may request a sequencer, an opaque byte-string that describes the state of the lock" (l. 410). Client passes sequencer to servers; server checks with `CheckSequencer` against its Chubby cache or last observed sequencer (l. 417–421). Without sequencers, "imperfect but easier mechanism" is cache flush on release (l. 424).

4. **Scaling by lease extension, not faster polling (§3, p. 8; l. 921–929).** "The master may increase lease times from the default 12 s up to around 60 s when it is under heavy load, so it need process fewer KeepAlive RPCs. (KeepAlives are by far the dominant type of request ..., and failure to process them in time is the typical failure mode of an overloaded server)" (§3, l. 923). Increasing the lease reduces load; decreasing the check interval increases it.

5. **Polling vs invalidation (§4.3, p. 10; l. 1179–1197).** DNS TTL caching "based on time ... discarded when they have not been refreshed within that period" (l. 109). To replace failed services promptly, "TTL can become small enough to overload the DNS servers" — example 3k clients → 150k lookups/s vs Xeon handling 50k/s (l. 1190). "In contrast, Chubby's caching uses explicit invalidations so a constant rate of session KeepAlive requests can maintain an arbitrary number of cache entries indefinitely at a client, in the absence of changes" (l. 1197). A proxy reduces KeepAlive traffic by factor Nproxy (~10k) and read traffic by mean sharing (~10, l. 951).

6. **What the paper concedes as mistakes (§4–4.6, pp. 11–15; l. 1124–1365).** §4.4 fail-over: optimisation that deferred DB writes for read-only sessions meant "young read-only sessions may not be recorded ... may be discarded if a fail-over occurs ... this is unsafe; ... could then read stale data" (l. 1205–1220) — repaired by waiting full worst-case lease (l. 1245). §4.5 abusive clients: "Lack of aggressive caching" — developers "regularly write loops that retry indefinitely when a file is not present, or poll a file by opening it and closing it repeatedly" (l. 1268); " Lack of quotas" — one 1.5 MB file rewritten on each user action exceeded all other clients (l. 1285). Remedies: limit file size 256 kB, make repeated Open cheap rather than punishing retries (l. 1292). §4.6: "we would prefer developers to plan for short Chubby outages, so that such an event has little ... affect" — and three mechanisms to prevent over-optimism about availability (l. 1326–1341).

This is the same hedging Chubby's §2.1 intends for coarse grain, but the check still consumes the lease as a failure verdict.

## What is new here

**The critique Chubby makes, read literally, is that freshness implemented as frequent polling of a lease does not scale, that a lease expiry under load is jeopardy rather than failure, and that a coarse-grained presence signal must not be consumed as a fine-grained correctness gate.** Each point maps to this plant without analogy.

1. **A coarse-grained presence lease consumed fine-grained.** Chubby §2.1 prohibits fine-grained lock use and offers sequencing for the one case that needs it. This plant's pane lease advances "ticks every frame" (footer literal at `observations.py:23`) — presentation liveness — but `wall_view.py:133-135` turns that into a per-tick staleness verdict read by `pane_lease_lines` from every render (diagnostic/host/operator views compose the same path). The paper's term is misbehaviour: polling that grows with data (4.5) and expecting prompt replacement at TTL cost. The plant's own predecessor measurement (2026-10-22, 350 accusations, 92% inside 20–28 s renderer cycle) already showed the cost of treating every render-cycle edge as a suspicion.

2. **Lease expiry under load is jeopardy, not failure, and the lease must lengthen when the server is slow.** Chubby §3's scaling remedy is literally lease extension: 12 s → 60 s "when it is under heavy load, so it need process fewer KeepAlive RPCs" (l. 923). The dashboard at entry is `host-capacity LIMITED/CRITICAL` with `RENDERER BYTES` and `PANE LEASE` contending for the same host. A fixed `max(120, 6*refresh)` does not lengthen; it is the TTL that §4.3 warns requires 150k lookups/s. Chubby's correct response to "failure to process [KeepAlives] in time is the typical failure mode of an overloaded server" is to extend the lease, flush the cache, and enter jeopardy — not to record `RED stale` and trigger downstream work. This plant today has no jeopardy vocabulary: `wall_view.py:140` collapses Chubby's two states into one (`RED`), and there is no grace timer or cache-disable-then-retry.

3. **Polling a TTL vs receiving an invalidation.** §4.3's contrast is the paper's central critique of freshness: DNS discards after TTL; Chubby "uses explicit invalidations so a constant rate of ... KeepAlive ... can maintain an arbitrary number of cache entries indefinitely ... in the absence of changes." The pane lease is read by `tmux capture-pane` polling (-S -5) at `:104` every diagnostic compose, even when no window changed. The plant has no event for "renderer advanced" — the reader re-reads the timestamp. The proxy lesson (KeepAlive reduction factor Nproxy) is that batching and caching the *absence* of change is the scaling mechanism; this plant instead re-captures every pane on every render.

4. **The sticky-unsafe action is the same one Chandra-Toueg identified, but Chubby names its operational analogue.** §4.4 fail-over shows a fixed-timeout optimisation that discarded young read-only sessions was "unsafe" because they "could then read stale data" (l. 1220) — repaired by waiting the full worst-case lease. The plant's analogue is `coordination/site_sync.py:282-431` (prior critiques) pinning `observed_sha` behind a `stale` verdict; `wall_view.py` pins `PANE LEASE: RED` behind a polled age. Chubby's paper refuses to mask the ambiguity: a jeopardy event is delivered (§2.8, l. 719: "grace period begins via a jeopardy event"), the client blocks API calls (l. 765), and only expiry after grace tears down. The plant skips that middle state.

**What this reading does not claim.** Chubby's session protocol assumes a master that actually holds leases, replicated via Paxos, with explicit KeepAlive RPCs and a replicated DB — none of which the pane footer has. The pane footer is a single-process write to a tmux pane buffer, not a distributed lock service; there is no master to extend the lease and no "session" to store. The sequencer (§2.4) has no analogue in the pane footer — the closest is the session-receipt journal's Lamport ID. The numeric 12 s → 60 s range is not portable to a `max(120, 6*refresh)` that is already generous on one host. What transfers is the *critique* (coarse vs fine grain, fixed TTL vs invalidation, load-adaptive lease, jeopardy vs failure), not the mechanism constants.

**Relation to predecessors.** 2026-10-22 (Chandra-Toueg) proposed a repentant detector: retract suspicion + widen per-peer timeout after a mistake. 2026-11-01 (Huang) showed the retry loop that retries the wrong thing. Chubby's critique is distinct: it asks whether the lease *should have been* a fine-grained verdict at all, and whether expiry should even be a verdict yet when the host is shed. It does not contradict Chandra-Toueg; it scopes it — per-peer widening is Chubby's post-mistake repair, while Chubby's pre-mistake repair is preemptive lease lengthening under load and jeopardy distinction.
