## What is new here

Canciani's contribution is not another Merkle detail but a terminology and auditability boundary that RFC 9162 assumes: authenticated structures prove authenticity and integrity of a datum but not that the sequence of operations that produced it was consistent, and current literature "proposes some approaches aimed at executing audits by internal actors with prior knowledge". The externally auditable refinement makes the gap testable:

1. **Three definitions separate concerns.** Digest (second-preimage-resistant state identifier) vs consistency (reachability by valid edits between a pair) vs history consistency (pairwise consistency across a whole ordered digest list). RFC 9162's Merkle consistency proof is one instantiation; Canciani's definition is operation-validity, which matters for this plant where the only valid edit is append.
2. **External auditor without prior knowledge and without data.** An externally auditable structure must expose a history devoid of data — digests and consistency proofs that are one-way indirections — so secrecy is preserved. This is strictly stronger than "an auditor can re-read the tape": it asks whether the history can be checked *without* reading the prose or the `artifacts/` bytes.
3. **Trusted storage + incremental extension.** The server writes digests and consecutive-pair consistency proofs to trusted storage on each edit; the auditor reads that store, not the server. Verification is pairwise between consecutive digests in the published list. This separates where history lives (trusted) from where data lives (server), which the plant currently collapses (one host writes chat.log, evidence files, and the observer's reading).
4. **Operational taxonomy with surveyed limits.** Edit-operation replay (full log re-execution), data-exposing proofs, and Merkle proofs trade secrecy for completeness in distinct ways. LedgerDB and QLDB provide internal auditability (require journal/data) but fail the external test; Trillian and Traent pass it by anchoring Merkle consistency proofs in a separate verifiable structure (Traent's ledgers-tree on Algorand publishes one digest sequence for a collection). The paper's own limit: it is a terminology + framework + survey, not a new cryptographic construction; it states the problem is early-stage and does not claim a single proof system.

For this plant the transferable point is framing: per-outcome `sha256` is an integrity proof for one artifact; `supersedes` chains are edit operations; but the plant's outcome history today has no published digest list that an external auditor without the chat prose or artifact bytes could verify for history consistency by pairwise proofs. Naming that distinction does not change any tape shape or verification, and it complements (not duplicates) the RFC 9162 mechanism note: RFC names the Merkle proof shape; Canciani names when any proof counts as externally auditable and when it does not.
