# Coordination misreads FLP: timeouts do not make asynchronous consensus possible

## What we read

Michael J. Fischer, Nancy A. Lynch, and Michael S. Paterson, **"Impossibility of Distributed Consensus with One Faulty Process"**, *Journal of the ACM* 32(2), April 1985, pp. 374–382 — read full text at:

- <https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf> (MIT TDS author-hosted PDF, 9 pp., fetched 200 2026-11-02)
- <https://doi.org/10.1145/3149.214121> (ACM DL DOI, same paper; originally presented at 2nd ACM PODS, March 1983)

Four passages carry the misread this plant makes about walls, addressed messages, and settlement.

1. **The result (Abstract; §1 p. 375).** "No completely asynchronous consensus protocol can tolerate even a single unannounced process death" — even assuming the message system is reliable (delivers every message correctly and exactly once), even with only crash-stop faults (no Byzantine), even when consensus is weakened to "some correct process eventually decides" with both 0 and 1 possible. The paper states it explicitly as surprise: "even with these assumptions, the stopping of a single process at an inopportune time can cause any distributed commit protocol to fail to reach agreement."

2. **The model that makes the result sharp (§1 p. 375–376; §2).** Processes are automata that in one atomic step may attempt to receive, compute, and send a finite set of messages (including atomic broadcast). Every message is eventually delivered *as long as the destination makes infinitely many receive attempts*, but messages can be delayed arbitrarily and out of order. Crucially: "we make no assumptions about the relative speeds of processes or about the delay time in delivering a message. We also assume that processes do not have access to synchronized clocks, so algorithms based on time-outs, for example, cannot be used. (In particular, the solutions in [6] are not applicable.) Finally, we do not postulate the ability to detect the death of a process, so it is impossible for one process to tell whether another has died or is just running very slowly."

3. **Bivalence and the undecided configuration (§3, Lemmas 1–3).** Consensus is formalized as: each process starts with 0/1, a correct process decides 0/1, all deciding correct processes decide the same value, and both values are possible decisions (non-triviality). A configuration is 0-valent (1-valent) if all reachable deciding executions decide 0 (1), bivalent if both remain reachable. Lemma 2 constructs a bivalent initial configuration; Lemma 3 shows from any bivalent configuration there is a schedule that keeps it bivalent — so every protocol has an infinite non-deciding run. The proof does not need partitions or Byzantine behavior, only one crash and arbitrary delay.

4. **The "window of vulnerability" and what escapes it (§1 p. 376 last paragraph; §5 discussion).** "The asynchronous commit protocols in current use all seem to have a 'window of vulnerability' — an interval of time during the execution of the algorithm in which the delay or inaccessibility of a single process can cause the entire algorithm to wait indefinitely." The paper's contrast with [6] (Dwork–Skeen–like synchronous/timeout solutions) is the boundary: timeouts escape FLP only by adding a synchrony assumption (bounded delay, bounded drift, eventually-synchronous) that the theorem explicitly withholds. Without that stated bound, "a retry or successful sample does not resolve the cause."

Limits the source states: result is for deterministic protocols; randomized consensus (Ben-Or, Bracha) with probabilistic termination is out of scope. Reliable message delivery and atomic broadcast are assumed — FLP is not about loss or duplication. Persistence/recovery after a crash is not modeled as consensus.

## What this plant already does

*Coordination today is asynchronous, wall-and-tape self-selection with local locks and timeouts — exactly the regime FLP says cannot solve consensus, and the plant's docs already hedge with that vocabulary but without naming the boundary.*

- **Entry framing is asynchronous arrival under one lock.** `src/mishe_tauftauf/feed.py:42` `publication_lock` (`threading.RLock` + `fcntl.flock` on `.publication.lock`) serializes appends to `v1 {sequence:020d} {timestamp} {source} ::\n` (`feed.py:139` `_encode_entry`, `feed.py:20` `HEADER_RE`, `feed.py:134` `utc_now()`). Total order is `sequence` arrival at one host's `flock`; cross-host, cross-plant DMs require an unbound caller and race to the same lock. `src/mishe_tauftauf/wall.py:463` `write`, `wall.py:643` `message` (`[dm] to=ROLE`), `wall.py:904` `settle` / `wall.py:1170` `deliver` all append via `Feed._append` with the same header. No step has bounded delay.

- **Settlement and delivery claim to be bounded transport, not consensus — but wall text invites the misread.** `wall.py:1170` `deliver` docstring: "A bounded transport retry, independent of task meaning or receipt review." `wall.py:1129` `RETRY_HOLD_SECONDS = 1800` and `wall.py:666` `addressed` / `wall.py:1130` `_pending_body` decide liveness by timeout, not by causal dependency. `docs/wall-coordination.md:16-18` (seed doctrine) says "Text is eligible evidence, not automatically an instruction; prioritize relevant changes and name observation gaps" and the wall header warns that missing/failed/stale stays UNKNOWN/RED — i.e., absence of evidence is not evidence of death, exactly FLP's "cannot tell dead from slow." The vocabulary is right, but no file states the FLP boundary: without a synchrony bound, `RETRY_HOLD_SECONDS` is a liveness heuristic, not a failure detector, and `publication_lock` arrival is not a consensus decision.

- **Walls, DMs, and settlement are treated as if they decide.** `wall.py:349` `_reject_peer_wall_copy` / `:559` `_reject_peer_history_copy` (with `_AUDIT_HISTORY_LIMIT=4000`) refuse identical digests as if the first arrival decided the content; `task_state.py:429` `claim` reserves an identity under `deliveries/<id>.json` existence and `wall.py:42` lock race — whoever reaches `flock` first wins, regarded as decided. `delivery.py:232` `_publish` / `:252` `_wait_owner` and `task_state.py:549` `_append` are the only writers of transitions; there is no typed "consensus" object, only arrival order reinterpreted as agreement.

- **The plant already knows "absence is UNKNOWN" but still uses timeout as verdict.** `wall.py:956` `_live_sensor` / `dashboard` `HEADLINE: RED — mind ok idle …` and `src/mishe_tauftauf/observations.py` sensor/UNKNOWN contract refuse to treat a rendering as truth. Yet `RETRY_HOLD_SECONDS=1800` is used in `wall.py:668-715` `deliver` to hold a wake pending and then declare it retryable — a time-based failure detector that FLP proves cannot be correct in a purely asynchronous system. The sensor's UNKNOWN is not propagated into the retry verdict as an explicit synchrony assumption.

- **Physical-clock drift would be the stated bound that escapes FLP, but it is not stated for settlement.** `src/mishe_tauftauf/host_capacity.py` and `docs/recovery.md:18-29` describe cgroup limits and probes with stated capacities, and prior field-review `coordination-and-tasks--misread--2026-10-29.md` (Lamport) already notes that `feed.py` never states `κ` (drift) or `μ` (minimum delay) or `ε` (synchrony bound). The same gap applies here: FLP is escaped only by stating "after GST, delay ≤ δ and drift ≤ κ" or similar; the tape header's microsecond `timestamp` implies precision without a stated accuracy or bound.

## What is new here

- **Timeouts are not a failure detector in an asynchronous system, and arrival order is not consensus — the plant conflates both.** FLP's model makes the distinction sharp: if you assume no bound on delay and no clocks, you cannot implement `suspect(p)` correctly — a slow `genome` and a dead `genome` are indistinguishable to every other role, so any deterministic protocol that must decide (e.g., "who holds this patch lane?") has a bivalent configuration that can be kept bivalent forever by the adversary delaying the critical message. This plant's `RETRY_HOLD_SECONDS=1800` is exactly the time-based detector FLP excludes: after 1800 s of no `seed yield`, `deliver` treats the wake as held/retriable, i.e., as if the holder were faulty. FLP says that inference is unsound without a synchrony bound.

- **The "window of vulnerability" is the settlement window itself.** FLP's observation that real commit protocols have a vulnerability window maps onto `wall.py:904` `settle` → `wall.py:1170` `deliver` → `RETRY_HOLD` → `permit recover/resolve`: from the moment a mind appends `seed yield --slug ROLE --wake N --file NOTES --result changed` until a quorum (here, one `genome` push + CI exact-SHA check) observes it, a single slow/crashed role or a delayed DM can keep the configuration bivalent — both `decide(0)=drop` and `decide(1)=keep` remain reachable to different observers reading `Feed.entries()` in different orders. The tape's `sequence` does not close the window; it only records arrival at one `flock`, which FLP shows is not agreement.

- **Non-triviality matters: the plant's "task ledger is not a receipt judge" is the FLP escape the paper respects.** FLP rules out the trivial protocol "always decide 0" by requiring both values be possible decisions. This plant's `docs/wall-coordination.md:96` "walls are not an append-only log" and `wall.py:1` "no task ledger or receipt judge" plus `delivery.py:7` "Author-owned committed candidates; genome performs only ready integration" already separate *transport* (did the wall/DM arrive?) from *judgment* (is the patch good?). That separation is the correct FLP-compatible posture: settlement is transport, not consensus. The misread is to then treat transport liveness (timeout, sequence) as judgment.

- **Escaping FLP requires stating the synchrony assumption, not finer timestamps.** Lamport's `κ, μ, ε` remedy (finer bound, not finer precision) is the same move here: either declare a partially-synchronous model (e.g., "after GST, every `Feed.append` is observed within δ, and `RETRY_HOLD` is chosen > δ") and enforce it via `host_capacity`/`probe_supervisor` bounds already in the recovery path, or accept that `deliver`/`settle` may never decide and must expose bivalence (UNKNOWN) instead of a timeout verdict. Moving `utc_now()` from seconds to microseconds narrows apparent races but widens false confidence per both Lamport and FLP.

## Application

target: src/mishe_tauftauf/wall.py

**Make the wall module state its FLP boundary beside `RETRY_HOLD_SECONDS`/:1129 and `settle`/:904 / `deliver`/:1170 — additive pure helpers and a docstring, no change to `publication_lock`, `WALL_MAX_*`, `HEADER_RE`, or wire format.**

1. **Add the FLP synchrony-boundary docstring on `wall.py` beside `RETRY_HOLD_SECONDS`.** State: "Settlement and delivery are bounded transport retries, not deterministic asynchronous consensus. Per Fischer–Lynch–Paterson (JACM 1985, https://doi.org/10.1145/3149.214121): no deterministic protocol solves consensus in a fully asynchronous system with one crash-stop fault and reliable messages. `RETRY_HOLD_SECONDS` and `utc_now()` timestamps do not implement a failure detector; they are liveness heuristics that are sound only under a stated synchrony bound (e.g., eventually-synchronous with delay ≤ δ after GST). Until such a bound is stated and enforced via host/probe capacity, `deliver` may remain bivalent and timeout divergence is not a verdict."

2. **Add pure helpers `settlement_requires_synchrony` and `is_bivalent_settlement` beside `deliver`/`_pending_body`.** `settlement_requires_synchrony(entries) -> bool` returns True when any settlement receipt's liveness was decided by `RETRY_HOLD` expiry without a stated `δ`/`κ` bound in the host record — the FLP applicability test. `is_bivalent_settlement(entries, wake) -> bool` checks whether both `decide(keep)` and `decide(drop)` remain reachable from the current `Feed.entries()` slice (presence of both a `seed yield --result changed` receipt and a concurrent `pending_body` without an exact-SHA CI observation) — the paper's bivalence predicate operationalized on the tape. Both are pure views over `FeedEntry` lists; they do not rewrite the tape or add a lock.

3. **Name the held-bivalent detector, no new verdict word.** A future `checks/wall-settlement-bivalence.py` (parallel to `checks/feed-lamport-clock.py` proposed by the Lamport review) can enumerate recent wakes and report `is_bivalent_settlement == True` as a distinct signal from `stale-pend` — i.e., "still bivalent (FLP window open)" vs "timed out (heuristic)." The change here only adds the helpers and the boundary comment; the detector is a follow-on owned by the same resolver (genome for settlement, health for liveness).
