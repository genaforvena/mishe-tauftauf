The paper lists three initially plausible "unified objects" principles it rejects (p.3-4): a single natural design regardless of deployment; failure/performance deferred to implementation tuning; interfaces independent of context.
- What it concedes (and where the paper locates the concession): p.4-5 latency/memory could "in principle" be papered over if hardware/tools caught up or if one forbade address-space-relative pointers and used only marshalled object references — logically possible but at the cost of a new language style and lost transparency. ## What this plant already does

The plant already implements the critique's demand that the distributed nature be visible at the interface — not hidden behind a unified local-call abstraction with a "more reliable implementation" (§5 "The Myth of 'Quality of Service'"):

- Local vs remote memory is distinct: `drive_native` copies the caller's `context` and `obligation` at entry via `snapshot` (json round-trip, line 105-106 of inference_loop.py) and the store's `request_digest` canonically serialises content+arguments+authority+call id before any provider call. The durable journals (`intents.jsonl`, `starts.jsonl`, `outcomes.jsonl`) and exclusive lock file are the only shared state; the in-memory `messages` list is never the authority for a resume (`resume_from` + `_reconstruct_native` rebuild from journal rows rather than from live state). Tests: `tests/test_inference_loop.py:196` `before_turn` cannot edit history, `tests/test_inference_effects.py:430` interruption between start and outcome leaves unknown with no rerun.
- Partial failure is an interface property, not a QoS property: p.6 "one component (machine, network link) can fail while the others continue. ... there is no common agent that is able to determine what component has failed ... the failure of a network link is indistinguishable from the failure of a processor on the other side of that link." The plant treats that indeterminacy at the interface: a crash between intent and outcome is read back as `unknown`, `drive_native` calls `stop('unknown')` rather than retrying, `_re_read_evidence` digest-verifies the evidence artifact, `WorkerError` means no authoritative completion (never a synthesised zero: `wire_usage=None` means UNKNOWN, `fetch_ledger` likewise), and `reconcile_caller_journal` never re-dispatches an unknown or partial call (`tests/test_inference_loop.py:362` unresolved stops without retry, `tests/test_inference_loop.py:1049` reconcile never dispatches for unknown, `tests/test_inference_effects.py` ChangedContentReuse/AlreadyExecuted/ConcurrentClaim pin duplicate detection).
- Concurrency/partial-failure framing is explicit: the header says recovery scope is "local filesystem and process crash only" and the store holds the lock "across the whole read/check/start/execute/outcome sequence" — the one place the paper says a central resource allocator could hide partial failure for local objects (p.6) but cannot for distributed ones. The duplicate-enqueue story (§5 p.8-9: "there is no way to do duplicate elimination. The only way to fix this is to change the protocol to add request IDs") has a plant analogue already: provider-level idempotency or transport retry is rejected as a replacement for `operation_id`+`request_digest`; the protocol carries the ID.

## What is new here

Waldo's critique says the failure we would reproduce if we adopted the "objects all the way down" vision blindly is not that latency would be slow, but that we would hide indeterminacy and then call its consequences a quality-of-service problem. Two concrete reproducers map onto the inference boundary:

1. Treating `dispatch(call)` / `run_worker` / `session.turn` as a unified local call where "if the interface is correct and the implementation is reliable, location doesn't matter" (p.2-3 unified-objects vision). If the loop, the worker or the provider were retuned for "more reliability" — a transport retry inside `inference_worker`, a flush-only journal because the disk is durable, a provider idempotency key replacing the store's `request_digest` — §5 argues no such QoS upgrade can repair a mis-designed interface. The reproducers are the paper's §5 story (p.8-9 duplicate work enqueued multiple times because partial failure was handled as total failure; "robustness is not simply a function of the implementations ... Many aspects of robustness can be reflected only at the protocol/interface level" p.8) and the p.6-7 distinction that local failure is total/detectable by a central allocator whereas distributed partial failure leaves "no global state that can be examined that allows determination of exactly what error has occurred." For this plant the equivalent is synthesising `completed` from a transport success, or synthesising zero wire_usage/fetch_ledger where the worker emitted none — precisely what the current `None means UNKNOWN` rule forbids.

2. Treating tool schemas as location-independent interfaces ("the interface of an object is independent of the context in which that object is used" — one of the three rejected principles, p.3). The paper argues that robustness then requires either making every local call carry distributed indeterminacy (p.7 "all objects must bear the weight of concurrency semantics") or making every remote call ignore it ("fragile and non-robust") — neither is acceptable. The plant's gap is only documentary: the behaviour already chooses the correct distinction (local `snapshot`+lock vs distributed `unknown`+reconciliation), but a future reader who removes that distinction in the name of unifying `dispatch` with a local function, or who adds a "quality of service: retry unknown" flag to the worker, would be reproducing Waldo's failure mode, not optimising it.

The critique also names its own limits, which bound the proposal: latency/memory unification is "logically possible" if one controls all memory access (p.5) — we do not claim the plant proves otherwise. The paper does not discuss exactly-once; neither does the plant (at-most-once dispatch plus durable unknown, bounded by the local-filesystem scope). The paper's NFS example (p.8-9, stateless server with centralized-manager fallback "generally prevents a client program from seeing partial failure, but ... leads to a malady") is bounded as an analogy: it illustrates that hiding partial failure behind statelessness does not remove the interface's need to handle indeterminacy; it does not imply this plant should adopt statelessness.

None of this contradicts the recent revisit for this field (2026-11-02 misread via Saltzer et al. 1984 end-to-end argument, applied to `inference_effects.py` as docs-only placement of `request_digest`/`fsync`/`unknown` at the ends). Saltzer explains *where* reliability must live (ends, not middle, with low-level retry only as performance enhancement); Waldo explains *why* a unified local/remote abstraction cannot make that placement optional, and why interface-level indeterminacy handling (unknown + request IDs + reconciliation) is not replaceable by implementation QoS. One names the placement, the other names the critique of erasing the placement.
