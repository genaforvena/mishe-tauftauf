## What we read

**Crash-Only Software** — George Candea and Armando Fox (Stanford). *Proceedings of HotOS IX: The 9th Workshop on Hot Topics in Operating Systems*, Lihue, Hawaii, May 18–21, 2003, pp. 67–72 — read full text at:

- <https://www.usenix.org/legacy/event/hotos03/tech/full_papers/candea/candea.pdf> (PDF, 6 pages + refs, USENIX Association)

Four passages carry the misread this plant makes.

1. **The definition — one way to stop, one way to start (Abstract, p. 67; §2, p. 68):** "Crash-only programs crash safely and recover quickly. There is only one way to stop such software—by crashing it—and only one way to bring it up—by initiating recovery." And sharpened: "In high level terms, a crash-only system is defined by the equations **stop=crash and start=recover**." The paper's Occam's Razor argument (§1, p. 67): since any system must be prepared for a crash, a system that is crash-safe has no reason to retain additional non-crash shutdown mechanisms — they add states, code, APIs and bugs while optimising a path the system must already survive without.

2. **The external, idempotent power switch (§2, p. 68):** "Each crash-only component has a single idempotent 'power-off switch' and a single idempotent 'power-on switch'; the switches for larger systems are built by wiring together their subsystems' switches … A component's power-off switch implementation is **entirely external** to the component, thus **not invoking any of the component's code** and not relying on correct internal behavior of the component. Examples … include `kill -9` sent to a UNIX process, or turning off the … machine." Keeping the switch external makes it a high-confidence "component crasher."

3. **Recovery exercised on every start, not on exception (§2, p. 68):** "Recovery code deals with exceptional situations, and must run flawlessly. Unfortunately, exceptional situations are difficult to handle, occur seldom, and are not trivial to simulate … this often leads to unreliable recovery code. In crash-only systems, however, **recovery code is exercised every time the system starts up**, which should ultimately improve its reliability." The failure model follows: when recovery is cheap, "every detected failure" is transformed into a component-level crash, so components need only recover from one failure type.

4. **Leases, timeouts and self-describing requests as the crash-only vocabulary (§3.2, pp. 69–70):** "All resources are **leased**, rather than permanently allocated" — e.g. a 6-month login lease, a CPU execution lease killed by a watchdog — and "All interactions … have a **timeout** … if no response … the caller assumes the callee has failed." "Requests are **entirely self-describing**, by making the state and context needed for their processing explicit … Requests also carry information on whether they are **idempotent**, along with a **time-to-live**; both … can initially be set at the system boundary." Together these let a fresh instance pick up a request without the failed instance's cooperation, and let the system reason about what holds after a lease expires — "Infinite timeouts or leases are not acceptable" (p. 70).

The paper's limits it states: crash-only sacrifices steady-state performance, assumes workloads of "large numbers of relatively short tasks that frame state updates" (§1, p. 67), and "does not handle Byzantine failures" (p. 71). The cost is acknowledged; the claim is that fewer states and exercised recovery outweigh it.

## What this plant already does

*The plant's recovery has many ways to stop and many ways to start — the opposite of one switch.*

`src/mishe_tauftauf/native_recovery.py` defines four terminal words for a failed attempt — `SETTLED = 'settled'`, `RETRYABLE = 'retryable-no-effect'`, `RECONCILE = 'requires-reconciliation'`, `UNKNOWN = 'unknown'` (:92–95) — plus a transient predicate `TRANSIENT_STATUS = frozenset({408, 429})` extended to `500 <= status <= 599` (:99) and a count limit `DEFAULT_RETRY_LIMIT = 3` (:100). `classify_attempt()` (:374–448) walks a decision tree that turns failure into different kinds of stop:

- `if settled: return Attempt(SETTLED, ...)` (:422–425) — a clean stop that needs no recovery at all;
- `if dispatched or proposed: return Attempt(RECONCILE, ...)` (:426–430) — a stop that dispatched an effect (`starts.jsonl` + `outcomes.jsonl`) or proposed one (`_journal_effect_rows` counting `proposal`/`tool_result` :354–358) and must be reconciled, never retried;
- `if not transient: return Attempt(UNKNOWN, ...)` (:435–440) — a stop whose terminal failure is not transient and whose `failure.txt` completeness decides `UNKNOWN`;
- otherwise `return Attempt(RETRYABLE, ...)` (:446–448) — only when nothing was dispatched, the failure was transient, and `failure.txt` is a complete traceback.

`attempt_disposition()` (:568–622) then turns those classifications into a second branching of starts: `live` (an attempt still being written :588), `settled` (:595), `reconcile` when any `blocking` report is not `recoverable` (:599–604), `reconcile` again when `fresh_attempt() is None` — the budget exhausted (:605–617) — and only then `fresh-attempt` (:618–621). `fresh_attempt()` itself (:489–502) returns `Path(directory) / f'{wake}-retry-{number}'` for `number in 1..limit` or `None`. The effect is five distinct start behaviours for one wake, distinguished by counts and status codes, and a permanent clean-shutdown path (`settled`) that never exercises the recovery code.

*The plant's "off switch" lives inside the component it is judging.*

`_store_guard()` (:303–332) holds `STORE_LOCK = '.ledger.lock'` (:109) while reading `result.json`, `journal.jsonl`, three ledger journals and `failure.txt` (:280–302), and `LiveWriter` (:115) plus `_writer_active()` (:335–352) test whether "a writer holds the store lock right now." The completeness of `failure.txt` ("Traceback (most recent call last):" :112) is written by the dying writer itself (:200–220 ` _failure_record`) and then used to distinguish `RETRYABLE` from `UNKNOWN` (:441–445). In Candea's terms the power-off switch invokes the component's code — its own lock, its own traceback — rather than being external to it. The readable counterpart `BLOCKED_STATE = '{role}-native.blocked.json'` (:641) with `write_blocked_state()` (:659) and `clear_blocked_state()` (:727) is the plant's wedge signal, but its `verdict`/`reason`/`evidence` strings (:659–661) reproduce the same four-way vocabulary rather than collapsing to "crashed."

*Resources are counted, not leased, and requests carry no TTL/idempotency.*

`docs/recovery.md:18–29` describes kernel cgroup limits (MemoryHigh/Max, CPU, tasks) and `host_capacity` probes, but the wake-level budget is a count — `DEFAULT_RETRY_LIMIT=3` attempts — not a lease with an expiry after which reasoning is permitted. The outbox is durable (`SITE_HOME/recovery/`, 45 s command / 60 s service deadlines, :125–129) but a wake retry carries no `TTL` or explicit `idempotent` flag; `attempt_summary()` (:451–486) reports `capabilities` from `intents.jsonl` so a later attempt can reconcile, but it does not label the request as safely replayable. `recovery_io.py:196`'s `controller_lock` and `site_sync._leases` exist, but they guard the observer, not the attempt's resources. `checks/native-recovery-optin.py` verifies only that an opt-in names the exact pending wake — the right wake, not the right switch.

## What is new here

**This plant keeps the non-crash shutdown path that Crash-Only says to delete, and pays the price Candea names: recovery code that is not exercised, many states that must each be correct, and a failure taxonomy the plant must itself keep correct.**

1. **The clean-shutdown path is the misread.** Candea's Razor: if the system must survive a crash, the clean shutdown that avoids the crash is extra mechanism. This plant retains exactly that: `SETTLED` is a clean stop reachable without crash-recovery, `RETRYABLE` vs `RECONCILE` vs `UNKNOWN` are distinguished stops produced by inspecting the component's own bytes after the fact, and `DISPATCHED` vs `proposed` vs `transient` are the plant's own taxonomy of why this stop is different. The study underlying the paper's motivation — that recovery code "must run flawlessly" yet "occurs seldom" (p. 68) — maps directly: `fresh_attempt` runs only on `RETRYABLE`, so the recovery path for `RECONCILE` and `UNKNOWN` wakes is exercised only when that wake happens to fail that way. A wake that settles cleanly never exercises recovery at all. The consequence is more states, and each state's predicate (`transient_status`, `_journal_effect_rows`, `_failure_record`, `dispatched+reserved` counts, `limit`) is code that must be correct about an exceptional path that is rarely taken — the unreliability mechanism the paper predicts.

2. **The switch is internal, so a failed component can make itself look retryable (or not).** Because `RETRYABLE` requires "no effect admitted" plus "terminal upstream failure {reason}" transient plus "complete traceback," a writer that crashes without flushing `starts.jsonl` but with a transient status, or that truncates `failure.txt`, determines its own classification. An external switch — `kill -9`, power-off, cgroup freeze — cannot be vetoed by the component's internal corruption; an internal lock/ledger read can. Candea's "not invoking any of the component's code" is precisely the property `_store_guard` does not have: it reads the component's store through the component's lock. The plant's other guard, `mishe-containment.service` sampling cgroup pressure every two seconds without reading the conversation (`docs/recovery.md:31–38`), is the plant's one truly external crasher, but it guards the host, not the wake.

3. **Counting attempts is not leasing resources, and carrying no TTL is not self-description.** Candea's leases let the system say after expiry "this resource is reclaimable regardless of what the holder thinks" and timeouts let it say "no response in time means failed." This plant's `DEFAULT_RETRY_LIMIT=3` says "after three failures, reconcile" — a count that preserves exactly the coupling leases are meant to break: the wake's next action depends on how many times the same component has failed before, not on whether a lease the component held has expired. Likewise a request with `idemp=TRUE, TTL=2000` (Fig. 1, p. 70) can be transparently resubmitted; a wake retry with an implicit `proposal` row in `journal.jsonl` and no declared idempotency cannot — the plant must inspect the ledger after the fact to decide. The paper's `RetryAfter(n)` + resubmit discipline (§4, p. 70) is the shape `attempt_disposition` would have if every wake were a crash with a TTL.

**Limits of this reading.** Candea's workload assumption — short requests framing state updates, single data-center, no Byzantine faults — fits the plant's wake/attempt/journal shape but not its long-tail stalls (the `wall.tick` 30 s gate, `site_sync` 20 s remote lease) or its cross-site `docs/` publication; crash-only there would mean different costs. The paper's J2EE/EJB/RMI prototype (pp. 70–71) and Berkeley DB/Postgres state-store taxonomy do not map mechanically to Python journals. And "exercising recovery on every start" is a property of the wake start, not of the host container — the host's `kill -9` is not the wake's `kill -9`. This review keeps those boundaries and proposes only the wake-level change that is a strict instance of the paper's definition, not a migration to J2EE.

## Application

target: src/mishe_tauftauf/native_recovery.py

**Make the wake crash-only: one way to stop (crash), one way to start (recover), an external switch, and requests that say whether they are retryable — all behind the existing flag, additive to the current API.**

1. **Collapse the stop to "crashed" and exercise recovery on every start.** Add `crash_attempt()` / `recover_attempt()` beside `classify_attempt()` / `attempt_disposition()` — the existing functions keep their signatures so `health`/`genome` call sites and `checks/native-recovery-optin.py` do not change. `recover_attempt(directory, wake)` is the only start path: it runs the same `_read_evidence` + `classify_attempt` + ledger-reconciliation prelude for *every* wake, including one whose last summary says `settled is True`. When that prelude finds `settled`, it still exercises the recovery code but takes the fast path — the uncommitted-transaction analogue Postgres uses (p. 69: "it only needs to mark the uncommitted transactions as aborted"). The observable effect is Candea's p. 68 sentence made literal: recovery that is exercised on every start, where the rare-path bugs surface on the common path. A `MISHE_NATIVE_CRASH_ONLY=1` flag beside `MISHE_NATIVE_RECOVERY_WAKE` enables the collapsed stop; default `0` preserves the four-way `classify_attempt` exactly.

2. **Externalize the power-off switch.** The wake's off-switch must not read the wake's own store to decide whether the wake stopped. Introduce `_external_crash_marker()` that is written by the supervisor *outside* the attempt's `effects/` directory (alongside `BLOCKED_STATE`/`busy` in `journals/`, or a cgroup-freeze marker where available) via an operation that does not acquire `STORE_LOCK`. `classify_attempt` keeps its internal `LiveWriter` check for diagnosis, but the disposition's `live` vs ` crashed` decision consults the external marker first — a failed holder cannot veto its own crash by holding the lock or truncating `failure.txt`. This mirrors `mishe-containment.service`'s host-level external kill (docs/recovery.md:31) at wake granularity.

3. **Give each attempt a lease and each request a TTL/idempotency label.** Extend the attempt directory's metadata (the `result.json` / `summary` the wake already writes) with `lease_ms` (default derived from `observations._RENDERER_TIMEOUTS`/`RETRY_BACKOFF`/`RENDERER_FRAME` so the lease is the holder's budget, not the reader's threshold) and `ttl_ms` + `idempotent: bool` per `EffectIntent`/`DispatchClaim` (`inference_effects.py:90`). After `lease_ms` without a fresh `result.json`, any observer may declare the attempt expired without reading its ledger — the "ability to draw conclusions after a passage of time, possibly in the absence of communication" (p. 68, Gray & Cheriton lease property Candea reuses). Requests marked non-idempotent are never transparently resubmitted; idempotent ones are, with `RetryAfter`-style backoff rather than `DEFAULT_RETRY_LIMIT` counting. The count limit remains as a safety cap but is no longer the primary "when to stop retrying" signal.

**Acceptance (deterministic, runnable from this repository).**

- With `MISHE_NATIVE_CRASH_ONLY=0` the existing `classify_attempt`/`attempt_disposition`/`fresh_attempt` sequence for a fixture wake produces the same `Attempt`/`Disposition` bytes as before (replay the last 3 `failure.txt` + journal fixtures through `classify_attempt`; `python tools/check_parsing.py` stays green — `native_recovery.py` is not a `parsing-policy.json` boundary file, and the new symbols are additive).
- With `MISHE_NATIVE_CRASH_ONLY=1` and a synthetic settled wake (`summary.json: {settled:true}`), `recover_attempt` exercises the recovery prelude (it reads and reconciles the ledger) and returns a `Disposition` whose `verdict` is `SETTLED` but whose `evidence` includes the exercised read — the recovery path is covered on the clean path. Today no recovery code runs on a settled wake.
- With `MISHE_NATIVE_CRASH_ONLY=1` and a synthetic attempt whose `failure.txt` is truncated and whose `starts.jsonl` was not flushed, truncating `failure.txt` does not change `recover_attempt`'s liveness decision — the external crash marker determines `live` vs `crashed` without acquiring `STORE_LOCK` or parsing `failure.txt`. Holding `STORE_LOCK` in the main thread while `recover_attempt` probes does not block the liveness check.
- An `EffectIntent` with `idempotent=false, ttl_ms=2000` attempted after its TTL is not resubmitted by `recover_attempt`; the same intent with `idempotent=true` is resubmitted once with backoff. Three successive idempotent failures still hit the `DEFAULT_RETRY_LIMIT` cap and reconcile.

**Ownership.** `src/mishe_tauftauf/native_recovery.py` is the bounded fresh-wake recovery discipline and is consumed by the `health`/`genome` life-support slice; `health` is resolver for `native recovery, health, supervisors, watchdogs` (field `failure-and-recovery`'s `plant_part`) and owns `recovery_io`'s probe sampling. The `MISHE_NATIVE_RECOVERY_WAKE` opt-in is checked in `checks/native-recovery-optin.py`; the `MISHE_NATIVE_CRASH_ONLY` flag lives beside it.

**One thing this review does not ask for.** It does not propose rewriting the host containment controller, migrating journals to Postgres/Berkeley DB state stores, or making every HTTP/docs publication idempotent — those are the paper's §3.1 state-store and §5 prototype concerns, and they are genome-wide changes. This review only collapses the wake's stop to a crash and its start to recovery, externalizes the one switch that decides liveness, and labels the requests the switch retries — the part of crash-only that is a local misread of the paper's own definition.
