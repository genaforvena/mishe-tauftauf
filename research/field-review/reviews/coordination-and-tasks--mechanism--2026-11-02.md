## What we read

Mike Burrows, **"The Chubby lock service for loosely-coupled distributed systems"**, Google Inc., *Proc. 7th USENIX OSDI*, November 2006 — read full text at:

- <https://static.googleusercontent.com/media/research.google.com/en//archive/chubby-osdi06.pdf> (PDF, 6 pages, version 1.3, 115 KB, fetched 200 2026-11-02, pdftotext 1546 lines extracted)
- <https://doi.org/10.1145/324133.324234> via ACM DL (same paper; Chubby builds on Paxos [Lamport 12,13] / Oki & Liskov viewstamped replication [19] — paper claims "no new algorithms", §1)

Four passages carry the operational mechanism this plant re-implements as a single-host `flock`:

1. **Lock service vs. Paxos library (§2.1).** Chubby chose a lock service over a client Paxos library: prototypes gain replication/election without restructuring as state machines; elected primaries need a well-known place to advertise themselves (small file); locks are familiar to programmers even though distributed locks are routinely misused ("few consider the effects of independent machine failures ... with asynchronous communications"). GFS uses one lock to appoint its master, Bigtable uses Chubby to elect, discover, and expose the master (§1). The consensus core (typically 5 replicas, 3 required) is Paxos for safety; liveness needs clocks (§1: "Paxos maintains safety without timing assumptions, but clocks must be introduced to ensure liveness; this overcomes ... Fischer et al. [5, §1]").

2. **Coarse-grained design decision (§2.1, ¶ "A choice that may surprise").** Chubby is *intentionally coarse-grained* (locks held hours/days, e.g. master election) — not fine-grained seconds. Coarse-grained: acquisition rate weakly related to transaction rate, surviving server failure is wanted, modest servers suffice, and transfer requires costly recovery so failover must not drop locks. Fine-grained: brief unavailability stalls many clients, throughput matters, dropping locks on failover is acceptable. Chubby leaves fine-grained locking to application-specific servers provisioned by clients, each keeping a non-volatile monotonic acquisition counter (§2.1 end) and cache of lost locks reported at unlock or via short lease.

3. **Sequencers as fencing tokens (§2.4 "Locks and sequencers").** Each node is an advisory reader/writer lock (one exclusive or N shared, §2.4). Because a holder may issue request R, fail, another acquires the same lock, and R arrives late unprotected, Chubby provides *sequencers*: at any time the holder may request an opaque byte-string describing the lock state *immediately after acquisition* — it contains **lock name, mode (exclusive/shared), and lock generation number** (one of four per-node monotonic 64-bit numbers at §2.3: instance, content generation, lock generation, ACL generation, plus file checksum). The client passes the sequencer to downstream servers with operations; the recipient tests validity (against its Chubby cache or the last sequencer observed) and rejects if stale or wrong mode. Cost is one string per message vs. adding sequence numbers to every interaction (virtual time [11], virtual synchrony [1]). A cheaper imperfect fallback is *lock-delay*: a lock freed by failure is withheld up to 60 s before re-grant to protect servers that do not check sequencers.

4. **Sessions, leases, KeepAlives and the grace period (§2.8) + events/caching (§2.5, §2.7).** A session is maintained by periodic KeepAlive RPCs. Each session has a lease interval into the future that only the master advances (creation, failover, KeepAlive reply — default extension 12 s, larger under load). The KeepAlive is blocked at the master until the previous lease nears expiry, then returned with new timeout + piggybacked events/invalidations (so clients must acknowledge invalidations to keep the session and RPCs need one firewall direction only). The client keeps a conservative approximation (accounts for flight time and bounded clock drift "server clock advance no faster than a known constant factor faster than the client's"). If the local lease expires, the session is in *jeopardy*: cache is flushed/disabled and a 45 s grace period begins, with jeopardy/safe/expired up-calls to quiesce. Master failover (Fig. 2) stops the authoritative lease timer while no master exists; a new master (elected in ~6 s, sometimes 30 s, §2.2) uses a client epoch number to reject stale packets, and reconstructs state conservatively from stable database + clients. Caching (§2.7) is consistent write-through with invalidations (one round, node uncachable while unacknowledged); clients cache file data, metadata, handles and optionally locks (holder notified of conflicting request). Events (§2.5): file contents modified, child added/removed/modified, master failed over, handle invalid, lock acquired, conflicting lock request — the latter two "rarely used ... could have been omitted" with hindsight.

**Limits the source states.** Engineering, not research (§1); replication/election details omitted (covered by Paxos literature); Chubby itself has five replicas per cell and DNS-based replacement (§2.2); access control via ACL files (§2.3).

## What this plant already does

*The plant is a single-host, single-lock analogue of the Chubby cell described in §2.2, but without Chubby's explicit coarse-grained contract, generation numbers, sequencers, or session lease machinery — so every downstream check pays the ambiguity Chubby's sequencer was invented to remove.*

- **One global `flock` is the entire lock service.** `src/mishe_tauftauf/feed.py:46` `publication_lock` (`threading.RLock` + `fcntl.flock` on `.publication.lock`) serializes context capture, admission and `Feed.append` for walls, settlement, addressed DMs, `task_state.claim` and `native_recovery`. `Feed._encode_entry` (`feed.py:106` header `v1 {sequence:020d} {timestamp} {source} ::\n`, `feed.py:19` `HEADER_RE`, `feed.py:102` `utc_now`) assigns a single global monotonic `sequence` (arrival order) and a microsecond UTC wall-clock time. `feed.py:400` `_role_view` / `wall.py:464` `write` / `wall.py:642` `message` (`[dm] to=ROLE`) / `wall.py:904` `settle` all funnel through this one lock, sustaining the same total-order serialization that Chubby's consensus log sustains for a cell.

- **Coarse vs. fine is not declared.** `wall.py:19` `WALL_MAX_BYTES=16384` / `:21` `WALL_MAX_LINES=200`, `RETRY_HOLD_SECONDS=1800` (`wall.py:1129`), `task_state.py` advisory `candidates`/`select_task`/`claim`, and `AGENTS.md` "Genome pushes `main`..." together define a de-facto coarse-grained regime (wall edits and settlements span minutes/hours, publication is rare) — but the per-role wall, the tape DM, and `task_state` present a single uniform path. Chubby's explicit coarse/fine partition (application-provisioned fine-grained servers with their own acquisition counters behind a coarse allocation lock, §2.1 end) has no reification: every claim contends on the same `flock`, and the plant cannot state that a lock is expected to survive a server failover vs. be dropped.

- **No per-resource generation, no sequencer, no fencing token.** The tape has one global `sequence` (arrival tie-break); Chubby has *four* per-node generations (§2.3) and the lock generation inside the sequencer (§2.4). This plant's downstream consumers (the file server in Chubby's example, here `wall.py:500` `_reject_peer_wall_copy`, `wall.py:559` `_reject_peer_history_copy`, `wall.py:837` `reject_stale_staging_anchor`, `coord_tape.py` fog filter) are left to infer staleness from global arrival order or wall digest equality, not from a per-resource fencer they can compare at the operation site. The Chubby pattern `Acquire → GetSequencer → pass sequencer with RPC → CheckSequencer/reject if stale` has no typed analogue on the tape; a late-arriving write that lost its wall-lock race can still be acted on, exactly the anomaly sequencers prevent. The `lock-delay` fallback (withhold contended lock up to 60 s, §2.4) is analogous to `RETRY_HOLD_SECONDS=1800` but is applied uniformly as a settlement hold, not as a per-lock grace for sequencer-ignorant servers.

- **Session/lease/grace is timeout-only.** `wall.py:1170` `deliver` / `wall.py:1129` `RETRY_HOLD_SECONDS` + `wall.py:1153` `_native_gate_verdict` decide liveness by wall-clock timeout (held wake beyond 1800 s → stale-pend), not by a session lease with periodic KeepAlive renewal and conservative client approximation (§2.8). There is no epoch number to reject very old packets after failover (Chubby's new master epoch, Fig. 2, step 1), no `KeepAlive`-piggybacked invalidation acknowledgement, and no explicit jeopardy/safe/expired up-call for quiescing — the dashboard's "age" comment (`wall.py:378` `observation_text` stripping ages for semantics) hides the same timing signal Chubby's client library exposes to applications.

- **Events and caching are implicit.** Chubby's cache keeps file data/metadata/handles/locks consistent via invalidations driven by the master (§2.7); this plant's `feed.py:32` `_ENTRIES_CACHE` / `feed.py:42` `_ROLE_ENTRIES_CACHE` and `Feed.entries()` give whole-tape caching per feed path keyed by file metadata, but there is no per-node lease-driven invalidation, no master failure event, and addressed messages (`wall.py:642`) are visible-but-ephemeral DMs rather than typed delivery of Chubby's §2.5 events (file modified / child added / handle invalid / conflicting lock).

- **Best nearby precedent for this transfer.** `coordination-and-tasks--mechanism--2026-10-29.md` (this cell, Malone & Crowston) already added the Smith & Davis announcement/bid/award market as market-side mechanism for task assignment. That market sits *above* the lock service; Chubby sits *below* it — it names what the lock actually guarantees (coarse-grained advisory lock + sequencer fencer + session lease) so the market's `award` can be checked for staleness without adding a central scheduler. `coordination-and-tasks--misread--2026-10-29.md` (Lamport) and `...--misread--2026-11-02.md` (FLP) both note the missing `κ, μ, ε` and synchrony bounds for settlement; Chubby supplies the concrete engineering that escapes FLP while keeping safety: Paxos safety without timing, liveness via the lease timers described in §2.8.

## What is new here

**Name the lock service boundary explicitly — coarse-grained advisory locks with per-resource generation, a sequencer fencer string, and a session lease with grace — beside the existing global `flock`+`sequence`, so downstream consumers can reject stale operations locally, exactly as Chubby §2.4 does without putting sequence numbers on every interaction.**

1. **Per-resource generation vs. global sequence (§2.3–§2.4).** Chubby's instance/content/lock/ACL generations are per-node monotonic counts; the plant's `sequence` is per-tape. A per-wall (and per-task) monotonic generation gives a local notion of "later acquisition of *this* lock" that global arrival order alone cannot — two concurrent wall writes to different roles both advance `sequence`, but only one advances that wall's lock generation. Carrying that count in the sequencer makes staleness testable at the downstream site (file server / `wall.py` copy guard) without reading the whole tape history.

2. **Sequencer as a single-string fencer (§2.4) — not vector time, not full synchrony.** The sequencer is `(lock_name, mode, lock_generation)` rendered opaque; passing it alongside an operation and rejecting if `generation < current` or `mode` mismatches overcomes Fischer et al. impossibility the same way Chubby does: safety stays asynchronous (Paxos / `flock` + total order), liveness uses the lease clock. This is cheaper than Chubby's alternatives (virtual time/synchrony putting sequence numbers on every message) and directly fixes the stale-write anomaly the copy guards (`_reject_peer_wall_copy` / `_reject_peer_history_copy`) today detect only after publication.

3. **Session lease with conservative client approximation and grace (§2.8, Fig. 2).** A lease interval advanced only by the master (here: the publication site's wall/tape), renewed via periodic KeepAlive-like observation, with a client-side conservative lease (flight time + bounded drift), a *jeopardy* state when local lease expires, and a bounded grace period (Chubby: 12 s lease, 45 s grace) before expiry. Master failover stops the authoritative timer (equivalent to extending the lease) and a new master picks an epoch to reject old packets. Today's `RETRY_HOLD_SECONDS=1800` is a fixed hold, not a lease — it cannot distinguish "still leased, do not re-award" from "lease expired, safe to re-award" at the client that implements quiesce.

4. **Typed events over the lease channel (§2.5).** Carrying `file modified / child added / master failed over / handle invalid / conflicting lock` as typed wake events piggybacked on the lease renewal (rather than generic `[dm]` DMs) makes recovery observable: a client learns its cache/lease state in one round, exactly as Chubby's `KeepAlive` return delivers invalidations + events.

Limits kept: as §1 says Chubby is engineering, this transfer does not claim a new consensus algorithm, does not replace `publication_lock`/`flock` with a 5-replica Paxos cell, and does not change queueing/probability production/coordination/vulnerability numbers — only the fencing vocabulary that makes the existing arrival order checkable.

   - `wall_sequencer(home, role, mode="exclusive") -> str` — opaque fencer string encoding `f"{role}:{mode}:{generation}"` (with `generation = wall_lock_generation(home, role)`), the sequencer §2.4 that a holder requests immediately after acquisition.    - `is_sequencer_valid(home, sequencer, *, expected_mode="exclusive") -> bool` — recipient-side check §2.4: parses the sequencer, extracts `(role, mode, gen)`, and returns `gen == wall_lock_generation(home, role) and mode == expected_mode`. A late-arriving operation carrying an older `gen` is rejected; a mode mismatch (shared vs. exclusive) is rejected. Pure and advisory — callers decide whether to reject.
   - `session_lease_state(home, role, now=None) -> dict` — lease view §2.8 over bounded evidence (`Feed` timestamps via `feed.entry_timestamp` and audit tail): returns `{"lease_timeout": datetime|None, "in_jeopardy": bool, "grace_remaining_s": int|None, "epoch": int}` where `lease_timeout` is the last publication/KeepAlive-equivalent plus the coarse lease extension (analogous to Chubby's 12 s, scaled to wall's coarser cadence without changing `RETRY_HOLD_SECONDS` semantics), `in_jeopardy` is `now > local_conservative_lease`, and `epoch` is a per-wall monotonic instance number (§2.3) suitable for rejecting very old packets after a master/site failover (Fig. 2, step 1).
