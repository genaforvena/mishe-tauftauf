Canonical source repo: <https://github.com/slsa-framework/slsa> (spec source). v1.0's informative note states "For version 1.0 the Source aspects were removed to focus on the Build track. A Source track may be added in future versions" — the spec is Build-track only in 1.0 (levels p.1).

Six passages carry the operational mechanism this plant would need to claim "this commit was honestly built" — each with its stated limits kept.

1. **Levels as tracks with intent (levels p.1–2).** "SLSA is organized into a series of levels that provide increasing supply chain security guarantees. This gives you confidence that software hasn't been tampered with and can be securely traced back to its source." The descriptive ladder: L0 No guarantees (no requirements); L1 Provenance exists — "Package has provenance showing how it was built. Can be used to prevent mistakes but is trivial to bypass or forge"; L2 Hosted build platform — "Forging the provenance or evading verification requires an explicit 'attack' ... builds run on a hosted platform that generates and signs the provenance"; L3 Hardened builds — "Forging ... requires exploiting a vulnerability beyond the capabilities of most adversaries ... builds run on a hardened build platform." Tracks: Build track describes provenance trustworthiness; Source track removed in v1.0. Intended audiences differ: L1 for quick mistake prevention, L2 switching to hosted platform, L3 hardened releases. Limit kept: L1 is explicitly "trivial to bypass" — provenance existence alone is not tamper protection (levels p.2).

2. **Producer requirements (requirements: Producer).** Three MUSTs on the artifact producer (who owns the source and publishes the artifact): (a) *Choose an appropriate build platform* — "If a producer wishes to produce a Build Level 3 artifact, they MUST choose a builder capable of producing Build Level 3 provenance"; (b) *Follow a consistent build process* — "The producer MUST build their artifact in a consistent manner such that verifiers can form expectations about the build process"; (c) *Distribute provenance* — "The producer MUST distribute provenance to artifact consumers." Limit kept: spec does not dictate the distribution channel (package ecosystem sidecar vs transparency log) — only that acceptable-format provenance be distributed; L1 completeness is best-effort, resolvedDependencies MAY be missing.

3. **Build Platform: Provenance generation — Exists / Authentic / Unforgeable (requirements: Build Platform > Provenance generation).** The spec factors integrity into three increasing guarantees across the levels table (✓ per level):
   - `Provenance Exists` (L1 ✓): "The build process MUST generate provenance that unambiguously identifies the output package by cryptographic digest and describes how that package was produced. ... It is RECOMMENDED to use the SLSA Provenance format." Completeness at L1 is best-effort.
   - `Provenance is Authentic` (L2 ✓): provenance is tied to the builder through a digital signature authenticatable downstream, completing Authenticity; this also enables `Prevents tampering after the build through digital signatures`.
   - `Provenance is Unforgeable` (L3 ✓): Accuracy — "MUST be strongly resistant to forgery by tenants. Any secret material used for authenticating the provenance, for example the signing key, MUST be stored in a secure management system appropriate for such material and accessible only to the build service account. Such secret material MUST NOT be accessible to the environment running the user-defined build steps." L3 also tightens Completeness: externalParameters MUST be fully enumerated, else L1/L2 are SHOULD. Limit kept: the spec concedes `Completeness of resolved dependencies is best effort` even at L3 — dependency capture is never claimed complete.

4. **Isolation strength — Hosted vs Isolated (requirements: Isolation strength).** The build-platform isolation table:
   - `Hosted` (L2 ✓): "All build steps ran using a hosted build platform on shared or dedicated infrastructure, not on an individual's workstation. Examples: GitHub Actions, Google Cloud Build, Travis CI."
   - `Isolated` (L3 ✓): "The build platform ensured that the build steps ran in an isolated environment, free of unintended external influence. ... This MUST hold true even between builds within the same tenant project. The build platform MUST guarantee: It MUST NOT be possible for a run to influence another." Implementation notes: dedicated infrastructure, isolation between tenants and between runs of same project. Limit kept: spec notes that verifying isolation requires platform assessment (`Verifying build platforms`) and does not itself provide the audit.

5. **Provenance predicate shape — in-toto attestation with BuildDefinition and RunDetails (provenance p.1–4, requirements: Verifying artifacts).** SLSA Provenance v1 is an in-toto Statement predicate:
   `predicateType: "https://slsa.dev/provenance/v1"`, `predicate: { buildDefinition: { buildType, externalParameters, internalParameters, resolvedDependencies[] }, runDetails: { builder: { id, builderDependencies[], version }, metadata: { invocationId, startedOn, finishedOn }, byproducts[] } }`, `subject[]` is the artifact ResourceDescriptor `{ uri, digest { sha256|sha512|gitCommit } }`. Builder identity: "builder.id identifies this platform, representing the transitive closure of all entities that are trusted to faithfully run the build and record the provenance. The implementer SHOULD define a security model ... to clearly identify ... transitive closure." BuildType is the parameterized template (e.g., `https://slsa.dev/buildType/...`). Verifying artifacts requires: verify artifact digest matches provenance subject, verify provenance signature / builder identity against trust anchor, check buildType/externalParameters match expectation (implicit trust-on-first-use or explicit config). Limit kept: spec RECOMMENDS the SLSA Provenance format but permits alternate formats bi-directionally translatable; builder.id is trusted closure, not a DNS proof — the security model is out-of-band.

6. **Distributing and Verifying as consumer-visible mechanisms, not just producer claims (requirements: Distributing provenance, Verifying artifacts).** "The build platform is responsible for generating provenance" while the producer is responsible for distributing it; the verifier's job is separate: check `subject` digest equality, check provenance authenticity (signature), check builder and externalParameters against expected source/buildType. Threats & mitigations (spec) states the mechanism's placement: it mitigates tampering after (L2) and during (L3) the build, not content truth of the artifact's depicted facts. Limit kept: SLSA provenance being `Trusted` means binding held under checked goals and builder trust — not that depicted source code is correct or faithful to intent; source track absence means provenance does not itself prove source integrity.

**Why this literature, for this cell.** Field `publication-and-attribution` is "the reader book, the DEV blog, commits, CI and pushes" and angle is *mechanism* — an operational mechanism this area proposes that is implementable, not just philosophy. SLSA v1.0 is the first widely-adopted cross-ecosystem publication mechanism that makes "published commit X was built by builder Y from digest Z via buildType T" a checkable in-toto attestation rather than a remembered `git push` and a CI badge. This is the publication-level analogue of the C2PA ingredient manifest the plant just typed for DEV articles — but for commits/CI, where the honest-voice claim is "this SHA on main was produced by this hosted platform run, exactly."

## What this plant already does

*The plant publishes commits and CI results to three disconnected surfaces that never meet as one typed Build-level manifest — `git` hashes, a `ci` feed line, and a DEV article quote, with no provenance predicate, no builder identity beyond `gh`, and no isolation word.*

- **CI is a poll-read, not a provenance generation, and the CI line is not a predicate.** `src/mishe_tauftauf/ci_watch.py:41-82` `read()` shells `gh repo view` and `gh run list --commit SHA --json databaseId,headSha,status,conclusion,url,workflowName,event,headBranch` (retries 5× with 2 s backoff), deduplicates by `workflowName` taking max `databaseId`, classifies `state` as `fail` (any failure conclusion), `pending` (any non-completed), else `pass` (all success) or `unknown` (no matching run or missing requiredWorkflows). `tick()` `84-106` writes the result to `SITE/ci/latest.json` and appends one `Feed` entry `"[ci] state=... sha=... run=... url=..."` via `feed.Feed(home).append("ci", ...)`. There is no digest-bound subject (the artifact SHA is carried but not hashed as `subject` with `sha256`), no `buildType`, no `externalParameters` (workflow inputs, runner image, `GITHUB_SHA`), no `resolvedDependencies` (checkout SHAs, action pins), no `runDetails.builder.id` (the runner / hosted platform identity), no `metadata.startedOn/finishedOn/invocationId`, and no signature — the line is a human-readable summary of badge state, not the SLSA "unambiguously identifies the output package by cryptographic digest and describes how that package was produced."

- **Delivery pushes but does not generate or distribute provenance.** `src/mishe_tauftauf/delivery.py:149` `_push` is `git -C repo push origin head:refs/heads/main --force-with-lease=refs/heads/main:base`; `submit`/`check`/`integrate` orchestrate readiness from facts and feed projection but create no `provenance.json` sidecar, no in-toto `Statement`, no DSSE envelope, and no distribution step ("producer MUST distribute provenance" has no reification). The only integrity word is `ci.state == "pass"` gating readiness, which at SLSA descriptive level is L0/L1 — it catches mistakes (no run, missing workflow, failed conclusion) but per levels p.2 is "trivial to bypass or forge" because the platform is not required to be hosted nor provenance signed.

- **Isolation strength has no vocabulary, and the existing lock is the opposite.** `src/mishe_tauftauf/feed.py:42` `publication_lock` serializes via `fcntl.flock` on `.publication.lock` plus `threading.RLock`; `ci_watch._command` retries gh calls 5× tolerating `EOF/TLS`. Neither states `Hosted` (dedicated vs workstation) nor `Isolated` (tenant-separated, no cross-run influence, signing material inaccessible to user steps). The spec's L3 rule — "secret material ... MUST NOT be accessible to the environment running the user-defined build steps" — has no analogue; a self-hosted runner with a leaked `GITHUB_TOKEN` would read as `pass` identically to hardened GitHub-hosted `ubuntu-latest`.

- **Verification is badge-equality, not predicate verification.** `ci_watch.line(home)` `116-127` formats `CI: PASS sha=... run=... url=...`, and `delivery.read_ci()` / `ci_watch.read()` is consumed as `state ∈ {pass,fail,pending,unknown}`. There is no step that checks `subject.digest == git rev-parse HEAD`, checks `predicate.buildType` vs expected workflow file, checks `externalParameters` completeness, or validates a signature over the predicate against a builder trust anchor — the `Verifying artifacts` section of SLSA is not embodied. `rg -n "provenance|predicateType|buildDefinition|runDetails|builder\.id|in-toto|DSSE|SLSA" src/mishe_tauftauf/ci_watch.py` is empty until this review. `rg -n "SLSA|slsa" src/` is empty plant-wide before this review (the transfer review typed Merkle/C2PA, not SLSA).

*Consequence the source predicts.* SLSA levels p.2: L1 without hosted + signed provenance "Can be used to prevent mistakes but is trivial to bypass or forge." Applied here: an actor with push lease can push a SHA, forge a `[ci] state=pass` tape line on a compromised host, or bypass the gh poll entirely, and the current reader holding only commit `hex40` and the CI badge line cannot tell `L1` (provenance-exists best-effort) from `L2` (signed, hosted) from `L3` (hardened) — the authentication and isolation guarantees are undistinguished and the `trivial to bypass` caveat the spec requires is invisible. The recent C2PA addition typed `DISCLOSURE_LEVELS/MANIFEST_STATES` for DEV articles but explicitly left commits/CI at "hash is hard binding" with no Build-level ladder, so the plant repeats that gap at the CI boundary.

## What is new here

**SLSA v1.0 reframes the plant's `ci.state/pass` and `git push` from "badge + hash" to a closed Build-level ladder (L0→L3) with provenance-generation requirements and isolation requirements, each with a typed predicate shape that is import-safe to name before any signer exists — so a CI observation without provenance, or provenance without hosted/signed, is visibly below the claimed level rather than a neutral CI word.**

Five ideas transfer directly, each bounded by what SLSA concedes.

1. **Build Levels L0–L3 as the closed publication vocabulary (levels; requirements: Levels).** Today `ci_watch` exposes `state ∈ {pass,fail,pending,unknown}` — a verdict. The transfer makes `SLSA_BUILD_LEVELS = ("L0","L1","L2","L3")` the *mechanism* word: an artifact is at a level only when the corresponding MUSTs hold. `L0` is explicitly "No guarantees"; `L1 = Provenance Exists` alone; `L2 = L1 + Provenance Authentic + Hosted + signed`; `L3 = L2 + Unforgeable + Isolated` (externalParameters fully enumerated). This vocab lets a review state "this commit is at most L1" when only a CI badge exists, rather than implying `pass → trusted build`.

2. **Provenance Exists → Authentic → Unforgeable as the generation ladder, separate from CI verdict (requirements: Provenance generation).** The plant's CI `state` does not distinguish existence vs signature vs tamper-resistance. The transfer exposes `SLSA_PROVENANCE_STATES = ("none","exists","authentic","unforgeable")` with pure predicates: `exists` when a predicate with `subject.digest == sha256(head)` is present; `authentic` when that predicate's signature/builder.id is present and verifiable in principle (no fetch in this commit); `unforgeable` when secret material is documented as build-service-only (the L3 Accuracy requirement). The three Completeness/Authenticity/Accuracy dimensions are kept verbatim.

3. **Provenance predicate shape as typed facts, not prose (provenance spec).** SLSA provenance v1 is `in-toto Statement` with `predicateType = "https://slsa.dev/provenance/v1"` containing `buildDefinition { buildType, externalParameters, internalParameters, resolvedDependencies[] }` and `runDetails { builder { id, version }, metadata { invocationId, startedOn, finishedOn }, byproducts[] }`, plus `subject[]` digests. The transfer makes this shape a pure helper vocabulary (e.g., `slsa Provenance` dict construction and `is_valid` predicate) so quoting `sha=abc... run=123 url=...` without a typed `subject.digest` + `buildDefinition.buildType` + `runDetails.builder.id` is visibly a provenance omission, not a neutral CI summary. The `buildType` mirrors the workflow's parameterized template (the producer's "consistent build process" commitment).

4. **Isolation strength Hosted vs Isolated, and what it guarantees (requirements: Isolation strength).** `Hosted` — all steps ran on hosted shared/dedicated infra, not a workstation; `Isolated` — platform guaranteed no cross-run influence, even within same project, and signing secrets inaccessible to user steps. These become boolean predicates on a CI observation (`builder_is_hosted`, `isolation_is_isolated`) plus the documented runner examples (GitHub Actions qualifies as Hosted). A `pass` from a self-hosted runner without isolation documentation is correctly typed as `hosted=False → at most L1` regardless of its badge — the L2 barrier is visible.

5. **Producer vs Build Platform separation and the "MUST distribute" / "MUST verify" mechanism (requirements: Producer + Build Platform, Verifying artifacts).** The spec assigns: Producer MUST choose capable builder, MUST keep build consistent, MUST distribute provenance; Build Platform MUST generate provenance meeting the level's MUSTs; Verifier MUST check subject digest, check builder predicate vs expected trace, check authenticity when required. The transfer documents this routing: the *platform* generates (ci_watch reads), the *producer* (delivery/genome) distributes (currently missing), the *consumer* verifies (currently only checks `state`). Keeping "Distribution missing → at most L0" honest is the detector the spec demands.

**Limits the proposal keeps from the source.** No X.509 signer, no Sigstore/Cosign/DSSE envelope, no Fulcio/Rekor, no GH_OIDC token fetch, no JUMBF or watermark, no trust-anchor list, no GH API signature validation is implemented — exactly the spec's own limit that `L1 is trivial to bypass` and `L3 usually requires significant changes to existing build platforms`. No `Feed.append`/`seed yield`/wall mutation, no new `SENSE_ID`, no `WALL_MAX_*` change, no chat-protocol wire change. Source track remains absent (SLSA v1.0 removed it) so source integrity is not claimed by this vocab. Completeness of `resolvedDependencies` stays best-effort at L1/L2 and is only MUST at L3 with explicit note that non-falsifiable capture is still ongoing. `Trusted` still means "binding held under checked goals and builder trust," not "depicted facts are true," matching SLSA's threat model (mitigates tampering after/during build, not content truth).
