Four passages carry the change this plant has not made.

1. **From provably beneficial to empirically validated — relaxing the Gödel Machine (Schmidhuber 2007, §3, p. 3–4).** The Gödel Machine requires a formal proof that a self-rewrite is net beneficial before it is kept; the paper states this is "impossible in practice" without restrictive assumptions about the system (p. 3: the benefit of "more tools" depends on model training and task context, so a tool that helps in one setup confuses the next). DGM replaces proof with empirical trial: the agent edits its own Python codebase (Turing-complete medium) and the edit is kept only if it compiles, retains codebase-editing ability, and improves a held benchmark score (SWE-bench / Polyglot). The analogy to biology is explicit: mutations are not verified in advance but produced, trialed, and selected via observed result (Fig. 1, §3).

2. **The archive as the mechanism — open-ended exploration via stepping stones (§3, §4.3–4.4, Figs. 1–3, Appendix C.2–C.4).** Starting from one agent, DGM maintains an archive of *all* generated variants that still compile and can edit code; parent selection each iteration is roughly proportional to performance score and number of children with codebase-editing functionality (Appendix C.2). Each parent analyses its own benchmark logs, proposes the next feature to implement, and self-modifies to produce one child (Appendix C.3). The archive grows as a tree (Fig. 3 Left: 80 nodes, node 0 base; colour = success rate, border = evaluation depth). Critically, the lineage of the final best agent includes two performance dips (iterations 4 and 56, Fig. 3 Right) that an archive-free hill climber would have discarded — but from those dips the later explosion of improvements branched (node 24's children). The design intent is from Hughes et al. 2024 / Stanley-Leman "interesting yet suboptimal stepping stones" (cited p. 2, p. 8): keep diverse, even lower-performing variants because they may enable future breakthroughs.

3. **Self-improvement as benchmarked coding (SWE-bench 20.0%→50.0%, Polyglot 14.2%→30.7%, full benchmark; §4.4, Fig. 2, Fig. 4).** The key assumption (§3, p. 4): increase on coding benchmarks indicates better coding capability and hence better ability to self-modify — so downstream task performance *is* the self-improvement metric, closing the self-referential loop without a fixed meta-agent. DGM automatically discovered granular file viewing by lines, string-replacement editing, multiple patch generations with FM-based ranking, non-empty patch validation, and history-aware generation (Fig. 3, Appendix F). Baselines isolate the two ingredients: DGM without self-improvement (ADAS-style fixed meta-agent, Algorithm 2) improves early then tapers sharply; DGM without open-ended exploration (always branch from latest, Algorithm 3) stagnates after a poor modification removes editing ability (Fig. 2, Appendix A.1). Transfer (§4.4, Fig. 4): SWE-bench's best agent scores 28.9% on Polyglot (vs 14.2% base) and 59.5% on Claude 3.7 Sonnet (vs 19.0% base) — improvements are general skill, not benchmark overfitting.

4. **Safety and limits the source states and this review keeps (§5–6, Appendices A, C, H).** The paper sandboxes every execution and self-modification with strict time limits, traces every diff via the archive, and has found no harmful behaviour — but notes that benchmark-only optimisation can amplify misalignment if the benchmark does not capture safety/robustness, and that iterative rewrites can produce increasingly uninterpretable logic (citing Bostrom, Sheth et al., Greenblatt et al.). Fixes are not claimed: training FMs themselves is left out (frozen pretrained FMs only), open-ended archive maintenance/selection is currently fixed and not itself evolvable ("avenue for future work" §3), each iteration edits one child, staged evaluation uses 10→50→200 task subsets to bound cost (Appendix E), and robustness to stochastic LLM noise is via re-evaluation heuristics (40% threshold on 60 tasks).

A mindset change that removed codebase-editing capability would simply be a red check, not a retained, scored archive node that a later iteration could branch from.

## What is new here

**Replace "prove the edit helps" with "try the edit, measure it on a benchmark, keep the lineage" — and keep the dip that later enables the jump.**

Today the plant's self-development diagnosis is one-directional: an outcome is `OBSERVED` when its bound evidence file is digest-equal and path-eligible, otherwise `UNKNOWN`/`BLOCKED`; a retry is `SETTLED`/`RETRYABLE` by whether the next unused `attempt-N/` directory exists. There is no notion of a child codebase edit that is *lower-performing* yet interesting, no archive that would retain it, and no parent selection that would later resample it despite its dip — exactly the hill-climbing failure that Fig. 2 renders as the gap between DGM and "DGM w/o open-ended exploration" (which retains only the latest editable version and stagnates after one bad edit makes self-modification impossible).

Three ideas transfer directly, each with a line number in this repository where it would land, and each additive to the existing `OBSERVED`/`PARTIAL`/`UNKNOWN` and `BLOCKED`/`CLEAR` vocabulary rather than a replacement.

1. **Empirical validation over proof is the missing complement to the clause.** The paper's §5 warning — "modifications optimized solely for benchmark performance might inadvertently introduce vulnerabilities … if evaluation benchmarks do not fully capture all desired agent properties" — maps to the plant's `EVIDENCE_BINDING_CLAUSE_TIME` and `remedy_successor` discipline: the archive must remain sandbox-traced, digest-bound, and human-reviewable (the same `logs/wall-write-audit.jsonl` and `artifacts/*` binding the `wall outcome` clause enforces since 3c22087). DGM's sandbox + time limit + lineage traceability (§5) is the way to keep `initiative.collect`'s empirical extension from becoming an unreviewed auto-commit — every `attempt-N` diff stays a candidate, not a deployed pin, until `Genome`'s pinned activation.

2. **Open-ended exploration is the mechanism the plant's single-path retry needs.** The study's Fig. 3 shows many paths to innovation traverse lower-performing nodes and a single key innovation (node 24) leads to an explosion of children built on it. The plant's `fresh_attempt()` analogue today is hill climbing: it always branches from the latest. A DGM-style archive `initiative_archive.json` (beside `checks/initiative.json`) that stores every prior `initiativ` *plant-version* snapshot — `{version_id, parent_id, score, tasks_scored, editing_capability: bool, diff_sha256, benchmark: "SWE-bench-mini|Polyglot-mini", produced_at}` — with parent selection roughly proportional to `score × branching_factor` (Appendix C.2) is the way to keep a dip alive long enough for the later jump. The paper's cost model (10→50→200 staged subsets, 40% trigger, §4.2, Appendix E) gives the budget: do not re-score the full benchmark on every candidate.

3. **"Stepping stone" is observable as a distinct kind, not a synonym for "best so far".** DGM's archive distinguishes *best* (highest score) from *interesting yet suboptimal* (cited p. 2: Hughes et al. 2024) — the latter are retained even when they are not the max. For this plant the distinction is between the current `report["patches"]` `counts` (`attempt_recorded`/`checked_delivery`/`open_delivery_gap` …) and an *archive* projection that names which prior versions were stepping stones: versions whose score dipped below parent but whose children's later scores exceeded the archive best. That is the counterfactual the plant cannot answer today: not "is the latest deployment green" but "did a worse version enable a later better one that hill climbing would have lost".

**Limits the proposal keeps from the source.** DGM does not evolve its own archive-maintenance/selection loop ("fixed and not modifiable" §3), does not train FMs, runs one child per iteration with 2–4 parallel iterants, and stages evaluation to bound cost. The same bounds apply here: the archive is measurement and candidate generation only, under `genome` review, with sandboxed trial branches and exact-SHA pinned activation unchanged. A benchmark-only loop can overfit and can amplify misalignment; the plant's existing `eligible_evidence_path` / `MAX_EVIDENCE_BYTES` / `MAX_TOTAL_EVIDENCE_BYTES` budgets are not widened to pass it.

1. **Add archive constants and pure helpers beside `EVIDENCE_BINDING_CLAUSE_TIME` (:32) and `WINDOW_SECONDS` (:35) in `src/mishe_tauftauf/initiative.py`.** New symbols (names illustrative, additive only): `INITIATIVE_ARCHIVE_VERSION: Final[int] = 1` with a docstring citing Zhang et al. 2025 arXiv:2505.22954v2 §3/§4.3 (array of all prior generated plant-version snapshots, not only the latest) and distinguishing it from the rolling 24 h `collect()` window; `DGM_EMPIRICAL_VALIDATION = "empirical-benchmark, not proof"` referencing Schmidhuber 2007 → DGM §3 replacement; `ARCHIVE_MAX_VERSIONS = 512` mirroring `MAX_PATCHES`; `STAGED_SUBSETS = (10, 50, 200)` and `STAGED_TRIGGER = 0.40` from §4.2/Appendix E as the evaluated-by-benchmark budget. No I/O, no new snapshot consumer.

2. **Add two pure, deterministic helpers that implement the DGM archive distinction — no tape scan, no file read.** `stepping_stone_score(version: dict) -> float` — the DGM parent-selection weight: `performance_score * (1 + children_with_editing_capability)` normalised over the archive (Appendix C.2), returning `0.0` when `editing_capability is False` (only compiling, editing-capable versions branch, §3 "only agents that … retain ability to edit a codebase are added"). `is_stepping_stone(candidate: dict, archive: list[dict]) -> bool` — true when the candidate's immediate score is below its parent's yet some later descendant in the archive exceeds the archive best that was present at the candidate's creation — the Fig. 3 lineage predicate that separates "worse but enabling" from "worse and discarded". Both are pure dict→float/bool, import-safe, mirroring `top_level_for`/`top_profile_for` in `trial_metrics.py` as a graded profile rather than a single retired sum.

3. **Reuse the plant's existing vocabulary and keep the contract intensive.** No `GREEN`/`RED`/`UNKNOWN` verdict word is newly published, no `checks/initiative.json` shape changes, no `SNAPSHOT_MAX_AGE` or `checks/initiative-watch.json` threshold changes. Missing / stale / future archive is `UNKNOWN` via the same `read_snapshot` raise pattern (`initiative.py:513`) that `follow_through.py` already uses; a non-editing candidate is retained in the archive with `state="archived-no-branch"` but zero selection weight — the same way `invalid` entries become `PARTIAL` with retained gaps (:210–212) rather than a hidden discard. Every archived diff's `sha256` is digest-bound via the existing `hashlib.sha256` path and `MaxBytes` budgets, so `python tools/check_parsing.py` and `ledger-band-second-reader.py` remain the detectors.

4. **Instrument only the reporting entry points the DGM paper names — passive, not committing.** The archive helpers are called from `collect()`'s return as an optional `archive_projection` key inside the JSON-safe evidence (alongside `patches`/`limits`), or from `initiative_watch.evaluate()` as a notice detail — never from `native_recovery.clear_blocked_state` or `wall settle`. No fork, no container, no model change, no new launcher parity.
