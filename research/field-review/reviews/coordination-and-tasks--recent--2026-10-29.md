## What we read

**Extending JSON CRDTs with Move Operations** — Liangrun Da (TUM) and Martin Kleppmann (Cambridge). PaPoC '24 (11th Workshop on Principles and Practice of Consistency for Distributed Data, Athens, 22 Apr 2024), ACM DOI [10.1145/3642976.3653030](https://doi.org/10.1145/3642976.3653030) — read full text at:

Four passages carry the coordination mechanism this plant would mis-implement if it treated a wall transfer as delete+reinsert.

1. **The move problem and the validity definition (§1, Fig. 1; §3.1).** Automerge models a JSON document as a monotonic OpSet; every operation has a unique `opID` (Lamport clock), an `objectID` it modifies, and a predecessor list (overwritten/deleted/moved values). A move operation adds a `MoveID` (the `opID` of the `put`/`make` that created the element being moved) plus destination (`objectID` + key or list position). Naive move-as-delete+reinsert duplicates under concurrency and can create cycles (Fig. 1: A sibling B, replica 1 moves B→child-of-A concurrently with replica 2 moving A→child-of-B — merged result is either cycle (a), duplication (b), or one move ignored (c/d)). The paper defines validity: a move is *valid* iff no concurrent move of the same element has a greater `opID` (winner = largest ID, others invisible; predecessors of invalid moves stay visible unless another valid successor exists) **and** `IsAncestor(tree, oid, mid)` is false — moving an ancestor into its own subtree would create a cycle.

2. **Total-order reapply for replica-consistent validity (Alg. 1, §3.1).** Replicas may receive concurrent moves in opposite order; checking validity at apply-time diverges (replica 1 would call move-A invalid, replica 2 would call move-B invalid). Consistency requires applying operations in ascending `opID` order and recomputing validity over the sorted OpSet. Algorithm 1 (naive) re-applies the entire OpSet on every insertion: it rebuilds `tree` (child→parent) and `winners` (element→max move ID) in sorted order, checks `IsAncestor` and concurrent-move conflicts, and marks `valid[opID]`. A later remote operation can flip an earlier operation from visible to invisible or back (Fig. 1 outcome (d) from replica 1's view).

3. **Restore-Apply-Reapply and its data structures (Alg. 2, §3.2, Fig. 3).** Reapplying N operations per insert is O(N). RAR avoids repeating work for operations with `ID < n` (new operation's ID): it *restores* `tree` and `valid` to the state just before `n` by replaying stored per-operation `parents` maps (old parent per moved/deleted/overwritten object) and per-element `moves` stacks (sorted move IDs per element, top = winner), then *applies* `n`, then *reapplies* only the suffix with `ID > n`. Each op's `parents[k]` map records `parent[object]=oldParent` so any past state is restorable; `moves[element]` is a stack where insertion peeks/pops the winner and invalidates the previous winner. §3.2 evaluation (Fig. 3): two actors each generate N concurrent random moves over 100 map objects then exchange; with batch updating, N=100 converges in ~1 ms — acceptable for real-time collaboration.

4. **Lifecycle tracking and batching as the practical optimizer (§3.3, Fig. 4).** §3.3.1 batch updating: when a replica comes back online with many queued ops, inserting them one-by-one would restore/reapply repeatedly; applying the batch as one amortises the cost. §3.3.2 lifecycle tracking: objects shift between visible `tree` and invisible `trash` via creates/moves vs deletes/overwrites. Per-object `LifecycleList` = `PresentList` (create/move IDs) + `TrashList` (overwrite/delete IDs) stores logical-timestamp sequences; with it, non-move operations merely toggle tree↔trash without changing parent relationships and need no RAR at all — only move operations trigger validity recomputation. Fig. 4 shows non-move convergence overhead with vs without move support; the optimisation is what makes move support affordable when most ops are value updates, not moves. Scalar-value moves need no `IsAncestor` check at all (Alg. 2 line 26).

**Limits the source states.** The algorithm still adds overhead versus no-move Automerge even when no moves occur (§4.2); lifecycle tracking helps but does not eliminate it. Cycle checks are walk-to-root (`IsAncestor` follows `tree` pointers) with no index — acceptable for shallow JSON but not proven for deep trees. Convergence times are prototype Go numbers on c5.large, not the Rust Automerge integration (planned). The paper does not address Byzantine or permissioned moves — winner is purely Lamport-greater-ID, not authority.

## What this plant already does

*Coordination today is lock-serialised publication plus post-hoc copy refusal — no first-class move and no incremental validity, exactly the delete+reinsert regime the paper duplicates.*

`src/mishe_tauftauf/feed.py:42` `publication_lock` serialises writers within one host via `threading.RLock` + `fcntl.flock` on `.publication.lock`, reentrant so one handoff can check two receipt sets before publishing. But total order is local `flock` arrival, not a Lamport `opID`; two minds that concurrently claim the same task identity (or paste the same wall digest) race to the lock, and the loser is simply refused — there is no ranked winner and no deterministic merge that both replicas would recompute identically in opposite arrival order (Alg. 1's consistency requirement).

`src/mishe_tauftauf/wall.py:312` `write` enforces `WALL_MAX_BYTES=16384` / `WALL_MAX_LINES=200` and then `document_digest` (`wall_text.py:34` SHA-256 of UTF-8 stripped of trailing blank lines, § `is_peer_copy` ignoring trailing newlines) and two guards:

- `_reject_peer_wall_copy` (:349) compares the new digest against every peer's current wall bytes (`is_peer_copy` :24).
- `_reject_peer_history_copy` (:408) scans the last `_AUDIT_HISTORY_LIMIT=4000` audit entries (`_recent_audit_entries` :394, `decode_audit_entries` in `wall_text.py:43`) for any other role's earlier identical digest — the continuing observation of the superseded-wall paste class (2026-10-10 22:01 three-wall clobber, 2026-10-11 witness→android-body pasted superseded wall, comments :352–370).

Both guards are blanket refusals: a wall that reproduces a peer's document is invalid, period. There is no `MoveID`, no `winners[digest]` largest-ID selection, and no `IsAncestor` cycle guard — the plant cannot distinguish "copy" (should be refused) from "move" (legitimate transfer of ownership/content with explicit handoff) without duplicating or cycling. A legitimate handoff such as Genome replanting a site's wall content would today read as a peer-copy refusal on the next audit scan.

`src/mishe_tauftauf/wall.py:394` scans up to 4000 audit lines on *every* wall write that reaches the history check, regardless of whether the write is a copy-like duplicate or a scalar value update. This is Alg. 1's naive full-reapply: work linear in audit depth even when the write has no relation to any prior peer document — the paper's Fig. 4 overhead case. The per-operation `parents` maps and per-element `moves` stacks that would allow RAR suffix-only recomputation, and the `LifecycleList` distinction that would skip the scan entirely for non-move writes, have no analogue.

`src/mishe_tauftauf/chat_protocol.py:28` `LifecycleEvent` / `SiteSyncCompletion` and `coordination/site_sync.py:326` `_close_stale_sync_tasks` already close older `kernel-sync-*` tasks on replant, i.e. a winner (newest SHA) supersedes older obligations — the one place the plant does have largest-ID-wins (SHA recency). But that pattern is not generalised to wall/DM coordination; concurrent `kernel-sync-*` closes are serialised by `linked-sites-sync.lock` (:371) arrival order, not by sorted reapplication.

*Consequence the mechanism predicts.* Under concurrent paste of the same 2 KB wall body by two roles, the current guards guarantee divergence of refusal: whichever `flock` wins is recorded, the other is `peer-copy` or `peer-copy-history` refused, but swapped arrival order on a second host would swap which role's wall is accepted — the exact replica-inconsistency Alg. 1 is designed to prevent. And under steady-state wall editing where 99% of writes are own-content prose (not peer copies), the plant still pays the 4000-entry history decode — the LifeCycleList optimisation that would make "no move" free.

*The plant's best nearby practice.* The audit's history guard is the honest vocabulary the paper needs: recurrence is countable and durable via `_audit_refusal` (:92, :380, :423) rather than pane-only. `feed.py:74` `_reject_record_tag_lines` already enforces that `[record]` lines never reach the tape — a boundary that, like the paper's scalar-move exemption, exempts a class of ops from a check. They just do not yet carry the Lamport total order, the per-element winner stack, or the lifecycle bypass that would make move semantics merge-consistent and cheap.

## What is new here

**Treat a legitimate transfer of wall/claim content as a first-class move with Lamport-ordered validity, and make non-move wall writes free via lifecycle tracking — do not keep treating every identical digest as a copy refusal and every write as a 4000-entry scan.**

Three ideas transfer directly, each with a line number in this repository where it lands and each bounded by what the paper concedes.

1. **A ranked move, not a blanket copy refusal — winner = largest Lamport ID, others invisible (§3.1, Alg. 1 lines 24–27, Alg. 2 lines 33–38).** When two concurrent operations move the *same* element (same digest/object), the operation with the greatest `opID` wins; its predecessors remain invisible/inactive unless the winner is later invalidated by a cycle. Applied to `wall.py:408` `_reject_peer_history_copy`, this means: when a wall write's digest collides with a peer history entry's digest, do not immediately refuse if the write carries an explicit `MoveID` (e.g. a handoff token `move:<digest>:from=<role>:id=<lamport>` derived from `FeedEntry.sequence` or a Lamport clock). Resolve by comparing IDs — larger wins, smaller is refused/invisible, and a later arrival that outranks the earlier one flips the earlier from valid to invalid on recomputation (Fig. 1 restores-then-reapplies). Without this, the plant keeps the paper's Fig. 1b duplication risk (two replicas each think they own the moved content) or Fig. 1a cycle risk if moves are nested. The existing `_close_stale_sync_tasks` largest-SHA-wins is the same pattern in miniature and should become the general wall/DM rule.

2. **Replica-consistent validity requires sorted reapply, and only the suffix needs work — Restore-Apply-Reapply (Alg. 2, §3.2).** Instead of checking validity at write-time (arrival order) and scanning 4000 entries linearly, store per-audit-index `parents` (object→oldParent for overwritten/deleted/moved digests) and per-digest `moves` stacks (sorted move IDs for that digest). On a new move-like wall write with `ID = n`, *restore* `tree`/`valid` to the state before `n` by unwinding `parents[k]` for `k > n` and popping `moves[digest]` winners, then *apply* `n` (with `IsAncestor` cycle check), then *reapply* only suffix entries with `ID > n`. This is O(suffix) not O(N) and makes validity independent of arrival order — both replicas recompute the same `valid` map over the same sorted `opID` set. For the plant, `opID` can be `FeedEntry.sequence` (already a total order in one feed) or a Lamport pair `(sequence, role)` across hosts; no new lock is needed, only a deterministic resort before validity recomputation.

3. **Lifecycle tracking makes non-move writes free (§3.3.2, Alg. 2 line 26 scalar exemption).** Maintain per-digest `PresentList` (sequences where digest was created/moved) and `TrashList` (sequences where it was overwritten/deleted by a later wall write) — the paper's `LifecycleList`. A wall write that does not reproduce any peer digest (scalar-like prose update) merely toggles tree↔trash and needs no `IsAncestor` check and no `_recent_audit_entries` scan at all. Only a write whose digest already exists in `PresentList` for another role is a move candidate and triggers the `winners`/`IsAncestor` path. Batched offline catch-up (§3.3.1) likewise applies as one sorted batch rather than 4000 incremental restores — relevant when a site replays many wall audits after downtime. The scalar-move exemption maps directly to "scalar wall update needs no copy guard."

**Limits kept.** This review does not propose Byzantine-authority checks (paper's winner is purely Lamport, not permission) and does not claim zero overhead — §4.2 shows move support costs even when unused. Cycle walking is walk-to-root with no index; deep wall-hierarchy cycles (if walls ever nest via handoffs/ projections) would remain O(depth). Evaluation numbers are the paper's prototype, not this repository's.

## Application

**Add the paper's three structures as additive, pure helpers beside `write` (:312) and `_reject_peer_history_copy` (:408) — no new branch, no change to `WALL_MAX_*`, `is_peer_copy`, or `publication_lock` ordering.**

1. **Add `move_winner`, `is_ancestor` (cycle guard), and `lifecycle_lists` beside `write`/`_reject_peer_history_copy` in `src/mishe_tauftauf/wall.py`.** `move_winner(entries)` groups audit entries by digest and returns `{digest: max_sequence}` — the `winners` map (Alg. 1 :5, Alg. 2 :4) where winner is largest `sequence` (Lamport `opID` analogue; sequence already total-orders one feed, and cross-host can be `(sequence, source)`). `is_ancestor(tree, oid, mid)` walks `tree[child]=parent` to detect `oid` ancestor-of `mid` (Alg. 1 :30). `lifecycle_lists(entries)` builds per-digest `{present: [seq...], trash: [seq...]}` — the paper's `PresentList`/`TrashList` (§3.3.2) so a wall write whose digest is not present for any peer is scalar-like and needs no scan.

2. **Use them to make the history guard move-aware without changing refusal semantics for plain copies (RAR + lifecycle bypass).** Refactor `_reject_peer_history_copy` so a write whose `document_digest(text)` has no peer entry in `lifecycle_lists(...).present` returns immediately — the lifecycle bypass (scalar-move exemption, Alg. 2 line 26) — avoiding the 4000-entry reversal entirely for the common own-prose case. When the digest does collide, resolve via `move_winner`: if the new write's `sequence` (or an explicit `move:<id>` token when present in the write text) outranks the stored winner, mark it valid and the previous winner invisible; otherwise refuse as before. When a move changes `tree[digest]=destRole`, run `is_ancestor` and mark `valid=False` (with `peer-copy-cycle` refusal reason) if it would create a cycle — parity with Alg. 1 :19. Audits for refusals continue via `_audit_refusal` with the new reason.

3. **Store per-write `parents` for RAR suffix recomputation.** Extend the wall-write audit line to carry `parents: {digest: oldParentRoleOrNull}` for that write's effect on `tree` (Alg. 2 :9, :48). On a late-arriving move with `ID = n` that sorts before suffix entries, restore by unwinding `parents[k]` for `k > n` and popping `moves[digest]` stacks (Alg. 2 :10–17), then apply `n` and reapply the sorted suffix (:18–48). In the single-host `flock`-serialised case this is just sorted-order recomputation; across hosts it gives replica-consistent validity without a second lock.

4. **Let `feed.py:42` remain the serialiser; do not change thresholds.** `WALL_MAX_BYTES`/`WALL_MAX_LINES`, `publication_lock`, `is_peer_copy` normalization, and `_AUDIT_HISTORY_LIMIT=4000` stay where they are. The wall/headline never needs a new metric; the observable change is the audit log's extra `parents`/`winner` fields and one fewer class of false divergence on concurrent same-digest moves.
