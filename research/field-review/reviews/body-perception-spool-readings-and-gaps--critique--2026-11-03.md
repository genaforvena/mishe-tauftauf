- Verbatims carrying the critique (page refs to the CACM paginated PDF, pp.74–80):
  - Key insights box p.74–75: "Even rare performance hiccups affect a significant fraction of all requests in large-scale distributed systems." / "Eliminating all sources of latency variability in large-scale systems is impractical, especially in shared environments." / "Using an approach analogous to fault-tolerant computing, tail-tolerant software techniques form a predictable whole out of less-predictable parts."
  - Why Variability Exists p.74–75: five sources — Shared resources ("Machines might be shared by different applications contending for shared resources (such as CPU cores, processor caches, memory bandwidth, and network bandwidth), and within the same application different requests might contend for resources;"), Daemons ("Background daemons may use only limited resources on average but when scheduled can generate multi-millisecond hiccups;"), Global resource sharing, Maintenance activities (data reconstruction, log compaction, garbage collection), Queueing ("Multiple layers of queueing in intermediate servers and network switches amplify this variability"); plus hardware trends Power limits, Garbage collection, Energy management.
  - Component-Level Variability Amplified By Scale p.76: fan-out figure — "If a user request is handled on just one [10 ms typical, 1 s p99] server, one user request in 100 will be slow (one second)… If a user request must collect responses from 100 such servers in parallel, then 63% of user requests will take more than one second (marked 'x' in the figure). Even for services with only one in 10,000 requests experiencing more than one-second latencies at the single-server level, a service with 2,000 such servers will see almost one in five user requests taking more than one second (marked 'o' in the figure)." Table 1 (real Google fan-out service): single random leaf p99 10 ms, but all leaves p99 140 ms, 95% of leaves p99 70 ms — "waiting for the slowest 5% of the requests to complete is responsible for half of the total 99%-percentile latency."
  - Reducing Component Variability p.76–77: Differentiating service classes / higher-level queuing ("Keep low-level queues short so higher-level policies take effect"), Reducing head-of-line blocking (time-slicing long requests), Managing background activities and synchronized disruption ("synchronize the background activity across many different machines… In contrast, without synchronization, a few machines are always doing some background activity, pushing out the latency tail on all requests"), plus note "caching… do[es] not directly address tail latency, aside from configurations where it is guaranteed that the entire working set… can reside in a cache."
  - Hedged requests p.77: "A simple way to curb latency variability is to issue the same request to multiple replicas and use the results from whichever replica responds first. We term such requests 'hedged requests' because a client first sends one request to the replica believed to be the most appropriate, but then falls back on sending a secondary request after some brief delay. The client cancels remaining outstanding requests once the first result is received." / "Although naive implementations of this technique typically add unacceptable additional load, many variations exist that give most of the latency-reduction effects while increasing load only modestly." / "One such approach is to defer sending a secondary request until the first request has been outstanding for more than the 95th-percentile expected latency for this class of requests. This approach limits the additional load to approximately 5% while substantially shortening the latency tail… The overhead of hedged requests can be further reduced by tagging them as lower priority." / Benchmark: "sending a hedging request after a 10 ms delay reduces the 99.9th-percentile latency for retrieving all 1,000 values from 1,800 ms to 74 ms while sending just 2% more requests." / "Permitting more aggressive use of hedged requests with moderate resource consumption requires faster cancellation of requests." / "A common source of variability is queueing delays on the server before a request begins execution. For many services, once a request is actually scheduled and begins execution, the variability of its completion time goes down substantially."
  - Tied requests p.77–78: "choosing but rather enqueuing copies of a request in multiple servers simultaneously and allowing the servers to communicate updates on the status of these copies to each other. We call requests where servers perform cross-server status updates 'tied requests.' The simplest form… when a request begins execution, it sends a cancellation message to its counterpart… There is a brief window of one average network message delay where both servers may start executing the request while the cancellation messages are both in flight… It is useful therefore for the client to introduce a small delay of two times the average network message delay (1 ms or less in modern data-center networks) between sending the first request and sending the second request." Table 2 (BigTable small read): tied after 1 ms reduces median 16–21% and p99.9 ~32–38% with <1% disk overhead via cancellation; without tied, concurrent terasort raises latencies to the level tied achieves under contention.
  - Probe vs hedged p.78: "An alternative to the tied-request and hedged-request schemes is to probe remote queues first, then submit… It can be beneficial but is less effective than submitting work to two queues simultaneously for three main reasons: load levels can change between probe and request time; request service times can be difficult to estimate due to underlying system and hardware variability; and clients can create temporary hot spots by all clients picking the same (least-loaded) server at the same time."
  - Limits/concessions p.77–78 and p.79: "Note, too, the class of techniques described here is effective only when the phenomena that causes variability does not tend to simultaneously affect multiple request replicas. We expect such uncorrelated phenomena are rather common in large-scale systems." / Hedging at the 95th percentile "limits the benefits to only a small fraction of requests" — caps load at ~5% but narrows the tail reduction. / Directly before cross-request section: "Even if such perfect behavior could be achieved in isolated environments, systems with shared computational resources exhibit performance fluctuations beyond the control of application developers." / Long-term adaptations concede separate timescales: within-request tens of milliseconds vs cross-request tens of seconds to minutes (probation / micro-partitions / selective replication), and shadow requests to avoid permanent exclusion ("The system continues to issue shadow requests to these excluded servers, collecting statistics on their latency so they can be reincorporated… This situation is somewhat peculiar, as removal of serving capacity… during periods of high load actually improves latency.").
  - Large IR "Good enough" p.79: speed as quality metric — returning slightly sub-best results quickly can beat waiting for the slowest leaves.

- Limits kept here: the paper's IR "Canary… SCP" figure details after p.79 and the acknowledgements are not transferred; only the tail-amplification numbers, causal taxonomy, hedged/tied mechanics with their explicit load/correlation/cancellation windows, and the stated impracticality of eliminating all variability are used.

## What is new here

The critique Dean & Barroso make of the "just add redundancy" reflex, and what adopting that reflex blindly would reproduce in this plant's spool shape.

1. **Tail amplification already applies to the dense queue's "fan-out" in time.** The paper's figure p.76 is a combinatorial amplification argument, not a BigTable-specific claim: fanning one user request over 100 leaves each with p99 1 s makes 63% of user requests >1 s; with 2,000 leaves even 1-in-10,000 outliers make 18% of requests >1 s. The dense window's "fan-out" is 2000 rows in time. Table 1 shows the symptom that maps verbatim: a single leaf p99 10 ms becomes all-leaves p99 140 ms (14×), and waiting for the slowest 5% is half of p99 (70 ms of 140 ms). The plant's window has the same shape: a single-row freshness target `FRESH_SECONDS 30.0` vs a 2.8 h window that must wait for *all* leaves (rows) to judge "carried-device coverage." The outlier that matters is not a slow server but a single lagging `epoch` (measured 100 s) or a single batch's 1335 s inter-arrival |D| — enough to flip `break_seconds` or dominate the RFC 3550 smoothed J (83.0 s from one 1335 s step at 1/16 decay). Reporting one `break_seconds` / one `J` hides this decomposition exactly as reporting only single-leaf p99 hides Table 1's 95%-vs-100% split.

2. **Hedged/tied "fix" without the paper's three load invariants would reproduce the paper's warned failure.** Dean & Barroso prove hedged requests work *because* the source of latency is often interference not inherent request cost (p.77 "the source of latency is often not inherent in the particular request but rather due to other forms of interference"; queueing before execution dominates p.77), and then list the invariants that make hedging not "unacceptable additional load":
   - Defer the duplicate to the 95th-percentile expected latency — caps extra load ~5% (p.77) but explicitly "limits the benefits to only a small fraction of requests." Naive hedging without this cap is the warned "unacceptable additional load."
   - Require faster cancellation / cross-server cancellation within a 1 ms-scale window, with a 2× network-delay stagger to avoid both replicas executing (tied requests p.77). Without cancellation, disk overhead is not <1% as in Table 2 but multiplied by the hedged fraction; probe-then-submit is "less effective than submitting work to two queues simultaneously" for three stated reasons (p.78).
   - Effective only when variability is uncorrelated across replicas (p.77 "effective only when the phenomena that causes variability does not tend to simultaneously affect multiple request replicas"). The plant's spool has at least two shared contention domains that would correlate: global resource sharing / tailnet + file-system sharing (Why Variability Exists p.74–75) and synchronized maintenance windows (log compaction, garbage collection p.75). Duplicating polls over the same tailnet/FS/synchronised-window path would co-fail, as the paper says to expect.

   Blindly mapping "spool gaps are tail latency, so hedge the poll" onto the current consumer (`read_redmi10_dense_baseline` reading one `DENSE_TAIL_BYTES` tail, one `FRESH_SECONDS` gate, one `STALL_SECONDS 300.0` cursor check) would add load to the exact shared resources the taxonomy says amplify variability (CPU/cache/bandwidth, background daemons, queueing, GC) and would not be rescued by the tailnet path diversity that tied requests assume (three FS replicas, three-minute-level partition mobility in BigTable §§p.78–79). The plant documents none of these invariants.

3. **The paper's conceded two-timescale decomposition and "good enough" have direct analogues the plant does not type.** The paper explicitly separates within-request short-term adaptations (tens of milliseconds: hedged/tied) from cross-request long-term adaptations (tens of seconds to minutes: micro-partitions 20–1,000 tablets per machine shedding load in ~5% increments, selective replication of hot micro-partitions, latency-induced probation with shadow requests to avoid permanent exclusion p.78–79). The plant's freshness fixes live in only one timescale: a 30.0 s binary gate plus a 24 h halt window plus a 2.8 h dense window, with no probation/shadow discipline for a stale peer or a synchronised-maintenance window. The "Good enough" IR principle (p.79, speed as quality: "once a sufficient fraction of all the leaf servers has responded, the user may be best served by being given slightly [sub-best results]") maps to the dense summary's untyped choice to wait for 100% of `DENSE_WINDOW_ROWS` vs returning on 95% completion as in Table 1 — the paper shows the last 5% is half the p99.

4. **What the critique concedes and where the transfer's limits lie.** The paper concedes tail-tolerant techniques *can* use fault-tolerance resources for "low additional overhead" (p.74), and gives existence proofs where hedging works (Table 2: <1% disk overhead via cancellation; Fig. benchmark 1,800 ms → 74 ms for 1,000 keys at 2% extra requests). So the critique is not "never hedge" — it is "hedging without load cap / cancellation window / correlation check hurts." The paper also concedes micro-partitions / selective replication / probation are complementary long-term tools, and that caching alone does not fix tails unless the entire working set is guaranteed cached (p.77) — so proposing "just enlarge `DENSE_TAIL_BYTES`" as a cache would be the wrong lesson. The plant is not a fan-out leaf service and has no measurable replica set (one Redmi10 tail, one tailnet peer, one host FS); the quantitative Table 1/Figure amplification numbers are transferred as the combinatorial argument, not as a calibration of this host.

The prior critique (Schafer & Graham, MAR/MNAR, complete-case denominator) is therefore complemented, not superseded: that critique is about whether `motion_ratio` ignores missing rows; this critique is about whether adding duplicate reads to *reduce* missingness would itself amplify tails when shared.
