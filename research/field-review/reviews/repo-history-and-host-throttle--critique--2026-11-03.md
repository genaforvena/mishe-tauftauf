## What this plant already does

- The head-rewinds sense already embodies a bounded, general-case dropped-commit detector (2026-11-01 misread fix): any SHA that leaves HEAD in the reflog window is counted, not just resets, with branch-switch/cherry-pick/amend/rebasing all producing the same observable. The count is reported inside the window and never as "work was lost"; loss is decided per path, never from the count. Dispositions sit beside the reading, not inside it.
- The window and its expiry are already named in the docstring ("Counting rule" paragraph, l.3810–3820): last-200 entries, `gc.reflogExpireUnreachable` 30 days, count is a count *inside* that window. `reset_origin` stash correlation is explicitly correlation-only.
- What it does not yet say is that the boundary the paper proves for an *external* snapshot detector also binds the *local* reflog detector, only tighter. SWH's construct threats are: archival frequency misses short-lived rewrites; multiple alterations between two snapshots merge into one; metadata hidden when files also change; 10-generation horizon is arbitrary. The plant's 200-entry/30-day window reproduces each of those at a smaller scale plus one local conflation: a single `dropped-commits=N` merges resets, branch switches, amends and rebases into one scalar, and a quiet window (`0 dropped`) is not evidence of no alteration — only of no reachable SHA leaving HEAD in that window. The 2026-11-03 recent review proposed taxonomy constants (`ALTERATION_CATEGORIES`, `ALTERATION_TAXONOMY_DEFINITION`, `alteration_category_hint`) without carrying these validity limits into the same docstring.
- Prior critique for this field (2026-11-01) covered the *throttle* failure mode (ratio as limit event vs demand/stranding/burst, Chiluk + Indeed). This review complements it with the *history* failure mode: adopting the history-alteration taxonomy/scale without its validity section would overclaim what either detector can prove.

## What is new here

The critique is the paper's own — it concedes four blind spots that transfer one-to-one onto the plant's local detector, each stronger locally:

1. **Short-lived alterations are invisible outside the window.** SWH: "Malicious or accidental short-lived alterations might be missing … if they have been fixed by reverting … between two archival visits." Local analogue: a rewind that is itself rewound (or expires) before the last-200 window, or more than 30 days before the scan, leaves no SHA to count. A `0 dropped` sample after a busy week is not "clean history", only "no alter inside the window". Adopting the 1.22 M / 111 M prevalence prior without this distinction would read a quiet local sample as global cleanliness.

2. **Multiple alterations collapse to one observation.** SWH: "we cannot distinguish multiple history alterations that happen between two visits … we will recognize them as a single alteration, merging together what changed in all of them." Local analogue: `dropped-commits=N` counts distinct shas, not episodes; a `reset` followed by an `amend` followed by a `cherry-pick` in the same window collapses to `N` shas, and `needs-review-paths` merges their path sets. The detector's sample cannot answer "how many rewrites happened", only "how many shas left HEAD in this window and what happened to each path's bytes".

3. **Metadata rewrites are silent when file changes co-occur.** SWH: "Metadata changes are not detectable … when file changes also occur, due to the lack of a commit to compare against." Local analogue: a dropped SHA whose `diff-tree --name-only` list is non-empty shows a DIR signal even when its amend also changed message/author-date; the plant's current per-path buckets approximate DIR (lossless≈modified-already-present, absent≈removed) but collapse META-only signals into DIR noise or into `0 changed paths`. A dropped SHA with `changed_paths=[]` is not "nothing happened" — it is the 13.3% META-only class the paper isolates (committer-date most frequent), and the plant's earlier misread noted that a `commit (amend)` entry with zero changed paths fits it.

4. **"Same file" horizon is a judgement, not a fact.** SWH: file content tracked "up to 10 commits deep … it would become debatable whether a file reappearing 'many' commits away … is to be considered the same file." Local analogue: `git apply --check` against HEAD's tree decides lossless/absent/needs-review by byte equality to one commit's hunk, not by file identity across 10+ generations. A path that reappears re-committed many commits later can read as `absent` (forward-apply fails at HEAD) or `needs-review` (`superseded`/`rewritten` line counts), without answering whether it is the same file. Treating `needs-review` as "alive" or "dead" would overclaim beyond the paper's own caution.

5. **Predecessor relation (explicit).** 2026-11-01 critique named the throttle-ratio overclaim (limit event misread as demand). This names the history-count overclaim (windowed reflog/SWH count misread as alteration count or as proof of absence). Both are counting-rule misreads — one on `nr_throttled / nr_periods`, one on `dropped-commits` — and both keep the warning/reading observation-only. 2026-11-03 recent supplied the taxonomy and prevalence; this supplies the validity section that qualifies them.

Honest limits of this reading: single 10-page paper read via rendered HTML + 104 kB pdftotext, not the SWH graph Rust code [5]; SWH dedup horizon and ScanCode heuristics not re-verified; local detection path (`rev-list HEAD` + `apply --check`) measured only on this checkout's last-200 window (10 of 198 distinct shas, single-digit stable per discover/latest.json), not on a forced multi-rewrite sequence. No supply-chain judgment is made about any path; LICENSE/secret patterns remain higher-scrutiny classes, not verdicts.
