## What we read

**Retry Amplification in Distributed Systems: A Systematic Analysis of Retry Policies and Their Role in Cascading Failures** — Rishabh Mehan, Jasmit Kaur Saluja. *arXiv:2608.25403 [cs.SE]*, 26 Aug 2026, 12 pp. — read full HTML at:

- <https://arxiv.org/html/2608.25403v1> (canonical)
- <https://arxiv.org/abs/2608.25403> (abstract)

Four passages carry the change this plant has not made.

1. **RAF and multi-tier compounding — Definition 1, Eq.2–3, §III-B/C, p. 3.** For a service with failure probability `p` and retry limit `n`, `RAF = sum_{k=0}^{n} p^k = (1-p^{n+1})/(1-p)` (Eq.2); at `p=0.5, n=3`, `RAF=1.875` — request volume nearly doubles at one tier. Across a chain of depth `d` with the same policy, `RAF_aggregate <= RAF^d` (Eq.3); three tiers at `p=0.3, n=3` give `(1.417)^3 ≈ 2.85`, at `p=0.5` it is `≈6.59`. The model assumes `p` constant; overloaded services raise `p` with each retry wave, pushing the bound higher. Temporal dynamics (§III-D): immediate retries concentrate into a spike, deterministic backoff without jitter makes independent clients synchronize into periodic surges.

2. **How real code is configured — §IV, Table I, p. 5.** In 200 Python microservice repos (Go 47.6%, Python 31.2%, Java 21.2% in the 1,000-candidate pool; first 200 by collection order are all Python, §IV-A), regex rules detected retry logic in 23/200 = 11.5% ±4.4% (Wilson); carrying a seeded 33.3% false-negative rate (10/30 undetected repos actually retry, §IV-B) puts true prevalence near 41% (28.5–56.8%). After cleaning 162 raw hits → 113 production configurations (41 non-production, 8 duplicates): retry count `>5` is the largest group 32/73 = 43.8% (beyond 3-attempt vendor guidance), `no backoff (immediate)` 35/113 = 31.0%, `exponential backoff` only 24/113 = 21.2%, `jitter (verified)` 1/113 = 0.9% (eight `jitter|random` hits audited, three genuine, two documentation; §IV-B). Re-check of 30 detections gave 96.7% precision. Limitations the source states: runtime env/config params appear as static values, YAML-configured retries (Spring Cloud) missed, detections concentrated (1 project supplies 23/113, top three 44%), so configuration-level percentages are descriptive, not independent draws.

3. **Five anti-patterns — §IV-D, p. 5.** Per-project (denominator 23): No Backoff 14/23 = 60.9% ±18.5pp; Missing Jitter 22/23 = 95.7% ±10.1pp (narrow reading: exponential-backoff without jitter 9/23 = 39.1%); Aggressive Retry (>5 with minimal backoff) 7/23 = 30.4%; Static Configuration 23/23 = 100%; No Cross-Service Coordination 23/23 = 100%. The last two are universal and, per the model, the drivers of multi-tier compounding.

4. **Simulation that retries can hurt, and ARB that does not — §V–VII, Tables II–IV, Algorithm 1, p. 6–8.** Discrete-event five-tier chain (API→Auth→Catalog→Inventory→Database, capacity 1000 RPS, base 500 RPS, `n=3` exponential 100/200/400 ms + jitter; `n=100` trials per cell). Model-predicted RAF (Table II): S1 50% at tier 3 → 1.88; S2 10→70% at tiers 4–5 → 1.23–6.42; S3 60% at tiers 3–5 → 10.30. Measured (Table III–IV, §VII-B): S3 success NR 55.4% ±0.1pp, SR (standard retry) 41.5% — retries *cut* success by ~14pp (a quarter) under correlated failure; S1/S2 similar inversions. Circuit breakers (50% threshold, 30 s open) help only after overload is observed. Adaptive Retry Budgeting (§VI, Alg.1): per-tier budget `B←B0=0.2`, EMA failure rate `fr←0.9·fr+0.1·1[failed]`, retry probability `prob←min(B,1-fr)` only if `B>0` and downstream not `OVERLOADED`; per-failure `B←max(0,B-1/λ)`, per-second `if fr>θh=0.3 or OVERLOADED then B←B·(1-β=0.5)` else if `fr<θl=0.05 then B←min(B0,B+α=0.1)` with `T=1.0 s`; `OVERLOADED ≡ (Q>0.8·Qmax) ∨ (CPU>0.9)` emitted as header/metadata. ARB holds S3 success near the no-retry baseline while still recovering transient faults; cost `O(1)` per request plus five tunables and a deploy-coordinated backpressure contract (§VI, last paragraph). Source is simulation, not production measurement, and the empirical base is Python-idiom-visible code only.

**Why this literature for this cell.** The prior `failure-and-recovery--recent` on the branch (2026-10-29, PILOT NSDI'26) answered "what happens *after* detection when the recovery itself is wrong" and proposed phantom-thread rehearsal. The RAF paper answers the complementary question "what happens when every recovery is locally correct but globally uncoordinated." The plant's own recovery is bounded and classified (see next section) — PILOT would rehearse a bad retry, ARB would prevent a storm of good ones. A 2023–2026 source distinct from PILOT is required for the revisit rotation; this is 2026-08-26.

## What this plant already does

*Bounded, classified retry with no amplification accounting.* `src/mishe_tauftauf/native_recovery.py` classifies one failed wake from its own bytes: `classify_attempt()` checks `summary.json`, journal rows and three ledger journals (`_read_evidence` :278, `_journal_effect_rows` :354), checks completeness of `failure.txt` (`_failure_record` :200) and decides `SETTLED`/`RETRYABLE`/`RECONCILE`/`UNKNOWN` (:92–95) with `TRANSIENT_STATUS = {408,429} ∪ [500,599]` (:99) and `DEFAULT_RETRY_LIMIT=3` (:100). `fresh_attempt()` returns the next unused `attempt-N/` directory or `None` at the limit (:489–502). `attempt_disposition()` chooses the bounded next action from the attempt-report sequence (:568–622). Evidence is the attempt ledger; there is no cross-attempt rate, no queue signal, and no budget.

*No backoff, no jitter, no coordination, static policy.* The three retries are immediate at the runner's cadence. `fresh_attempt` takes a fixed `limit` (default 3) — a static configuration in this paper's taxonomy. No `b(k)`, no randomization, no `prob←min(B,1-fr)` gate. A downstream `OVERLOADED` in another role (or host `capacity LIMITED/CRITICAL` as in dashboard episode 37, `recovery/events/*.json` `available_ratio ~0.51–0.52`) does not reduce the next role's `B`; each role's `MISHE_NATIVE_RECOVERY_WAKE` opt-in (`checks/native-recovery-optin.py`) checks "is this the exact pending wake" not "should this wake be retried now." The paper's universal anti-patterns — static, uncoordinated, and in this file immediate — are the plant's current policy.

*The rehearsal lane exists, the load lane does not.* The PILOT review (2026-10-29) added a `pilot_attempt()`/`pilot_report()` rehearsal vocabulary to this same target. That rehearsal asks "would this next retry corrupt state or propagate?" ARB asks "would this next retry, even if correct, amplify aggregate load `RAF^d` beyond capacity?" The two stack: a retry can be rehearsed-correct and still storm-wrong under `S3` (60% correlated failure, `RAF≈10.30` predicted, measured SR < NR). The plant today has the first lens but not the second; host-pressure `LIMITED`→`CRITICAL` events on 2026-11-02 (sensors 187277–187337) are observed by `health` but not consumed as a retry gate.

## What is new here

**The failure mode is not a bad recovery, it is `d` good recoveries at once.** Eq.3 is the transferable idea: in a plant where several roles or tiers can each retry 3 times, the load a degraded dependency sees is not `1.875×` but `~6.6×` at `p=0.5`, and the empirical study says production code skews toward the aggressive end (`>5` retries 43.8%, no backoff 31.0%, jitter 0.9%). The plant's `DEFAULT_RETRY_LIMIT=3` is moderate, but without backoff/jitter its retries concentrate into the same spike the paper's §III-D warns about, and without a budget its three attempts are spent regardless of `fr` or queue pressure. PILOT's phantom thread would approve each retry in isolation; ARB would deny the second or third because `fr` has crossed `θh` or `OVERLOADED` has arrived.

**Three ideas transfer directly, each with a line number in this repository where it would land.**

1. **Budget as a shared resource beside the attempt counter.** ARB's `B0=0.2` (≈20% of base load may be retries) maps to `fresh_attempt`'s `limit`: instead of "3 attempts per wake regardless," "at most `B·λ` retries per interval, decremented `B←max(0,B-1/λ)` on each `fresh_attempt`, replenished `B←min(B0,B+α)` when `fr<θl`." The paper's operational cost (five tunables, deploy-coordinated signal) is honest; for this plant the signal already exists as `host_capacity` / `pressure-*.json` and the `OVERLOADED` header can be the existing `recovery/events/*.json` `host-pressure CRITICAL` — no new collector, just a consumer in `native_recovery.py` beside `_transient` (:267).

2. **Jittered backoff before `fresh_attempt` is created.** The paper's 100/200/400 ms + jitter and the standard vendor guidance it cites are not in this file. Adding `b(k)=base·2^k + Uniform(-jitter,jitter)` between `attempt_disposition` returning `RETRYABLE` and `fresh_attempt` creating the directory spreads the spike. The anti-pattern to fix is the paper's top one: No Backoff (60.9%) — the plant is currently in that bucket.

3. **Cross-wake/role coordination via backpressure.** Finding 5 of PILOT (92% inter-thread/process/service) already says recovery failures propagate; RAF says retry *load* does too. The paper's `No Cross-Service Coordination 100%` is this plant's per-role independence: `health` observes `host-pressure` but `native_recovery` does not gate on it. Wiring `S_d=OVERLOADED → FAIL without retry` (Alg.1 lines 10–11) into `attempt_disposition` makes retries a system-level property, which is the paper's thesis sentence.

**Limits the proposal keeps from the source.** The empirical base is Python-idiom-visible code in popular Python microservice repos with a disclosed 33.3% false-negative rate — prevalence near 41% is an estimate, not a census, and says nothing about Go/Java (47.6%/21.2% of the 1,000-candidate pool but 0% of the first-200 sample, §IV-A). The evaluation is simulation on a synthetic five-tier chain at `n=100` trials per cell; variance is reported as ±0.1pp but the topology and 500/1000 RPS numbers are not this plant's. ARB is tunable (five parameters) and its `T=1.0 s` / `θh=0.3` / `β=0.5` values are not calibrated to wake-recovery durations (which are seconds-to-minutes, not milliseconds). The paper does not claim ARB replaces circuit breakers or load shedding; it complements them (§VI, last paragraph). Adopting the budget is therefore a conservative gate, not an optimizer for MTTR.

## Application

target: src/mishe_tauftauf/native_recovery.py

**Add a retry budget and jittered backoff gate beside `fresh_attempt`/`attempt_disposition` — additive, behind a flag, host-pressure-aware.**

1. **Add `retry_budget.py`-like state or inline `Budget` dataclass beside `DEFAULT_RETRY_LIMIT` (:100) in `src/mishe_tauftauf/native_recovery.py`.** Fields `B: float = 0.2`, `fr: float = 0.0`, constants `B0=0.2, α=0.1, β=0.5, θh=0.3, θl=0.05, T=1.0` mirroring Alg.1. EMA update `fr←0.9·fr+0.1·1[failed]` on every `classify_attempt` result; budget decrement `B←max(0,B-1/λ)` on `fresh_attempt` success where `λ` is the role's recent wake rate (initially `1.0` to keep `1/λ=1`). Periodic `tick()` implements `if fr>θh or overloaded then B←B·(1-β) else if fr<θl then B←min(B0,B+α)` — called from the same site that emits `pressure-*.json` or on each `attempt_disposition` invocation with `T`-gated timestamp.

2. **Gate `attempt_disposition`/`fresh_attempt` on budget and `OVERLOADED`.** At entry to `attempt_disposition` (:568) after the existing `RETRYABLE` check: if `budget.B <= 0` return `Disposition(RETRYABLE, recoverable=False, reason="retry budget exhausted", evidence=…)` (caller does not create a fresh attempt); if `overloaded(home)` (new helper reading `recovery/events/*.json` `host-pressure` or `Q>0.8·Qmax`/`CPU>0.9` from `recovery_io`) return similarly with `reason="backpressure OVERLOADED"`. Otherwise compute `prob←min(budget.B, 1-budget.fr)` and draw `random.random() < prob`; on `False` exhaust the budget decision without creating the directory. This is the `prob` line of Alg.1 (lines 13–14) — the only place randomness enters.

3. **Jittered exponential backoff before directory creation.** Wrap `fresh_attempt` (:489) call sites (caller in `runner.py`/`mind_loop.py`) with `delay = min(30.0, 0.1 * 2**(attempt_index) + random.uniform(-0.02, 0.02))` (100 ms base, capped, jitter ±20 ms — scaled to wake discipline, not the paper's RPS-scale 100/200/400 ms); the delay is a `time.sleep` or scheduled wake, not a new service. With `MISHE_NATIVE_RETRY_BUDGET=0` (default) the path is a no-op and `fresh_attempt`/`attempt_disposition` produce identical `Attempt`/`Disposition` bytes as today (backward-compatible replay of the last 3 `failure.txt` fixtures through `classify_attempt`).

4. **Emit `RAF` as evidence, not a new state word.** Extend `Attempt`/`Disposition` evidence tuple (the `tuple[str,...]` at `_evidence` :361 and `unseen_attempts` :847) with `raf=1.88` (single-tier at `p=fr`) or `raf_aggregate` for `d` recent distinct waking roles, computed `RAF= (1-fr^{n+1})/(1-fr)` when `0<fr<1`. `BLOCKED_STATE` verdict stays one of `SETTLED`/`RETRYABLE`/`RECONCILE`/`UNKNOWN` (:92–95); the budget/backpressure decision is `evidence`, preserving the ledger's vocabulary. Missing/stale pressure follows `UNKNOWN` when `overloaded()` is unreadable, matching `recovery_policy.transition` (:34) and `recovery_io.status` (:237).

**One thing this review does not ask for.** It does not propose changing `DEFAULT_RETRY_LIMIT` to an optimized MTTR, nor replacing PILOT rehearsal, circuit breakers, or load shedding. It only gates *when* the next bounded retry may spend the shared budget, using the RAF lens to make retries a system-level property — the complementary half to PILOT's "is this recovery correct?" question.
