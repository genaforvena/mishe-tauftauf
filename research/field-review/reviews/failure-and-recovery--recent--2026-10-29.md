## What we read

**Pilot Execution: Simulating Failure Recovery In Situ for Production Distributed Systems** — Zhenyu Li (Virginia), Angting Cai (UCSD), Chang Lou (Virginia). *23rd USENIX Symposium on Networked Systems Design and Implementation (NSDI '26)*, May 4–6, 2026, Renton, WA. 13 pp. (pp. 113–125 instrumented; refs to p. 125) — read full text at:

- <https://www.usenix.org/system/files/nsdi26-li-zhenyu.pdf> (PDF, 13,500 SLOC PILOT described, 75-incident study)
- <https://www.usenix.org/conference/nsdi26/presentation/li-zhenyu> (abstract page)

Four passages carry the change this plant has not made.

1. **Recovery failures are the failure mode — 75 incidents, 8 systems, 2010–2025 (§2, Table 2, p. 114).** 38% since 2019; 61% automatic (state recovery 25%, primary-backup failover 16%), 39% manual. Consequences: unavailability 41%, resource exhaustion 14%, data loss 13%, partial hang 12%, performance degradation 11%, inconsistency 9%. Root causes: state management 37%, error handling 28%, resource lifecycle 13%. The paper's point: recovery code is under-tested because "the complexity of writing and exercising tests for recovery paths" (p. 113, citing [46]) and a small mistake when the system is already vulnerable "can amplify failures instead" (HBase WAL-corruption → all RegionServers down, Fig. 1, p. 113; Azure DDoS filter misconfiguration → 10-hour Microsoft 365 outage; DynamoDB renewal → region outage).

2. **92% manifest beyond the local thread — and 63% were avoidable with a tweak (Findings 5–6, p. 114–115, Fig. 2).** Inter-thread 30% (HDFS-16115: faulty handler in one thread piles commands in another), inter-process 35% (KAFKA-10832: broker recovery corrupts producer), inter-service 27% (TiDB-963: Kubernetes scales TiKV on misinterpreted failure). §2.1 Finding 6: tolerating non-critical errors 19%, enforcing sequence 12% (RabbitMQ health check after election), rebalancing 18%, config tweak 14% — no complex strategy, just a different input or order, had the impact been visible before commit.

3. **Pilot execution vs speculative execution — the dry-run model (§3, Table 1, p. 114; §4, pp. 115–120).** Speculative execution assumes the future work is correct and contention is performance; pilot execution assumes recovery may be wrong and failure is the desired signal, aborts on contention to avoid perturbing production, and produces evidence (pass/fail, traces, metrics) not a candidate result. Design goals (p. 115): fidelity (same handlers/queues/RPCs so same timeouts/exceptions), safety (no mutation), observability (exceptions, resource curves, checker violations), performance (not delaying real recovery). Workflow (Fig. 3, p. 115): intercept at entry, send RPC marked as pilot, receiver spawns phantom thread, writes go to shadow HDFS copy visible only to pilot participants, failure signal observed, operator adjusts strategy before commit.

4. **How it is built — phantom threads, context propagation, shadowing (§4.2–4.4, Figs. 5–7).** Phantom threads are ephemeral in-process units that share address space read-only, registered under `/pilot-runs/<id>` with TTL/heartbeat cleanup, speculative locking that yields to production threads on conflict (aborts pilot rather than blocking live), cycle detection for feedback loops (Fig. 5, §4.2.1–4.2.3). Context propagation carries compact `PilotContext` (pilot ID, spanID, parentSpanID, timestamp) across thread/process/RPC boundaries, wrapping APIs and injecting headers, creating spans for an execution tree (Fig. 6, Fig. 8, §4.3; OpenTelemetry-based). Isolation via selective shadow fields: augment each field with `field$pilot`, shallow-copy on first access, redirect writes recursively; I/O wrappers (`Files$wrapper`, `ZooKeeperClient$wrapper`) redirect to pilot-scoped namespaces with lazy copy (directory structure first, data on read-after-write, Fig. 7, §4.4.1–4.4.2). Observation (§4.5) replaces `Runtime.halt()` with `PilotUtil.report(e)`, streams anomalies to `observe()` and materializes the caller–callee tree on failure. Warmup/memoization (§4.6) caches transferred state and pure-function results during pilot so real recovery reuses them after checksum validation. Static transformation via Soot (Java) automates entry identification, hook injection and `f() → f$pilot()` generation (Fig. 9, §4.7).

**Evaluation the source claims and this review keeps.** Five systems (Solr, HDFS, Cassandra, HBase, YARN; Table 4, p. 120, 122K–1220K LOC, 12–60 entry points, 313–1191 context hooks): 17/20 severe recovery failures uncovered, one unknown HBase bug found, +17.63% delay on recoveries >10 s (p. 120–122). Limits the source states: targets propagation/amplification failures; less effective for purely local bugs, long accumulative drift, or semantic violations without checkers (§3, p. 115); manual header injection needed for custom RPCs (41 lines Cassandra, 89 HBase, 50 Hadoop).

**Why this literature, for this cell.** The field already has no recent reading (the grid shows 0/6 for failure-and-recovery). The plant's own recovery literature is 1970s–2000s face-to-face: Chandra–Toueg repentance, Gray & Cheriton leases, Hayashibara ϕ — all about *detection*. Pilot execution is about what happens *after* detection fires: the recovery that itself fails and needs a reversible, observable rehearsal.

## What this plant already does

*Bounded, classified retry with a durable ledger — but no rehearsal.* `src/mishe_tauftauf/native_recovery.py` classifies one failed wake from its own bytes: `classify_attempt()` reads `summary.json`, journal rows and three ledger journals (`_read_evidence` :278, `_journal_effect_rows` :354), checks completeness of `failure.txt` (`_failure_record` :200) and decides `SETTLED`/`RETRYABLE`/`RECONCILE`/`UNKNOWN` (:92–95) with `TRANSIENT_STATUS = {408,429} U [500,599]` (:99) and `DEFAULT_RETRY_LIMIT=3` (:100). `fresh_attempt()` returns the next unused `attempt-N/` directory or `None` at the limit (:489–502). `attempt_disposition()` chooses the bounded next action for one wake from its attempt report sequence (:568–622). Evidence is the attempt's own `effects/` ledger, `failure.txt` traceback, and the `BLOCKED_STATE` record `{role}-native.blocked.json` that makes a wedged resident observable without reading an attempt dir (:641–647). `recovery_io.py` and `recovery_policy.py` do the same for host-pressure incidents: `transition()` samples `host_pressure`/`guard freshness`/:253, requests backup at deadline, requires explicit `accept` (:52), latches `limited` until `recover_seconds` of clear samples (:58–77). `docs/recovery.md` is explicit: an incident belongs to the failing *function*, its probe must pass repeatedly across the stability interval, `MITIGATED` is not closed, missing/stale stays visible, and "Never replay an unknown mutation or remove a live lock to clear an alert" (:122–123). Snapshots + exact-byte `revert` and `guard-activation/apply.py` give a tested revert path for *containment* (:140–146) — but there is no equivalent dry-run for a *wake* recovery.

*No phantom, no shadow, no tree.* The plant's recovery executes live: `runner.py` compares `MISHE_NATIVE_RECOVERY_WAKE == pending_wake`, `native_recovery.clear_blocked_state()` and `fresh_attempt` create the next attempt directory and run it for real. There is no `PilotContext`, no `f$pilot` wrapper, no redirected `Files$wrapper`/`ZooKeeperClient$wrapper`, no speculative lock that aborts on contention, no cross-thread/process span tree (cf. PILOT Fig. 8, Fig. 9). The checker `checks/native-recovery-optin.py` verifies only that an opt-in names the exact pending wake — that the wake is the right one, not that its recovery is safe. The consequence is the one the study measures: when a retry fails it fails live, and because 92% of the paper's failures propagated inter-thread/process/service, a live failure can pile commands in another thread, corrupt a producer or trigger Kubernetes scaling before the operator learns it was the wrong recovery.

*Workarounds that are already pilot-like in spirit.* The operator's `retained pane` (`artifacts/operator-model-restart-20261029-1550/field-review.before.txt` cited in this wake's trigger) and the `--dry-run` idiom the paper names for Git (p. 114) are the same intuition — preview before commit — but they are manual and post-hoc. The `ledger-band-second-reader.py` check verifies a reading can be recomputed from published fields alone; PILOT verifies a recovery can be observed from a rehearsed execution alone.

## What is new here

**The plant rehearses the wrong thing, or not at all.** Today `attempt_disposition` decides "retryable with no effect" by counting `proposal`/`tool_result` rows (`_journal_effect_rows` :354) and checking the terminal failure is transient (:268–275). That is a static count of what the *last* attempt did. PILOT decides by *running the next* recovery once, on phantom threads, through the same handlers, and reporting whether that run would have propagated. Three ideas transfer directly, each with a line number in this repository where it would land.

1. **Phantom-thread rehearsal is the missing complement to fresh-attempt.** Finding 6's 63% "avoidable with a tweak" maps to the plant's `fresh_attempt` + `attempt_disposition` loop: the tweak is a different `range`/`keyspace`/`table` (Cassandra Fig. 4), a different backoff, a reordered `health check after election`. The plant never tries the tweak first in a sandbox; it commits it as the next `attempt-N/`. A PILOT-style `pilot_attempt(entry, policy)` beside `fresh_attempt` (:489) would spawn the next attempt's code path as a phantom: read-only share of `effects/`, shadow ledger writes visible only to pilot participants, `Runtime.halt` replaced by `report(e)` (PILOT Fig. 7, lines 22–23), speculative locks that abort rather than block the live holder (§4.2.2). PILOT's cycle detection and TTL cleanup (§4.2.3) answer the plant's own concern about orphaned transient scopes — which the containment slice already kills but without a per-run registry like `/pilot-runs/<id>`.

2. **Context propagation is the mechanism the plant's cross-component failures need.** The study's 92% inter-thread/process/service figure is not an abstract risk here: a wake retry can emit a ledger row, a chat append, and a wall write that other roles' probes (`wall.tick` 30 s, `_leases` 20 s, `site_sync._leases`) then read. PILOT's `PilotContext` (`pilot ID`, `spanID`, `parentSpanID`) propagated via thread-local + RPC header injection (§4.3, Fig. 6) is the way to keep the rehearsal in pilot mode across `cli.py → wall.py → site_sync.py → discovery.py` without forking the whole plant (which the paper rejects as heavyweight, §4.2). The plant's thread pools and async callbacks (§4.3: "the non-obvious part is doing this transparently in systems that heavily use thread pools") are present in `inference_worker.py`, `mind_loop.py` and tmux capture — the exact place PILOT's wrapping is needed.

3. **Shadow state + I/O redirection make "observable without mutating" precise.** The doctrine "No fix without causal investigation … Preserve the original failure evidence" (AGENTS.md) is enforced for *evidence* by the ledger journals; it is not enforced for *effects*. PILOT's selective `field$pilot` shallow copy and `Files$wrapper` lazy copy (Fig. 7, §4.4) give a pattern: first access shallow-copies the ledger store handle, subsequent writes redirect to `attempt-N.pilot/` or `recovery/pilot/<id>/`, reads inside the pilot see the shadow, production sees the original. The `controller_lock` in `recovery_io.py:196` and `.ledger.lock` in `native_recovery.py:109` already exist as the locks a speculative wrapper must yield on (§4.2.2 scenario 2: phantom held → original acquires → phantom releases and aborts).

4. **The execution tree is the report the operator does not have.** §4.5's `observe(RunId, sink)` / `report(RunId)` streaming spans, exceptions, timeouts and resource curves into a caller–callee tree (Fig. 8) is what the plant's `DELIVERY` outbox and `pressure-*.json` approximate but not per-recovery. Today a `BLOCKED_STATE` carries `verdict`/`reason`/`evidence` strings (:659–661); PILOT's tree carries the *path* `execute → processDeadServer → splitWALs → recoverLease → nodeChildren` that failed (Fig. 8). That is the difference between "retryable-no-effect" and "retryable-no-effect because `nodeChildren` on RS1 timed out after 10 s, which would have propagated to RS2".

**Limits the proposal keeps from the source.** PILOT is not a correctness proof; it "is less effective for purely local bugs, long-term accumulative issues … or semantic violations not covered by built-in checkers" (§3). Phantom threads trade completeness for safety: high contention causes timeout false positives (p. 118) — the right trade for this plant where blocking a live holder is worse than incompleteness. The Soot/Java automation does not apply here; the plant would instrument Python wrappers manually (the paper's 41/89/50 lines for custom RPCs, §6.1, is the cost model). Warmup memoization (§4.6) assumes deterministic pure functions — ledger `capabilities` calls with external side effects are not memoizable without the `checksum` validation the paper requires.

## Application

target: src/mishe_tauftauf/native_recovery.py

**Add a pilot dry-run beside fresh-attempt — additive, behind a flag, same evidence vocabulary.**

1. **Add `pilot_attempt()` and `pilot_report()` beside `fresh_attempt()`/`attempt_disposition()`** in `src/mishe_tauftauf/native_recovery.py` (:489, :568). `pilot_attempt(attempts: Path, wake: int, *, entry: Callable, policy: dict) -> RunId` creates a shadow attempt directory `attempt-N.pilot/` (never counted by `wake_attempts` :809 or `_wake_directories` :772), registers it under a lightweight `pilot-runs/<id>` registry (in-memory or `SITE_HOME/recovery/pilot-runs/<id>.json` with TTL, mirroring PILOT's `/pilot-runs/<id>` :119), and runs `entry$pilot` on a phantom thread. The `$pilot` wrapper is a shallow-copy shim: first field access copies `effects/` handles to `effects.pilot/`, all `save()`/`event()`/`append chat` calls redirect to the shadow prefix, `controller_lock`/`STORE_LOCK` acquire speculatively (yield-and-abort on contention, §4.2.2), and `Runtime.halt`/`sys.exit` inside the pilot becomes `report(e)`. `pilot_report(run_id) -> dict` materializes the span tree (caller–callee via a `PilotContext` thread-local + header propagation, §4.3) and the summary ` {status: "FAILED"|"PASSED"|"ABORTED", spans: [...], exceptions: [...], resource: {...}}` that `observe()` streamed.

2. **Wire it as a dry-run before `fresh_attempt` is committed.** The caller that today does `fresh = fresh_attempt(dir, wake); if fresh: run(fresh)` first does `run_id = pilot_attempt(dir, wake, entry=run, policy={"time_budget": 10, "max_phantom_threads": 8})` and `report = pilot_report(run_id)`. If `report["status"] == "FAILED"` the caller surfaces `report` in the `BLOCKED_STATE`'s `evidence` tuple (same `tuple[str,...]` that `_evidence` :361 and `unseen_attempts` :847 already use) and does **not** create `attempt-N/` — the operator adjusts inputs (different capability args, ordering, or backoff — Finding 6) and starts a new pilot. If `PASSED`, the caller proceeds to `fresh_attempt` and the warmup cache (§4.6) reuses any side-effect-free `run_probe`-like computations after checksum validation. A CLI/env flag `MISHE_NATIVE_PILOT=1` (beside `MISHE_NATIVE_RECOVERY_WAKE` checked in `checks/native-recovery-optin.py:12`) enables the gate; without it behavior is unchanged.

3. **Reuse the plant's existing vocabulary.** The report's `status` maps to the four verdicts already in the file (`SETTLED`/`RETRYABLE`/`RECONCILE`/`UNKNOWN` :92–95) plus `ABORTED` for contention/timeout. The `BLOCKED_STATE` `verdict` remains one of those four; the pilot report is `evidence`, not a new state word. Missing/stale/unknown handling follows `recovery_policy.transition`'s `UNKNOWN` when `result is None` (:34) and `recovery_io.status`'s `UNKNOWN` on unreadable inputs (:237).

4. **Instrument only the recovery entry points PILOT names (§4.7, Fig. 4, Fig. 9).** Passive: `try/except` handlers that classify transient failures (`_transient` :267) and `blocked_state` writers (`write_blocked_state` :659). Proactive: `fresh_attempt` call sites in `runner.py`/`mind_loop.py`. Five wrapper types (§4.3, Appendix B.3) are enough: thread spawn, RPC/chat append, shared ledger variables, queue submit, and `Files`-like ledger I/O. No fork, no container, no model change.

**Acceptance (deterministic, runnable from this repository).**

* Existing `tests/test_native_recovery.py`-equivalent checks (if any) and `python tools/check_parsing.py` stay green — `native_recovery.py` is not a boundary file in `parsing-policy.json`, and `pilot_attempt` is additive (no change to `classify_attempt`/`attempt_disposition`/`fresh_attempt` signatures).
* With `MISHE_NATIVE_PILOT=0` (default) the next `attempt_disposition`/`fresh_attempt` sequence for a known `wake` produces the same `Attempt`/`Disposition` bytes as before (replay the last 3 `failure.txt` + journal fixtures, if present, through `classify_attempt`).
* With `MISHE_NATIVE_PILOT=1` and a synthetic `entry` that would `halt` and touch `attempt-N/effects/ledger.jsonl`, `pilot_attempt`+`pilot_report` returns `FAILED` with a span tree containing the halt site, `attempt-N/effects/ledger.jsonl` is unchanged, `attempt-N.pilot/` holds the shadow writes visible only to the pilot, and no `attempt-N/` is created. A second pilot with a tweaked entry `entry` (e.g., tolerating that error, Finding 6) returns `PASSED`, after which `fresh_attempt` creates `attempt-N/` and the shadow `ledger.jsonl` checksums are reused.
* High-contention case: holding `STORE_LOCK` in the main thread while `pilot_attempt` runs aborts the pilot with `ABORTED`/timeout and leaves the store untouched (speculative-lock scenario 2, §4.2.2) — the pilot is incomplete but safe, and the live holder is not blocked.

**Ownership.** `src/mishe_tauftauf/native_recovery.py` is the bounded fresh-wake recovery discipline and is consumed by the `health`/`genome` life-support slice; `health` is the resolver for `native recovery, health, supervisors, watchdogs` (field `failure-and-recovery`'s `plant_part`) and for substrate `UNKNOWN` delivery gaps, and owns `recovery_io`'s probe/pressure sampling that the pilot's `resource` curve reports to. The `MISHE_NATIVE_RECOVERY_WAKE` opt-in is checked in `checks/native-recovery-optin.py` — the pilot flag lives beside it.

**One thing this review does not ask for.** It does not propose changing retry limit, queue discipline, or commit policy to *minimize* mean time to recovery, and does not propose a non-linear penalty or estimator cost for recovery duration — those are optimization (§VI of Yates is analogous) once the rehearsal exists. This review only publishes the dry-run the optimization would need, in the module that already defines what "retryable" means.
