# Coordination, delivery and release — mechanism: Kubernetes Deployment as a declarative rollout with bounded surge, readiness gating, deadline, and available/progressing conditions

## What we read

- Kubernetes Documentation, "Deployments" (`concepts/workloads/controllers/deployment`). Source read: https://kubernetes.io/docs/concepts/workloads/controllers/deployment/ (fetched 2026-11-02; HTML 594849 B saved as /tmp/k8s-deployment.html; text-extracted locally). The page is the reference for the Deployment controller, ReplicaSets, Pod template, strategy, progress and readiness gates, and status conditions.
- Passages read directly (quoted after tag-stripping; section names original):
  - Definition: "A Deployment manages a set of Pods to run an application workload, usually one that doesn't maintain state. A Deployment provides declarative updates for Pods and ReplicaSets. You describe a desired state in a Deployment, and the Deployment Controller changes the actual state to the desired state at a controlled rate."
  - Strategy: `StrategyType: RollingUpdate` with `RollingUpdateStrategy: 25% max unavailable, 25% max surge` and invariant "availableReplicas … must be between replicas - maxUnavailable and replicas + maxSurge" (note: "Kubernetes doesn't count terminating Pods when calculating the number of availableReplicas").
  - Readiness gating: `MinReadySeconds`, readiness probes, `Terminating Pods`, and condition `Available True / MinimumReplicasAvailable` vs to-be-available.
  - Progress guard: "`spec.progressDeadlineSeconds` denotes the number of seconds the Deployment controller waits before indicating (in the Deployment status) that the Deployment progress has stalled" — queried via `kubectl describe deployments` as `Progressing True NewReplicaSetAvailable` vs `Progressing False ProgressDeadlineExceeded`.
  - Status model: `Replicas: 3 desired | 3 updated | 3 total | 3 available | 0 unavailable` with `Conditions: Available / Progressing` (and later `ReplicaFailure`), separate from the spec.
  - Revision and control: `RevisionHistoryLimit`, `Paused` (pause/resume rollout), `Rolling Back a Deployment` / `Rolling Back to a Previous Revision`, `Rollover (aka multiple updates in-flight)`, and `Canary deployments` cross-reference.
  - Lifecycle note: each new Deployment observation creates a ReplicaSet; the controller scales new vs old ReplicaSets incrementally rather than flipping atomically.
- Not read: the full `kubectl` walkthrough, the API reference (`apps/v1 Deployment` spec tables), Horizontal Pod Autoscaler interaction, and the excluded `StatefulSet`/`DaemonSet` pages linked from the sidebar. This review does not rely on them.

## What is new here

The Deployment is not "deploy the binary" — it is a *declarative* desired state (`spec.template` + `replicas` + `strategy`) continuously reconciled by a controller that scales ReplicaSets, bounded on both sides (`replicas - maxUnavailable <= availableReplicas <= replicas + maxSurge`), gated by readiness (`readinessProbe` true for `minReadySeconds` before counting as available), guarded by `progressDeadlineSeconds` (after N seconds with no progressing, status becomes `Progressing=False Reason=ProgressDeadlineExceeded`), and reported as two orthogonal conditions (`Available` and `Progressing`, plus `ReplicaFailure`), not one binary. Revision history (`revisionHistoryLimit`) is retained so rollback is `roll back to a previous ReplicaSet`, not "re-apply old files". `Paused` lets the declaration accumulate without reconciling. `Rollover` names multiple desired states in flight where only the latest matters.

Transfer: candidate SHA = desired state (the Deployment `spec`); the release artifact / rollout record = the ReplicaSet revision; consumers (linked sites, operator view, health) = Pods/Replicas; `maxUnavailable` = how many consumers may lag head at once; `maxSurge` = how much extra rollout work (duplicate activation, extra hosts) the controller may spend during convergence; `minReadySeconds` = stability before a consumer that transiently reports head counts as `Available`; `progressDeadlineSeconds` = bounded wait before a non-converging declaration is `Failed` rather than forever `Progressing`/`HOLD`; `Available`/`Progressing`/`ReplicaFailure` = why `line()` should say `progressing` vs `available` vs `failed` vs today's undifferentiated `HOLD`.

This differs from both prior transfer REVISITs (Saltzer end-to-end acknowledgement provenance; BIS DvP iff linkage) and from the discarded canary: canary needs a control population to compare a subset against; Deployment needs a *desired state* to converge toward and bounds on how far actual may stray while converging.
