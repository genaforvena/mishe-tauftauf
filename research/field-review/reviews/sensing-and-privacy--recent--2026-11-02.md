## What we read

Companion sources read for the normative boundary (not the primary result):

- <https://www.rfc-editor.org/rfc/rfc9724.pdf> — RFC 9724 "State of Affairs for Randomized and Changing MAC Addresses" (Informational, Mar 2025), the inventory RFC that RFC 9797 updates in analysis; §6 use-case/pii framing shared.
- <https://standards.ieee.org/ieee/802.11bh/10525/> — IEEE Std 802.11bh-2024 "Operation with Randomized and Changing MAC Addresses" (published 2025-06-03, DOI 10.1109/IEEESTD.2025.11023005), the 802.11 amendment that standardises RCM procedure on the air interface (cited as [IEEE_802.11bh] in RFC 9797 §9, Appendix A).

Four passages carry the privacy boundary this plant lacks as explicit, testable text.

1. **A MAC address was never an identity, but became one — PII vs PCI (§2–2.1).** The globally-unique MAC existed to avoid collisions on a wired LAN ([IEEE_802] §8.4, U/L bit distinguishes universal/local). With mobility and Wi-Fi broadcast (§1), "identifying the device is trivial if it has a unique MAC … detecting any elements that directly or indirectly identify the user … (PII) is enough to link the MAC … then any … traffic … will also be linked … (PCI)" (§2, ¶5). For most 802.11 exchanges "source and destination MAC addresses are not encrypted even in networks that implement encryption" (§2.1) so any protocol-compatible OTA device can read them before decryption. The remedy is a locally-administered (U/L=1) address "change[d] in a fashion that prevents a continuous association between one MAC address and some PII" — but that breaks any peer that assumed a persistent MAC (AAA, DHCP, ARP/NDP caches, L2 bridge port learning).

2. **Who can see a MAC, and where the boundary is (§3.1–3.2).** §3 enumerates functional entities (AP/controller, L2 switches/bridges, IP routers, ARP/NDP, 802.1X/AAA) and human-related observers: OTA observers (any sniffer in range, OTA ranging/positioning available, §3.2.1), wireless access network operators, network access providers (lawful intercept, §3.2.3), over-the-wired internal (OTWi) observers inside the broadcast domain, and OTWe beyond routing (headers stripped). An OTWi observer "supposes … physical access to … the broadcast domain" while OTA requires only proximity — the two threat surfaces are different, and randomising the MAC helps only OTA/OTWi while underlay identifiers copied to upper fields (e.g. IPv6 IID pre-RFC 8981/7217, §3.2.5) still leak.

3. **Personal vs Shared-Service device, and three degrees of trust (§2 p.6, §4).** RFC 9724/9797 adopt [IEEE_802E] §6.2: a *Shared Service Device* (AP, switch, barcode scanner) cannot be linked to one person; a *Personal Device* can. Trust is not binary (§4): *Full trust* (share persistent MAC with the access network, assume L2 secrecy inside broadcast domain), *Selective trust* (per-SSID/BSSID/time/policy pseudo-persistent MACs), *Zero trust* (temporary per-service MAC, nothing long-lived). The trust choice "depends on (1) environment, (2) presence/nature of other devices, (3) network type" — i.e. on context, not on the address alone.

4. **Five environments and eight service breakages (§5–6.1, Table 1).** Environments A residential (Full, Simple), B managed residential (Selective), C public guest (Zero, Simple — "every time it attaches to a new AP"), D BYOD enterprise (Selective, Complex/High-support), E managed enterprise (Full, Complex). §6.1 then enumerates failures when RCM rotates without coordination: AP/controller session context (keys, QoS, capability) rebuilt; L2 MAC-port table exhaustion (Linux default 300 s, "Aggressive randomization … <300 s may cause … unintentional DoS"); AAA/802.1X port-blocking; DHCP scope exhaustion (release held for returning MAC); SLAAC/Optimistic DAD/NDP stale bindings; router ARP/NDP cache churn; parental/policy filters and IoT ranging keyed on MAC; IT-support identifiability. Appendix A lists frameworks that keep privacy without losing service: 802.1X/WPA2/3 mutual authentication (enterprise), OpenRoaming federation, proprietary per-SSID RCM — all using an upper-layer identity instead of the MAC.

**Limits the source states, kept here.** RFC 9797 is Informational, not Standards-Track; it recommends no mandatory rotation interval and does not define a sensing or location API. It assumes the device randomises its *own* MAC per OS policy — the document does not authorise a network or peer to link others' RCM addresses, nor to scan OTA MACs at scale. RCM "becomes harder" only "assuming no other visible unique identifiers or stable patterns are in use" (§1) — stable IEs, sequence numbers, or protocol fingerprints still re-identify despite U/L=1. 802.11bh is cited, not reproduced.

## What this plant already does

*The plant's wireless sense is a host-state decoder, not an OTA MAC observer; it has no RCM linking, no OTA sniff, and no broadcast-domain tap.*

- **Privacy vocabulary exists only for these host rows.** The keyword sweep (`sense`, `radio`, `privacy`) confirms usage only in host-state rows and docs; no occurrence of `RCM`, `randomi`, `U/L`, `PII`/`PCI`, `OTA observer`, or `802.11bh` exists in the tracked tree pre-review (`rg` 0 hits for `RCM|802\.11bh` in `src/`). ## What is new here

**Name Randomized and Changing MACs (RCM) as the concrete recent IETF/802.11 privacy boundary the host-radio decoder must be measured against, and make the plant's refusal to link RCM addresses a typed, testable fact in `host_radio.py`.**

RFC 9797 §1–6 turns an incidental property of Wi-Fi (plaintext MAC in every frame) into a named, standard-track privacy mechanism — and then catalogues why naïvely assuming "the MAC is the device" now breaks. For a host that only wants to know whether its own radios are up, the relevant distinction is *reading my adapters* (sysfs `wireless`/`operstate`/`flags`/`rfkill`, one `bluetoothctl show`) versus *reading others' adapters* (OTA/OTWi MAC observation, §3.2.1/3.2.4) and then *linking two randomised addresses to one device*. The RFC makes the second step explicit: linkability via stable IEs, sequence-number or timing fingerprints, or retention of a MAC-keyed AAA/DHCP/ARP cache all survive U/L=1 if the observer correlates. 802.11bh standardises the rotation; RFC 9797 names the personal-vs-shared distinction, the three trust degrees, and the five environments (Table 1) that determine whether rotation helps or hurts.

For this plant the transfer is negative: `host_radio` does not implement OTA MAC capture, does not store a peer MAC, does not attempt to re-correlate an RCM rotation, does not treat a MAC address as PII/PCI, does not parse probe/association IEs, and does not use a MAC-keyed cache to track a device across rotations. Framing it as a bearing from RFC 9797 §§2–3/Fig.1 vocabulary makes future drift checkable: any import of a packet sniffer, any neighbour-table parser, any `iw dev scan` call, or any dictionary keyed by peer MAC is a privacy-boundary change that must be reviewed under `docs/protocol-boundaries.md` and `docs/how-it-works.md:973`.

The metric the review applies is binary and local: the module's RCM-linking capability is `False`, and the repository's OTA-MAC vocabulary footprint is zero — the same style as `WLAN_SENSING_SUPPORTED = False` and the `AoI` warmup-None. A checks reporter can re-plug the same constant without the producer learning to sniff.
