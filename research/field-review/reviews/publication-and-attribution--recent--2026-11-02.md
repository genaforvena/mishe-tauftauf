Six passages carry the recent mechanism, each with its stated limits kept.

1. **What artifact attestations are — unfalsifiable provenance via Sigstore (Blog 2024-05-02 intro + Docs concept p.1).** Blog: "Generate and verify signed attestations for anything you make with GitHub Actions." Docs: "Artifact attestations enable you to create unfalsifiable provenance and integrity guarantees for the software you build. … you create cryptographically signed claims that establish your build's provenance" including "a link to the workflow … repository, organization, environment, commit SHA, and triggering event … [and] other information from the OIDC token." Primary predicate is `https://slsa.dev/provenance/v1` (SLSA Build provenance) via in-toto Statement; SBOM variant uses `https://spdx.dev/Document/v2.3` or CycloneDX. Limit kept: attestation ≠ artifact security — Docs Warning box: "artifact attestations are not a guarantee that an artifact is secure. Instead, artifact attestations link you to the source code and the build instructions that produced them. It is up to you to define your policy criteria …" — provenance judges binding, consumer judges meaning.

2. **How GitHub generates — Sigstore keyless + Fulcio + Rekor, with public vs private split (Docs concept "How GitHub generates" + Sigstore cosign overview).** Docs: "To generate artifact attestations, GitHub uses Sigstore … Public repositories … use the Sigstore Public Good Instance. A copy of the generated Sigstore bundle is stored with GitHub and is also written to an immutable transparency log that is publicly readable. Private repositories … use GitHub's Sigstore instance. … does not have a transparency log and only federates with GitHub Actions." Sigstore: keyless signing "associates identities, rather than keys, with an artifact signature. Fulcio issues short-lived certificates binding an ephemeral key to an OpenID Connect identity. Signing events are logged in Rekor, a signature transparency log." Fulcio certs valid 10 minutes, audited by CT log. Limit kept: private-instance attestations are not publicly log-auditable; OIDC identity is federated only with GitHub Actions, not with general OIDC.

3. **Generating for binaries vs containers — `actions/attest@v4`, permissions, subject-path vs subject-name+digest (Docs how-to "Generating artifact attestations for your builds").** For binaries: `permissions: id-token: write, contents: read, attestations: write` + `uses: actions/attest@v4 with: subject-path: 'PATH/TO/ARTIFACT'`. For container images: same plus `packages: write` + `subject-name: ghcr.io/ORG/IMAGE, subject-digest: sha256:HEX, push-to-registry: true` (digest from `docker/build-push-action` output). SBOM variant adds `sbom-path: 'PATH/TO/SBOM'` alongside subject. Limit kept: `subject-path` is local file path at build time; `subject-name` must be FQDN without tag; `push-to-registry: true` creates storage record for linked-artifacts page — none of this exists for markdown/DEV prose artifacts.

4. **SLSA level the mechanism actually achieves — L2 alone, L3 only via reusable workflow isolation (Docs concept "SLSA levels for artifact attestations").** Docs: "Artifact attestations by itself provides SLSA v1.0 Build Level 2." Level 2 = provenance exists + authentic + hosted platform signed. "This provides a link between your artifact and its build instructions, but you can take this a step further by requiring builds make use of known, vetted build instructions. … Reusable workflows can provide isolation between the build process and the calling workflow, to meet SLSA v1.0 Build Level 3." Limit kept: reusable workflow is the isolation mechanism, not attest itself; without it, `L2` is ceiling regardless of signing.

5. **Verifying — `gh attestation verify` for binaries and `oci://` for images, `--predicate-type` + `--format json --jq` for SBOM, offline variant (Docs how-to "Verifying artifact attestations").** Binaries: `gh attestation verify PATH/TO/BINARY -R ORG/REPO` (assumes online). Containers: `gh attestation verify oci://ghcr.io/ORG/IMAGE:tag -R ORG/REPO`. SBOM: add `--predicate-type https://spdx.dev/Document/v2.3` (or CycloneDX). Inspect: `--format json --jq '.[].verificationResult.statement.predicate'` for predicate payload. Offline/air-gapped: separate `verify-attestations-offline` page (fetch Sigstore bundle, no `gh` network). Limit kept: verification requires org/repo as trust anchor (`-R`) and online fetch by default; `--predicate-type` is required for non-default predicates — bare verify without it checks only SLSA provenance.

6. **What to sign and what not to — attestation-shaped artifacts only (Docs concept "When to generate attestations").** Docs: You should sign "Software you are releasing that you expect people to run `gh attestation verify ...` on. Binaries people will run, packages people will download, or manifests that include hashes of detailed contents." You should not sign "Frequent builds that are just for automated testing. Individual files like source code, documentation files, or embedded images." Attestations remain revocable/manageable via lifecycle docs (delete when obsolete). Limit kept: chat tape text, DEV markdown, wall outcomes are not credential-shaped build artifacts — the plant's tape is a journal, not a binary to be attested per-se; the mechanism applies to built outputs, not to prose.

## What is new here

**Artifact Attestations reframes the plant's `CI: PASS sha=...` and `hard-binding=sha256` from "badge + hash" to a closed, keyless, log-auditable attestation mechanism that names the workflow, repo, commit, OIDC identity and predicate type — so a CI observation without a Sigstore bundle, or a bundle without a reusable workflow, is visibly below the claimed SLSA level rather than a neutral PASS.**

Five ideas transfer directly, each bounded by what GitHub/Sigstore concede.

1. **Predicate types beyond SLSA — `slsa/provenance` default vs `spdx`/`cyclonedx` for SBOM (Docs how-to SBOM + SLSA attestation model).** Today `SLSA_PREDICATE_TYPE` names only `https://slsa.dev/provenance/v1`. The transfer adds `GITHUB_ATTESTATION_PREDICATES: Final = ("https://slsa.dev/provenance/v1","https://spdx.dev/Document/v2.3","https://cyclonedx.org/bom")` as the closed attestation-predicate vocabulary, with pure `predicate_is_valid` gate so a verify without `--predicate-type` that claims SBOM provenance is visibly incomplete. Limit kept: the predicate name does not imply the SBOM is accurate — only that this bundle claims that predicate type, per Docs `Warning` box.

2. **Subject kinds `subject-path` vs `subject-name+digest` and the "what to sign" boundary (Docs how-to binaries vs containers + "When to generate").** Binary attestations use local `subject-path`; container attestations use `subject-name` (FQDN without tag) + `subject-digest` (`sha256:HEX`) + `push-to-registry`. The transfer makes `ATTESTATION_SUBJECT_KINDS = ("binary-path","container-oci")` and a typed `subject_address_is_valid(kind, address)` predicate (path vs `oci://`+`ghcr.io/...:tag` excluded, `sha256:hex64` required for container), plus the typed advice that test-frequency builds and individual source/doc files are not `attest`-shaped — the Vocabulary is the detector (the plant's tape text and DEV markdown are not attestable as binaries, but a built wheel or image is). No `Feed.append` is attested in this commit.

3. **Keyless identity and transparency log as the builder identity concretion — Fulcio 10-minute cert + Rekor log, public vs private split (Docs concept "How GitHub generates" + Sigstore overview/Fulcio).** The plant's `builder.id` today is a transitive-closure string with no Issuer. The transfer adds `SIGSTORE_INSTANCES = ("public-good","github-instance")` and `ATTESTATION_LOG_STATES = ("logged","not-logged")` so that `public repo → Public Good Instance + Rekor logged (auditable)`, `private repo → GitHub Sigstore instance + not logged (federated only with Actions)` is a typed fact beside `SLSA_ISOLATION_LEVELS`. Fulcio's "X.509 certificates valid for 10 minutes" and OIDC (`github actions` token) are kept verbatim as the short-lived identity source. The transfer does not claim a log entry exists — only the instance/log word the predicate implies.

4. **SLSA level concretion for this ecosystem — attestations alone = L2, reusable workflow = L3 (Docs concept "SLSA levels for artifact attestations" + SLSA levels p.1–2).** Prior `ci_watch.py` maps `L0→L3` from `provenance_state + hosted + isolated + builder_id`; Docs makes the concretion testable: any valid attestation bundle from `actions/attest` on hosted GH Actions satisfies `≥L2`; `L3` requires `build ran in reusable workflow providing isolation between caller and build` (Docs exact requirement). The transfer exposes `slsa_level_for_github_attestation(is_logged: bool, is_reusable: bool, builder_hosted: bool) -> str` pure table that returns `L1` without bundle, `L2` with bundle+hosted, `L3` with bundle+hosted+reusable — the `--reusable` word is the Isolation boundary. Limit kept: Docs lists `L3` as "many repositories share the same vetted workflow" — the type is the guard, not proof the workflow is vetted.

5. **Verification dialect `gh attestation verify ... -R ORG/REPO` and the SBOM/inspect split (Docs how-to "Verifying artifact attestations" + next-steps).** The plant's verification is `state==pass`; the ecosystem's is `gh attestation verify PATH -R ORG/REPO` (binary), `gh attestation verify oci://ghcr.io/ORG/IMAGE:tag -R ORG/REPO` (container), with `--predicate-type https://spdx.dev/Document/v2.3` for SBOM and `--format json --jq '.[].verificationResult.statement.predicate'` to show the predicate payload, plus `verify-attestations-offline` for air-gapped. The transfer adds `ATTESTATION_VERIFY_SUBCOMMAND = "gh attestation verify"` and typed helpers `gh_attestation_verify_args_is_valid(subject, repo) -> bool` and `predicate_flag_for(predicate: str) -> str | None` (returns `--predicate-type` only when non-default), and documents the `Warning` that provenance ≠ security — consumer must evaluate workflow/commit content before trusting bundle.

**Limits the proposal keeps from the source.** No `actions/attest@v4` step is added to any workflow, no DSSE bundle is generated or stored, no Sigstore/Fulcio/Rekor fetch is performed, no `GITHUB_TOKEN`/`id-token`/`attestations: write` permission is requested, no built artifact is produced or distributed, no trust-anchor list or offline bundle fetch is implemented, no `Feed.append`/`seed yield`/`wall`/`delivery._push` mutation, no new `SENSE_ID` row, no `WALL_MAX_*` change, and no claim that an `L2`/`L3` bundle proves depicted facts are true (Docs `Warning` kept). The vocabulary is pure predicate over caller-held strings/dicts, import-safe without site home, clock, or network — exactly the SLSA spec's "L1 trivial-to-bypass" and the Docs "generating alone … benefit … not realized [without verification]" caveats.
