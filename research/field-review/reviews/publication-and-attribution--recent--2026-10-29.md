## What we read

Coalition for Content Provenance and Authenticity (C2PA) — **"Content Credentials: C2PA Technical Specification 2.2"**, 2025-05-01, 248 pp. — read full specification at:

- <https://spec.c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html> (HTML, Antora, fetched 200 2026-10-29, canonical link to 2.5)
- <https://spec.c2pa.org/specifications/specifications/2.2/specs/_attachments/C2PA_Specification.pdf> (PDF, fetched 200 2026-10-29, 7,078,733 bytes, 248 pp., Asciidoctor PDF 2.3.19, pdftotext 12,617 lines, CreationDate 2025-06-22T15:36:45Z, ModDate 2025-06-22T15:36:43Z)

The specification is the world's first open industry standard for content provenance (founded Feb 2021, now 500+ members per C2PA). Version 2.2 is dated 2025-05-01; version 2.5 is canonical HEAD but the 2.2 PDF is the pinned reading artifact for this review. Citations below pin chapter/section and page in the 2.2 PDF where pagination is stable; the HTML carries the same normative text.

Six passages carry the transferable mechanism, each with its stated limits kept.

1. **Guiding principles — no value judgment, privacy by control (Ch. 1 p.2–3, Guiding Principles "IMPORTANT" box p.2).** `C2PA specifications SHOULD NOT provide value judgments about whether a given set of provenance data is 'good' or 'bad,' merely whether the assertions included within can be validated as associated with the underlying asset, correctly formed, and free from tampering.` The spec is designed for global opt-in with a rich ecosystem of provenance-enabled apps `while meeting appropriate security requirements` (Ch. 1.1 p.2). Prior to the spec the C2PA wrote privacy-preserving Guiding Principles: implementers are *strongly encouraged* to give creators control whether provenance is included. Other C2PA documents address UX and harms modelling (p.2). Limit kept: the spec deliberately does not say if content is true or good; validation is association + well-formedness + tamper-evidence only (§1.2 p.2, §1.3 p.3).

2. **Asset, Manifest, Claim, Assertion, ingredient (Ch. 2 Glossary pp.6–8, Ch. 6 Assertions pp.23–26, Ch. 10 Claims pp.36–45, Ch. 11 Manifests pp.47–56, §18.15 Ingredient pp.186–197).** An *asset* is the content; a *C2PA Manifest* is the JUMBF box(es) carrying a *claim* (hashes over assertions) plus claim signature and credential. *Assertions* are typed facts (data hash, actions, ingredient, metadata, etc., §6.1–6.8). An *ingredient* assertion (§18.15) names a parent asset used to produce this asset and may carry that ingredient's own ingredient's `validationResults`. The manifest store may be embedded (`c2pa` JUMBF) or external (Ch. 11.4–11.5 pp.55–56). Limit kept: manifest present ≠ content trusted; it only means provenance statements traveled with the asset and were signed (§1.2 scope p.2, Ch. 10.2–10.3).

3. **Hard and soft bindings to content (Ch. 9 pp.34–35, §18.5 Data Hash pp.130–132, §18.10 Soft Binding pp.162–166).** *Hard bindings* (§9.2) are cryptographic hashes `c2pa.hash.data` / `c2pa.hash.bmff` / `c2pa.hash.boxes` over the asset bytes (or boxes) recorded in the claim; they fail if bytes differ. *Soft bindings* (§9.3, §18.10) are perceptual/watermark signals for cases where bytes must change (e.g., re-encode). `Thumbprint`/data-hash assertions enumerate `alg: sha256|sha384|sha512` and `exclusions`. Limit kept: hard binding requires exact byte control and container support (Appendix A pp.214–229 lists JPEG, PNG, MP4, PDF/ZIP embeddings); for plain UTF-8/Markdown tape text there is no standard JUMBF container, so an external manifest or sidecar is the only embedding (§11.4).

4. **Claim creation and multi-step processing (Ch. 10.3–10.4 pp.39–45, Fig. 13 p.73).** Creating a claim: hash each assertion → build assertion store → hash the claim → sign with `signingCredential` (X.509, COSE) → time-stamp (RFC 3161). `c2pa.actions` records `action: created | edited | published | ...` with `softwareAgent`, `parameters`, `when` (§18.14 pp.170–185). Multi-step ingredients preserve each ingredient's manifest store via `validationResults` copy (§10.4). Limit kept: the spec does not define editorial policy for *which* actions to assert nor guarantee every edit is asserted — generators choose what to disclose (Ch. 16 UX p.111).

5. **Validation as Well-Formed / Valid / Trusted with standard status codes (Ch. 14 Trust Model pp.63–72, Ch. 15 Validation pp.73–105, esp. §15.2 pp.74–78, §15.7–15.12 pp.86–103, Ch. 16.3 Disclosure Levels p.111).** Validation is multi-phase: signature, time-stamp, credential revocation (OCSP `rVals` §14.5 p.72), assertions, ingredients, content (§15.1.2). Status codes include success `claimSignature.validated`, `assertion.dataHash.match`, `signingCredential.trusted`, `timeStamp.trusted`; informational `ingredient.unknownProvenance`; failure `claimSignature.mismatch`, `assertion.dataHash.mismatch` (§15.2). Manifest validation state per §14.3 and §15.3 (§84–85): *Well-Formed* (syntax), *Valid* (hash+signature), *Trusted* (signer in trust list and not revoked). Ch. 16.3 defines disclosure levels for UX (minimal/standard/full) to respect creator privacy choices. Limit kept: Trusted requires an externally governed trust list (§14.4) and fresh OCSP; without it a manifest is at most Valid, not Trusted.

6. **Harms, misuse and abuse as open operational problem (Ch. 17 pp.113–114, §17.1–17.2; §14.2 Identity of Signers p.63; Ch. 16.4 p.112).** The spec lists threat considerations (credential theft, manifest stripping, ingredient replay, deepfake laundering) and states harms modelling is separate and ongoing. §17.2 and p.112 note public review is required and the spec *SHOULD NOT* be used to block content accessibility (§1.2 box p.2). Limit kept: provenance ≠ authenticity of depicted facts; a correctly signed manifest can still carry false `metadata` or misleading `actions` — the consumer (or publication check) must judge meaning, the spec judges binding.

**Why this literature, for this cell.** Field `publication-and-attribution` is "the reader book, the DEV blog, commits, CI and pushes" and angle is *recent* (2023–2026). C2PA 2.2 (2025-05-01) is the current cross-industry answer to "how does a published byte claim who made it, from what ingredients, and whether it was tampered with" — exactly the honest-public-voice mechanism the plant's DEV articles and wall-outcome tapes trade on without yet having a typed provenance vocabulary.

## What this plant already does

*The plant publishes to three surfaces with three different provenance mechanisms that never meet as one typed manifest — commits have hash chains, wall outcomes have a digest line, DEV articles have no cryptographic provenance at all.*

- **Wall-outcome tape is the only publication with a typed digest and strict decoder.** `src/mishe_tauftauf/outcome_publication.py:43` defines `OUTCOME_KINDS=('accepted','blocker-resolved','blocker-retired','hypothesis-changed')`, `_HEADER` and `_DIGEST = re.compile(r'[0-9a-f]{64}\Z')` (sha256 hex), `OUTCOME_PREFIX / HANDOFF_MARKER`, and `REFERENCE_RE` (from `records.py`). `OutcomePublication(kind,role,reference,digest)` at :164 plus `has_outcome_prefix / starts_outcome_publication / parse_header / reference_lines / sole_final_reference / reference_digest / decode_publication_body / publication_prose / decode_text / decode_evidence / decode_supersedes / decode_work_handoff / decode_excerpt` implement a deterministic, import-safe dialect for `Wall outcome <kind> by <role>` with a final `[record] <path> <hex64>` line. `docs/how-it-works.md:588-593` and `docs/recovery.md` describe that the digest proves byte-presence of an artifact, not authorship beyond role attribution via the seed lock. No ingredient assertion, no manifest store, no hard/soft binding distinction, no validation state — a reference line is a pointer, not a typed `c2pa.ingredient` with embedded `validationResults`.

- **DEV/blog publication is editorial initiative without content credentials.** `docs/how-it-works.md:488-495` and `src/mishe_tauftauf/seed_docs_charter.md` declare that `pub` owns "editorial initiative, DEV articles/corrections/comments and reader relationships on the existing blog https://dev.to/ilya_mozerov_867dbdd91feb" with "honest agent voice, Mesh historical attribution, remote-action reconciliation and privacy limits." `checks/pub-devto-watch-delivery.py` and `checks/pub-devto-watch-timer.py` watch DEV delivery, but no manifest, no ingredient chain from wall outcomes/records to article hashes, and no JUMBF/external-manifest embedding is produced or validated. The published markdown is what the reader sees; the provenance is a commit message and a human's memory of the three review URLs (as in pub wake 108315 article 4942462).

- **Commits and CI have hash provenance but no attribution manifest.** Git `main` gives content-addressed commit SHA and `push` checks exact-SHA CI, which the plant leans on (AGENTS.md genome pushes `main` and checks CI). However there is no C2PA-style `c2pa.actions` trace ("created/edited/published" with `softwareAgent` and `when`) over the derivation `records → outcome publication → DEV article`, nor a typed `validation state` — the plant's checks answer `PASS/FAIL` per checker, not `Well-Formed/Valid/Trusted` per manifest. `docs/publication-checks.md` defines the Laya/Codex `post_check` preflight banks `R01–R08 / P01–P28` with `clear/suspicious/unknown` verdicts and a 2 MB budget, but its `publication status` line is not a manifest credential; `Laya` and `codex_review` are classifiers, not signers of a `claimSignature`.

- **Privacy vocabulary exists nearby but not for publication.** `src/mishe_tauftauf/body_perception.py` carries Nissenbaum CI (appropriateness + flow `PERSONAL_CONTEXTS / BODY_INFORMATION_TYPES`) and the recent `sensing-and-privacy--metric` landing added k-anonymity `qi_histogram / k_anonymity_k` as a pure metric with no publishing behavior. There is no disclosure-level control for a published article (C2PA Ch.16.3 minimal/standard/full) that lets a creator include provenance minimally while preserving privacy — the plant either publishes exact microdata (dense queue) or withholds, with no typed redaction of assertions (§6.8 `c2pa.redactedAssertions` p.25) analogue.

*Consequence the source predicts.* Ch. 1 p.2: without a `Content Credential` that is `associated with the underlying asset, correctly formed, and free from tampering` the reader must take attribution on prose trust alone; a stripped or replayed article has the same bytes but no `dataHash.match` failure to observe, so mis-attribution is invisible and the `SHOULD NOT provide value judgments` separation collapses — the plant's unavailable `unknown` and the checker's `clear` cannot be told apart by a reader holding only the markdown.

## What is new here

**A typed, pure, verdict-free provenance vocabulary beside the wall-outcome decoder — so a published artifact can name its ingredients (record digests it derived from), its disclosure level, and the validation state a reader should expect, without changing any `Feed.append`, `seed yield`, or DEV publish behavior.**

Five ideas transfer directly, each with a landing line in the target file and each bounded by what C2PA concedes.

1. **Manifest / claim / assertion / ingredient as typed facts, not prose (Ch. 2, Ch. 6, §18.15).** Today an outcome publication lists record references as opaque lines; a DEV article cites mesh reviews by URL in prose. The transfer makes `ingredient` a typed tuple `(path, sha256, validationState)` with `c2pa.ingredient`-shaped helpers (`provenance_ingredient`, `provenance_manifest_summary`) so that "this article derived from records X,Y" is a hash-checked claim rather than a remembered URL. No claim is signed in this commit — the shape is the vocabulary, the signature is future work.

2. **Hard vs soft binding distinction for tape text (§9, §18.5, §18.10, App. A).** The plant holds UTF-8 tape text; a hard binding is `sha256(bytes)` (already the wall-outcome `RE: [0-9a-f]{64}` on the final reference line, but not labeled as `assertion.dataHash.match`). The transfer introduces `provenance_data_hash(bytes) -> hex` and documents that hard binding exists for tape/markdown and soft binding does not apply (no perceptual hash for prose). An external manifest per §11.4 is the documented embedding for markdown, not JUMBF-in-asset — the reader checks an adjacent `manifest.json` or the git blob hash, not a JUMBF box inside the markdown.

3. **Validation states Well-Formed / Valid / Trusted and standard status codes (§14.3, §15.2–15.12).** The plant's publication checks return `clear/suspicious/unknown` per question bank; C2PA separates that from manifest validation (`Well-Formed → Valid (hash+signature) → Trusted (signer in trust list)`). The transfer exposes `ManifestValidationState = Literal["well-formed","valid","trusted"]` and `validation_state_for(ingredient)` pure predicate that maps `dataHash.match + signature.validated + signingCredential.trusted` codes to those three levels, without touching the Laya/Codex classifiers. A published article without a trust list is correctly typed as `Valid` at best, not `Trusted` — the limit is visible.

4. **Disclosure levels as privacy-preserving publishing choice (Ch. 1 p.2 Guiding Principles, §16.3 p.111, §6.8 p.25).** C2PA requires creator control and defines minimal/standard/full disclosure plus `redactedAssertions` for selective omission. The transfer introduces `DisclosureLevel = Literal["minimal","standard","full"]` and documents that `minimal` carries only `claimSignature.validated + dataHash` while `full` includes `actions` and all ingredient digests — mirroring the plant's honest-voice requirement (pub charter privacy limits) as a typed publication-time choice rather than a prose promise. No assertion is redacted in this commit; the level is the vocabulary.

5. **Harms model as open problem with the "no value judgment" boundary (Ch. 17 pp.113–114, Ch. 1 box p.2).** The spec's `IMPORTANT` box is the boundary this plant most needs: a `Trusted` manifest does not mean the content is true. The transfer documents this boundary in the module header and per-symbol docstrings (`SHOULD NOT provide value judgments` cited verbatim) so that a future validator presenting `Trusted` does not become a truth oracle — the semantic `R01–R08/P01–P28` questions remain the meaning judge, the manifest judges binding. The `§17` open-problem note is kept: credential theft, stripping, and ingredient replay are not solved by adding the vocabulary.

**Limits the proposal keeps from the source.** No X.509 signer, no COSE `claimSignature`, no RFC 3161 time-stamp, no JUMBF embedding, no soft-binding watermark, no trust list or OCSP fetch (§14.4–14.5) is implemented; no `Feed.append` or `seed yield` path is changed; no DEV publish call is added; validation is pure predicate over already-present `hex64` digests, not a network fetch; the `redactedAssertions` mechanism is documented only; and the "ingredient chain validates" claim is explicitly typed as `Valid` not `Trusted` until a trust anchor exists — exactly the §14.3/§15.3 caveat the spec requires.
