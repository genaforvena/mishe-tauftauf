Operational mechanism extracted (pp.5–6 in this layout, §2.1 lines 357–415): Glanville re-presents Maxwell's Black Box via Ashby 1956 *An Introduction to Cybernetics*: "The principle of the Black Box is that, where we observe some change in a behavior, we construct and insert a Black Box allowing us to interpret the change as the result of the operation of an invisible mechanism, held within the Box, on what is now seen as input giving rise to output. The observer/scientist develops a description functioning as a mechanism/explanation (i.e. model) which accounts for the transformations of what are now input into output. The explanation is purely historical and the product of the interaction between the observer and his inventive, fictional insertion, the Black Box, although we come to believe that this explanation opens up (that is, Whitens) the Black Box — even if this Whitening is excluded, by definition. We do not know the cause, we have not looked inside the Black Box and, therefore, cannot observe it" (lines 360–370). Annexation: "The Black Box was annexed to Cybernetics by W Ross Ashby. In what may be the key basic text, his 1956 'Introduction to Cybernetics', he uses the Black Box artifice to permit the (scientific) observer to construct a description explaining the behavior to date of some system that interest us. The Black Box contains a presumed mechanism, which cannot be seen and is the product of the observer's interaction with the whatever-it-is. Ashby went so far as to suggest the Black Box might not be just a useful device, but universal, suggesting that we never really see what's causing a change, only some explanatory principle we take as a mechanism" (lines 380–386). Observer condition: "What is vital, for the development of second order Cybernetics, is that the Black Box is essentially and crucially a construct of the observer. When we use this concept, we bring the observer in to the process, rather than denying him. That the Black Box requires the observer's presence is acknowledged, and is circularly connected in. The observer watches and changes. What the observer learns he learns from interaction with the Black Box (which is his construct). Who can know what the (obscure) Black Box does?" (lines 405–412). Glanville adds second circularity (§2.2): the circularity of the observed system plus the circularity of the observing system observing it.

Limits of this reading: the chapter is a historical-philosophical survey (1968–1976 revolution, thermostat, Wiener, Macy Conferences), not a detector specification; the "mechanism" is the artifice of inventing a fictional interior and treating whitening as historical reconstruction rather than opening. No state-machine formalism or pass/fail threshold is given — the transfer below uses only the operational move: compare inputs/outputs historically without opening the box, and declare the observer's construct explicitly.

## What is new here

Glanville's Black Box formulation names a design choice the plant already makes and a limit it already accepts, in field-native terms.

1. **A detector is a Black Box witness by intention.** Glanville's description — construct a box around the obscure mechanism, read inputs/outputs, invent a model that accounts for the transformation historically, and call that model the mechanism — is exactly what `checks/observer-source-identity.py` does. Input is HEAD (tracked files `src/mishe_tauftauf/*.py` per commit) and the root's carried files; output is the identity verdict (HEAD / older commit / mixed / working-tree / declared-mismatch) with the differing modules listed verbatim (`differing_modules`). The interior that would "really cause" the service's behaviour — the live Python objects in memory — is never opened; the model is built from blob ids, which are the historical trace. The header can say so directly, citing Glanville §2.1 and Ashby 1956 universality, so a reader sees that git-blob comparison is not incidental hygiene but the Black Box method: treat the service as a box, reconstruct what must have been inside from history.

2. **The Box is the observer's construct and must be declared.** Glanville's vital point — the box requires the observer and is circularly connected — is already how the plant avoids the quiet-observer fallacy. `unit_import_roots` names the observer (the unit, the roots it runs from), `reproducing_commits` names the commits whose bytes could have produced the observed directory, and `declared_finding` checks the site's own declaration (`declared_roots.json`) against the same history. A review that pretends the check "just observes" would be first-order; second-order is to write down which brick produced the reading (`declared-roots.json` plus `tracked_relative`/`head_blobs`/`classify_tracked` for the working tree). The proposal does not change what is filed — it names why it is filed.

3. **Whitening is never opening.** Glanville stresses that we come to believe whitening opens the box even though it is excluded by definition; the explanation remains fictional and historical. For the plant this is the correct caution about `reproducing_commits`: a commit whose bytes exactly reproduce the directory explains the directory to date, but does not prove the directory was *produced* by checking out that commit — it could be a hand copy that happens to match. The check already honours this by reporting `mixed` and by distinguishing `running tree reproduces HEAD` from `working tree matches HEAD`. Naming the method as Black Box whitening lets a reader see why mixed-commit is the expected failure of a hand-assembled runtime.

Complements, not repetitions: Pask 1979 (previous mechanism) is about agreement as analogy — what a verdict means relative to the fields compared (`VERDICT_FIELDS` disclosure on AGREE). This mechanism is about how the verdict is produced without opening the observed. The von Foerster 1971 transfer (previous turn) is about trivial vs non-trivial machines — when an observation is history-independent. Together they answer three different SOC questions about the same observers.
