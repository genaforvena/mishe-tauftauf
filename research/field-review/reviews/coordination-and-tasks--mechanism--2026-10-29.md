## What we read

Thomas W. Malone and Kevin Crowston, **"The Interdisciplinary Study of Coordination"**, MIT Center for Coordination Science Technical Report CCS WP #157, November 1993; published as *ACM Computing Surveys* 26(1), March 1994, pp. 87–119 — read full text at:

- <https://ccs.mit.edu/papers/CCSWP157.html> (HTML, MIT CCS, CC BY-equivalent public TR, ~38 pp., TOC §§1–5 + Appendices A/B + REFERENCES, fetched 200 2026-10-29)
- <https://doi.org/10.1145/182139.182140> (ACM DL DOI 10.1145/182139.182140, same paper)
- <https://dspace.mit.edu/handle/1721.1/2649> (DSpace record, same TR)

Four passages carry the operational mechanism this plant mis-implements as lock arrival:

1. **Coordination = managing dependencies between activities (§2.1).** "Coordination is the process of managing dependencies between activities" — invoked for the conference, basketball team, assembly line intuition ("good coordination is nearly invisible ... we notice coordination most clearly when it is lacking" §2.1) and then made analytic: characterize the *dependency*, then name the *coordination process* that manages it. Table 1 (§2.2) is the handbook sketch this definition enables: shared-resource → first-come/first-serve / priority order / budgets / managerial decision / market-like bidding; task assignments → (same as shared resources); producer/consumer prerequisite → notification / sequencing / tracking; transfer → inventory management (Just In Time / Economic Order Quantity); usability → standardization / ask users / participatory design; simultaneity → scheduling / synchronization; task/subtask → goal selection / task decomposition.

2. **The generic task assignment problem (§2.3.1).** A system produces products each requiring tasks; tasks are typed and only server actors specialized for that type can perform them; which tasks appear cannot be predicted in advance and are known only to client actors at run time. The text calls this "not universally applicable" but "an abstract description that can be applied to many common task assignment situations" — its two planted examples are (1) "designing, manufacturing, and marketing different kinds of automobiles" and (2) "processing steps in different jobs on a computer network." The dependency is therefore a concurrent, unpredictably-arriving shared-resource (actor time) plus prerequisite (client knows, server must be told).

3. **Two operational mechanisms for the same dependency, with message types (§2.3.2, Smith & Davis 1981).** The paper contrasts them directly: (a) *highly centralized* — all clients and servers send all information to a central decision maker who decides which servers perform which tasks and notifies them; (b) *highly decentralized competitive bidding* — formalized by Smith & Davis — "a client first broadcasts an *announcement* message to all potential servers. This message includes a description of the activity to be performed and the qualifications required. The potential servers then use this information to decide whether to submit a *bid* on the action. If they decide to bid, their bid message includes a description of their qualifications and their availability ... The client uses these bid messages to decide which server should perform the activity and then sends an *award* message to notify the server that is selected." The three typed messages (announcement/bid/award) are the mechanism, not the metaphor.

4. **How to choose between mechanisms — production / coordination / vulnerability tradeoff (§2.3.2, Malone 1987; Malone & Smith 1988, queueing/probability models).** The paper does not endorse one mechanism: "they developed formal models to represent various forms of *markets* (centralized and decentralized) and various forms of *hierarchies* (based on products or functions). Then they used techniques from queueing theory and probability theory to analyze tradeoffs among these structures in terms of *production costs*, *coordination costs*, and *vulnerability costs*." Result reported: centralized schemes had lower coordination costs but higher vulnerability to processor failure; decentralized markets much less vulnerable but high coordination cost; decentralized (product) hierarchies low coordination cost but unused capacity → high production cost. §3.1 makes the methodology explicit as parametric vs baseline analysis — parameters like incentives, cognitive capacity, and communication cost differ across human/computational/biological systems, so the same mechanism's cost vector moves with the substrate.

**Limits the source states (§3.1, §2.4, §2.3.3).** "Even though these models omit many important aspects of human organizations and computer systems they help illuminate a surprisingly wide range of phenomena" (§2.3.3); §3.1 warns any theory "must neglect some things, in order to focus on others" and that coordination is one perspective alongside rational/structural/political (Kling 1980). Table 1 lists are "by no means ... exhaustive" and Crowston's task/resource taxonomy is one of several. The paper separates group decision-making (§2.4.1: authority vs voting vs consensus/negotiation) and communication (§2.4.2: alternative forms, standards, common knowledge) as distinct processes that coordination mechanisms compose, not replace — so bidding presumes a standard for describing tasks/qualifications and a decision rule for awarding.

## What this plant already does

*The plant manages the same task-assignment dependency (§2.3.1) that the paper studies, but with a single mechanism — self-selection arriving at one lock — and no announcement/bid/award vocabulary, so the paper's cost tradeoff is not observable.*

- **Entry and ownership path is lock-centralized, client-less.** `src/mishe_tauftauf/task_state.py:140` `registry(entries)` projects lifecycle from the shared tape; `task_state.py:294` `candidates(entries, now)` and `task_state.py:503` `select_task(entries, owner, now)` return the same advisory list to every role ("a role is a responsibility, not an eligibility partition" docstring :295); `task_state.py:429` `claim(home, identity, owner, wake, reason, evidence)` reserves an identity under `deliveries/<identity>.json` existence and delivery-owner checks (`_claim_delivery_owner` :419). Publication itself is `src/mishe_tauftauf/feed.py:42` `publication_lock` (`threading.RLock` + `fcntl.flock` on `.publication.lock`): arrival order at one host's `flock` decides who claims first. `docs/wall-coordination.md:5-9` states the doctrine as "Minds choose work, organize their plate and ask peers for help" with no dispatcher; settlement is `src/mishe_tauftauf/wall.py:648` `settle` / `src/mishe_tauftauf/seed.py:929` `yield_wake`.

- **Coordination process today is first-come/first-serve + managerial decision, exactly two cells of Table 1 — nothing else.** First-come/first-serve is the `flock` arrival race; managerial decision is `genome` pushing `main`, checking exact-SHA CI, and owning `wall-coordination.md`'s trial (`AGENTS.md` "Genome pushes `main`..."). The other Table 1 mechanisms for shared-resource/task-assignment — priority order, budgets, market-like bidding — have no reification. There is no `announcement` broadcast from the client that knows the task, no `bid` carrying qualifications/availability, and no `award` decision by the client; `claim` is a unilateral server-side reservation, not a client award after comparison.

- **The three bid components the paper requires are absent on the tape.** The contract-net messages would have to carry: announcement = description + qualifications required; bid = qualifications + availability; award = selection. Today's tape carries `task_state.TaskState` fields `identity, status, next_step, owner, reason, helpers, sequence, delivery` plus a `delivery_token`; `feed.py:134` `utc_now()` header `v1 {sequence:020d} {timestamp} {source} ::\n` (`feed.py:139` `_encode_entry`, `feed.py:20` `HEADER_RE`) serializes one total arrival order, not the three message kinds. `wall.py:520` `message` (`[dm] to=ROLE`) is a visible-but-ephemeral generic DM, not a typed `announce/bid/award` for task assignment.

- **Consequence the tradeoff predicts.** Under a burst of task creations from multiple clients, every idle role races to `candidates` → `select_task` → `claim` against the same `flock`. The contention cost is coordination cost in the paper's sense (messages/decisions before work), paid entirely in lock waiting, with no balancing production cost (who is actually best equipped) and no explicit vulnerability assessment (if the central `flock` host is slow, all awards stall). A decentralized market would spread coordination cost as broadcast + bids but reduce vulnerability; a product hierarchy would reduce coordination cost but leave capacity idle. The plant cannot state which tradeoff it has chosen because it has not named the alternatives — the only feedback today is `permit recover` on failure, not the §2.3.2 production/coordination/vulnerability decomposition.

- **Best nearby precedent for the transfer.** `research/field-review/reviews/coordination-and-tasks--transfer--2026-10-29.md` (this field, same source) already landed Malone's dependency taxonomy as a *diagnosis* — adding typed `dependency` (shared-resource/prerequisite/transfer/usability/simultaneity/task-subtask/other) + `depends_on` to `TaskState` and making `eligible`/`candidates` prerequisite-aware. That review gives the vocabulary for *which* dependency is being managed; this one adds the *mechanism* that manages it (Smith & Davis announcement/bid/award) and the *cost* by which to compare the mechanism to the existing lock-centralized one. `coordination/site_sync.py:326` `_close_stale_sync_tasks` already implements one award-like "newest SHA wins" (largest-ID supersedes older `kernel-sync-*` tasks) but it is scoped to replant, not generalized to task assignment. `src/mishe_tauftauf/wall_view.py:42` `pane_lease_lines` / `src/mishe_tauftauf/observations.py:363` `pane_lease_age` show how a second consumer can read the same tape differently — the same bid/award messages can be stigmergic substrate for health vs genome without extra writes.

## What is new here

**Treat task assignment as an explicit client-driven bidding market — announcement → bid → award — beside the current first-come claim, and make the production / coordination / vulnerability tradeoff measurable, exactly as §2.3.2 prescribes.**

1. **The paper's three message types are a drop-in protocol for "minds choose" without adding a central scheduler.** The client that creates the task is the natural `announcement` originator (it holds the description that the servers lack — the §2.3.1 asymmetry clients-know, servers-can-do); servers that are *qualified* (role in `helpers`, matching retry predicate in `task_state.py`, evidence path checked) decide to `bid` with their availability (wake, leases, `observations` probe) and qualifications; the client `award`s one. Today `candidates` → `claim` collapses the three steps into one server-side decision: whoever arrives at `flock` first wins, regardless of qualification breadth or availability depth, and the client never decides. Malont & Smith's analysis predicts the exact cost of that collapse: low communication but arrival-order bias and single-host vulnerability.

2. **The mechanism does not replace the existing paths — it adds the missing Table 1 row and makes the choice falsifiable.** Table 1 predicts five interchangeable processes for shared-resource/task-assignment; keeping first-come/first-serve and adding market bidding side-by-side is parametric analysis in §3.1's sense: same tape, different parameter (communication cost up, vulnerability down). A task row can now be read twice — once through the current `select_task` self-selection path, once through the `announcement → bids → award` path — and the difference in attempts-to-award, stale claims retried, and head waits becomes the coordination cost. `src/mishe_tauftauf/native_recovery.py:100` `DEFAULT_RETRY_LIMIT = 3` / `TRANSIENT_STATUS` and `src/mishe_tauftauf/recovery_policy.py:8` `transition(deadline, stable_seconds, max_gap)` already carry time budgets; the new mechanism just makes where the budget is spent legible.

3. **Standards and group decision rule are part of the mechanism (§2.4), not external.** The paper notes communication standards (how to describe tasks/qualifications) and the decision rule (authority vs voting vs consensus/negotiation) are coordination processes themselves. On this plant the standard is already `TaskState.identity/next_step/reason/helpers/dependency/depends_on` and `chat_protocol.decode_lifecycle`; the decision rule for award is deterministic "lowest coordination + production cost" or "first qualified bid meeting a threshold" — both analogous to the product vs market hierarchy comparison Malone & Smith model. Recording the award as a tape entry (`award:<task>:<winner>:bids=N`) makes the decision audit-replayable via `task_state.registry`.

4. **Limits kept.** This does not replace `publication_lock` ordering or add a new lock — bids and the award are ordinary tape entries under the same `flock`; total order remains arrival. It does not claim an optimal mechanism — the paper insists "one question that arises immediately is how to categorize these dependencies and coordination processes" and that lists are not exhaustive; the transfer is the handbook entry, not a theorem. It does not model incentives (Turoff bidding for internal projects §2.2.1) or common-knowledge formation (§2.4.2); those remain §2.4 concerns composable later. Production/coordination/vulnerability numbers from §2.3.2 are reported as counts/durations on the tape (bids sent, time announcement→award, lock wait), not as queueing-theory closed forms.

## Application

**Add the Smith & Davis announcement → bid → award protocol as additive, pure helpers beside `states`/`candidates`/`claim`/`eligible` — no change to `publication_lock` ordering, no new branch, no threshold change.**

1. **Add typed helpers `announcement`, `bid`, `award` and `bid_cost` beside `candidates`/`select_task` in `src/mishe_tauftauf/task_state.py`.** Each is a pure function over `list[FeedEntry]` and a tape-derived index: `task_announcements(entries) -> dict[identity, FeedEntry]` reads entries whose body carries `announce:<task>:requires=<qual>` (control tag `task-announce`); `task_bids(entries, identity) -> list[Bid]` reads `bid:<task>:qual=<qual>:available=<wake>` (`task-bid`); `award_task(entries, identity) -> Award | None` reads `award:<task>:winner=<role>:bids=N` (`task-award`). `Bid` is `NamedTuple(identity, bidder, qual, available_wake, sequence)` ordered by `sequence` (arrival tie-break); award selection is deterministic "lowest `bid_cost` then lowest `sequence`" where `bid_cost(bid) -> tuple` encodes the paper's tradeoff in tape terms: `coordination = bids_seen`, `production = qualifier mismatch penalty`, `vulnerability = host staleness (observations age)`. Validate with `validate_control`/`EVENT_RE`/`validate_slug` as `validate_control` (:76) already does.

2. **Wire `eligible`/`candidates` as a view of the market without changing refusal semantics.** Extend `eligible(state, entries, now)` to deny a task whose `depends_on` prerequisite is unawarded (the transfer review's `depends_on` field) and whose `announcement` exists but no `award` yet covers `owner` — i.e. a task is eligible for non-bidders only when no market exists; once an `announcement` exists, only bidding servers are eligible until the `award` closes the round. `candidates`/`select_task` remain as the bidding-client path: a bidder's `select_task` prefers its own `award`s, then tasks where its `bid` is winning, then classical `candidates` — the paper's decentralized market beside the product hierarchy. No `WALL_MAX_*`, `HEADER_RE`, `publication_lock`, or audit digest changes.

3. **Publish one cost telemetry helper, no daemon.** `announcement_cost(entries, identity) -> dict{coordination, production, vulnerability, latency}` computes from the award entry: `coordination = len(bids)`, `production = sum(mismatch penalties)`, `vulnerability = max host age at bid time`, `latency = award.sequence - announcement.sequence`. This is the `production/coordination/vulnerability` triple Malone & Smith analyse, read from the tape.
