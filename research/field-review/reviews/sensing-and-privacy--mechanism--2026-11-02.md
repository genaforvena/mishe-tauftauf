## What we read

Úlfar Erlingsson, Vasyl Pihur, Aleksandra Korolova — **"RAPPOR: Randomized Aggregatable Privacy-Preserving Ordinal Response"**, *Proceedings of the ACM Conference on Computer and Communications Security (CCS '14)*, Nov 3–7 2014, Scottsdale AZ, ACM 978-1-4503-2957-6/14/11, DOI 10.1145/2660267.2660348 — read the full 12-page CCS PDF at:

Seven passages carry the operational mechanism; each replaces a one-shot randomisation claim with a typed, longitudinal budget this plant can import as pure vocabulary.

1. **Two-stage randomized response with Bloom encoding (§2, p.4–6, Figure 1 p.5).** Client value `v` is hashed onto a Bloom filter `B` of size `k` with `h` hash functions (step 1, p.5). Permanent randomized response (step 2, p.5–6) maps each bit `B[i]` to `B'[i]` as `1` with prob `0.5 f`, `0` with prob `0.5 f`, otherwise `B[i]` with prob `1-f` where `f in (0,1)` is the longitudinal privacy parameter. Instantaneous randomized response (step 3, p.6) maps `B'` to report `S` with `P(S[i]=1|B'[i]=1)=q` and `P(S[i]=1|B'[i]=0)=p`, with `p,q in [0,1]`. Report `S` (size `k`) is sent; `Bloom filters serve not only to make reports compact, but also to complicate the life of any attacker (since any one bit … may have multiple data items in its pre-image)" (p.5). The example run uses `k=256, h=4, f=0.5, p=0.5, q=0.75` (Figure 1 caption p.5–6: 145 of 256 bits set, 2 of 4 signal bits survive to `B'`, both re-randomized to `S`).

2. **Memoization as the longitudinal primitive (§2, p.4, p.6).** `B'` is memoized and reused as the basis for all future reports on the same distinct value `v` (p.5: "Subsequently, this B' is memoized and reused as the basis for all future reports on this distinct value v"). Without it, "an adversary estimates the true value from observing multiple noisy versions of it" via averaging (p.6). Memoization is "absolutely effective … only in cases when the underlying true value does not change" (p.4) — if `v` moves `a->b`, two memoized values `B'_a, B'_b` are reused and may be correlated, so "an attacker … could learn those memoized 'noisy' values with arbitrary certainty … the attacker cannot be certain of the values of a and b because of memoization. This said, if a and b are correlated, [leakage remains]" (§1.2–§2, p.3–4). This bounds the contribution of memoization explicitly.

3. **Permanent epsilon (Theorem 1, p.8).** The permanent response alone (steps 1–2) satisfies `ε_∞`-DP where `ε_∞ = 2h ln((1 - 0.5 f)/(0.5 f))` (Theorem 1 display p.8–9). Proof bounds `RR_∞ = P(B'∈R*|B=B1)/P(B'∈R*|B=B2)` maximised when `h` signal bits differ (p.8–9). Therefore "ε_∞ is not a function of `k`. It is true that a smaller `k`, or a higher rate of Bloom filter bit collision, sometimes improves privacy protection, but, on its own, it is not sufficient nor necessary to provide ε-differential privacy" (p.9, sentence kept). Large `h` and small `f` inflate the budget; `f->1` drives `ε_∞->0` at cost of utility.

4. **Instantaneous epsilon (Lemma 1 + Theorem 2, p.9).** With one collection per client, privacy is amplified by the second randomisation. Lemma 1 gives effective bit probabilities `q* = P(S[i]=1|B[i]=1) = 0.5 f(p+q) + (1-f)q` and `p* = P(S[i]=1|B[i]=0) = 0.5 f(p+q) + (1-f)p` (p.9, mixture of random and true). Theorem 2: the instantaneous report (step 3) satisfies `ε_1`-DP with `ε_1 = h ln( q*(1-p*) / (p*(1-q*)) )` (p.9–10). The paper's numerical example `p=0.5,q=0.75,f=0.5,h=4` yields `q*=0.625, p*=0.5` and `ε_1 ≈ 1.74` per report vs `ε_∞ ≈ 4.39` longitudinal — the two budgets are independently tunable.

5. **Three stripped variants (§2.1 p.7).** One-time RAPPOR skips the instantaneous step (single collection, no longitudinal need); Basic RAPPOR replaces Bloom with a deterministic 1-bit-per-string mapping when the domain is small and enumerable (`h=1`, p.7); Basic One-time RAPPOR combines both (simplest, one round on a direct map). These bound what we do *not* need when the domain is high-cardinality strings: Bloom is then necessary, cohorts matter.

6. **Cohorts and decoding (§4, p.11–13).** Each client is permanently assigned to one of `m` cohorts implementing distinct sets of `h` hash functions (p.11); cohorts "greatly improve the false positive" rate due to Bloom collisions (p.11). Decoding on the server re-runs analysis without recollecting: hypothesis testing, least-squares and LASSO regression to estimate population frequencies from noisy bit counts, without ever learning a client's value (p.2, §4). The paper notes privacy holds "even for a single client that reports often on the same value" (§1 p.2) and that RAPPOR avoids externalities such as "maintaining a database of contributing respondents (which might be breached), or repeating a single, memoized response (which would be linkable, and might be tracked)" (§1 p.2).

7. **Deployment existence proof (§1.1 p.2–3).** "RAPPOR has already seen limited deployment in Google's Chrome Web browser, where it has been used to improve the data sent by users that have opted-in to reporting statistics" (§1.1 p.3, §5.4). Example use is counting hijacked settings (malicious search-provider overrides) across many clients without learning which client is hijacked — the forest/trees line from the abstract (p.1: "allow the forest of client data to be studied, without permitting the possibility of looking at individual trees"). This certifies the mechanism is not a thought experiment.

**Why this literature, for this cell.** Field `sensing-and-privacy` names "host radio (host_radio.py), body perception, personal analysis" and angle is *mechanism* — an operational, implementable privacy mechanism, not a philosophy. The cell's 2026-10-29 landing (Dwork & Roth 2014 Ch.2–3) supplied central DP for aggregates: `ε,δ`, sensitivity, Laplace `Δf/ε`, composition `Σ ε_i`, group `kε` beside `stats_boundary.py`'s exact decoder. RAPPOR supplies the complementary local mechanism for sensed client-side values: randomised response *before* transmission, memoization for longitudinal collects, Bloom for open string domains, and two separately tunable epsilons — exactly the gap between "decode my adapter" / "aggregate my stats with noise later" and "collect a body reading repeatedly without learning which body sent which value."

**Limits the source states, kept here.** No threshold for `f,p,q,k,h,m` is mandated; tuning trades utility vs attack model (§3–§4). Memoization does not erase leakage when `v` drifts to a correlated value and attacker collects many reports (p.3–4). Bloom collision alone is not DP (Theorem 1 note p.9). LASSO/least-squares decoding and cohort de-biasing are not privacy proofs — they are utility procedures (§4). `ε_∞` and `ε_1` are worst-case over Bloom pre-images, not per-string. Crowdsourcing assumes many clients (thousands); utility with one device is nil. The mechanism is performed locally on the client and does not require a trusted third party (p.2), which inverts the curator model of Dwork & Roth §2.1 p.11 — calibration must happen before the wall bus, not at query time.

## What this plant already does

*The plant decodes exactly and publishes exactly — repeatedly — with no local randomization, no memoization, and no per-value longitudinal bound, even though the wall bus is a broadcast channel that collects many reports per value.*

- **Central DP for aggregates, local exactness for bodies.** `src/mishe_tauftauf/stats_boundary.py:35` carries Dwork & Roth 2014 vocabulary: `DP_EPSILON_DEFAULT=1.0`, `DP_DELTA_DEFAULT=0.0`, `DP_SENSITIVITY_COUNT=1`, `l1_sensitivity_count/sum`, `laplace_scale(Δf/ε)` (Thm 3.6 p.30), `is_valid_dp_params` with `δ < 1/n` gate (p.18 danger), `dp_composition Σ ε_i/Σ δ_i` (Thm 3.16), `group_privacy_epsilon kε` (Thm 2.2) and post-processing immunity (Prop.2.1). This bounds future releases of aggregated OMP stats — the curator model (§2.1 p.11). It does not randomize on the client, does not memoize, and does not handle open string domains via Bloom.

- **Body sensing is exact per report, with a bounded retention window but unbounded longitudinal linkage.** `src/mishe_tauftauf/body_perception.py:805` `DENSE_WINDOW_ROWS=2000`, `DENSE_TAIL_BYTES`, `DENSE_FRESH_SECONDS=30.0`, `read_redmi10_dense_baseline(... -> dict)` (`:849`) publish an exact histogram over the retained queue tail (~101 bytes/line, ~2.5k lines, last ~2.8 h at 5 s cadence, `:807–811`) with light-class counts (`_dense_light_class` `:839`), provenance min/max/mean and acceleration summary. `read_redmi10(... -> dict)` (`:644`) decodes battery/light/acceleration/ble_scan/wifi_link_rssi from the Redmi queue with exact values, sequence/cursor provenance, and `channel_provenance`. Each report of the same underlying value (e.g., same battery `92`, same light bucket) is byte-identical; an observer with many wall outcomes averages to certainty — precisely the averaging attack RAPPOR p.6 memoizes against. The module's privacy vocabulary since the sensing-and-privacy track is CI + per-type sticky receipts (`PERSONAL_CONTEXTS`/`BODY_INFORMATION_TYPES`/`TRANSMISSION_PRINCIPLES`/`_APPROPRIATENESS`/`_CI_FLOWS`/`PERSONAL_CONSENT_RECEIPTS` plus Belmont `BELMONT_*` and `QI_DEFAULT_KEYS`/`K_ANONYMITY_*` (Samarati & Sweeney Def.2.1/2.3)) — all are exact, per-type allow/deny tables and disclosure metrics, not randomised responses. No `RAPPOR`, `Bloom`, `memoiz`, `cohort`, `ε_∞`, `q*`, `p*` occurs (`rg -n "RAPPOR|Bloom|epsilon.*inf|q\\*|p\\*|memoiz|cohort" src/` 0 hits).

- **The wall bus is the longitudinal collector RAPPOR warns about.** `src/mishe_tauftauf/outcome_publication.py` + `docs/how-it-works.md:239` + `docs/protocol-boundaries.md:224` publish every `sense.body.redmi10` field quoted into a wall outcome/DM/discovery event to every attached mind as a single distribution. Each publication carries sequence, cursor, and receipt epoch — exactly the "linkable identifiers" / "privacy externalities" RAPPOR §1 p.2 says to avoid by not maintaining a breached database or repeating a linkable single response. RAPPOR's desiderata "without linkability of their reports" (abstract p.1) is therefore inverted: the plant's bus is linkable by design (for auditability), so the protection must be applied *before* publication if a body value is to be reported longitudinally — which today it is not.

- **Best nearby precedent for the transfer.** The four sensing-and-privacy predecessors landed pure, additive, verdict-free vocabulary beside decoders: CI contexts/tables + predicates (`is_body_info_appropriate_for_context`), BEQ critique hardening (closed-world invariants), 802.11bf negative capability (`WLAN_SENSING_SUPPORTED=False`), Kaye sticky receipts (`CONSENT_RECEIPT_VERSION`, `PERSONAL_CONSENT_RECEIPTS`), and Dwork & Roth DP scales/composition. Each added `Final` constants + pure predicates with no new I/O, no `SENSE_ID` verdict, no daemon path, and kept `check_parsing` green. The RAPPOR mechanism reuses exactly that precedent: `Final` `f/p/q/k/h/m` constants + pure `ε_∞/ε_1` helpers beside `DENSE_WINDOW_ROWS` and `_dense_light_class`, with no file read beyond the caller's already-held arguments.

*Consequence the source predicts.* "Randomization is essential" (Dwork & Roth §2.3 p.16) and "without memoization or other limitation on responses, randomization is not sufficient to maintain [longitudinal] privacy" (RAPPOR §1.2 p.4). The plant's exact body reports with no memoization are therefore not longitudinally private, even when CI receipts gate the redistribution — the budget degrades linearly with reports, and averaging drives certainty. The operational step is to name the client-local, memoized, two-stage mechanism that calibrates longitudinal vs instantaneous epsilon so a future noisy body histogram can be reviewed as a privacy choice rather than a collector's prose claim.

## What is new here

**Memoized, two-stage, Bloom-filtered randomized response as a typed, pure vocabulary beside the plant's exact body decoder — so the cost of repeatedly reporting the same body value is an `ε_∞` (permanent) and `ε_1` (instantaneous), not just a cursor, and many reports compose longitudinally without averaging to truth.**

Five ideas transfer directly, each with a landing line in the target file and each bounded by what Erlingsson et al. concede.

1. **Bloom-encoded signal as typed facts, not prose (§2 p.5–6, Figure 1).** Today the body's high-cardinality domain (e.g., future string-valued body types) has no compact noisy encoding. The transfer makes `RAPPOR_K_DEFAULT=256` and `RAPPOR_H_DEFAULT=4` explicit as the example Bloom geometry (the paper's Figure 1 caption values, reused as defaults), with docstring citing §2 p.5 "hash client’s value v onto the Bloom filter B of size k using h hash functions" and noting that collisions add uncertainty but alone are not DP (Theorem 1 note p.9). Without `k/h`, `ε_∞` has no coefficient.

2. **Permanent vs instantaneous budgets as `ε_∞` and `ε_1` (Theorem 1 p.8 + Lemma 1/Theorem 2 p.9).** The paper's two epsilons are separately tunable. The transfer exposes them as pure functions `rappor_permanent_epsilon(*, f: float, h: int) -> float | None` returning `2*h*ln((1-0.5 f)/(0.5 f))` when `0<f<1, h>=1` else `None`, and `rappor_epsilon_1(*, p: float, q: float, f: float, h: int) -> float | None` computing `q*,p*` per Lemma 1 then `h ln(q*(1-p*)/(p*(1-q*)))` per Theorem 2 — the `UNKNOWN`-style typed deny the plant uses for invalid budgets (analogous to `aoi_summary` warmup-None). This does not sample noise or change `read_redmi10()` — it only makes the longitudinal vs one-shot scales typed and import-safe, so a reviewer can check calibration without running the mechanism. Limit kept: memoized `B'` still leaks when `v` drifts to a correlated value and attacker collects many reports (p.3–4).

3. **Memoization contract as documentation and one predicate (§2 p.4–6).** RAPPOR's "Subsequently, this B' is memoized and reused as the basis for all future reports on this distinct value v" (p.5) becomes an explicit module invariant: a comment above the RAPPOR vocab that any future noisy body release on a stable value must reuse the same `B'` (or a per-value memoized seed), with a pure predicate `is_rappor_memoized_reporting(value: str, repeats: int) -> bool` stub returning `True` (always memoized — the typed rendering of "avoid an averaging attack" p.6) and docstring citing the `B'` reuse sentence. Repeated randomization without memoization is typed as invalid. The `f=0.5` default gives `ε_∞ ≈ 4.39` at `h=4` — visibly larger than `DP_EPSILON_DEFAULT=1.0`, signalling local fares worse utility on one device (chrome needed thousands).

4. **Client-local vs curator trust separation (RAPPOR p.2 vs Dwork & Roth §2.1 p.11).** "The RAPPOR mechanism is performed locally on the client's machine, and does not require a trusted third party" (p.2) versus Dwork & Roth's trusted curator holding `database D`. Transfer is a module note that `stats_boundary.py` is curator-side (noise at query time over many rows) while this vocabulary is client-local (noise before wall publication over many reports from one value). Docstring cites both and states the plant stays exact — any release that leaves the consented set `{senses, health, body-research, inference-research}` via the wall bus must name which model it used, or be exact and therefore not longitudinally private.

5. **Cohorts and decoding as typed limits, not added code (§4 p.11–13, §1 p.2).** Cohorts "greatly improve the false positive" rate (p.11) by sharding `h` hash families; decoding needs "hypotheses testing, least-squares solving, and LASSO regression" (abstract p.1). Transfer is `RAPPOR_M_COHORTS_DEFAULT: Final[int] = 64` (the evaluated default, §4 p.11) and a note that decoding is server-side over thousands of reports — not in this module, not with one Redmi. This bounds utility: a noisy release from one device is not aggregatable; RAPPOR's utility theorem requires population size `>> k`.

**Limits the proposal keeps from the source.** No noisy release, no random sampling, no Bloom construction, no hash, no LASSO, no cohort assignment, no `S` report, no persistent store of `B'` — only the typed budget vocabulary that makes a future local release reviewable. The mechanism sample itself (`S`) is not called inside `read_redmi10()` or `read_redmi10_dense_baseline()` in this commit; the plant stays exact. The correlated-drift leakage (p.3–4), Bloom-only not-DP caveat (p.9), and many-clients requirement (population statistics, §1.1) stay as documentation; the book's "single client that reports often on the same value" longitudinal guarantee (abstract p.1) is cited as the bound actually provided when `f>0` and memoization holds.
